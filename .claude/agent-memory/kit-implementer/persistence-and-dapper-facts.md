## EF Core and Unit of Work routing (#8, 2026-10-05; EF Core 10.0.12, Npgsql EF 10.0.3, EFCore.NamingConventions 10.0.1)

- **Unit of Work routing (one container, many Modules):** `ModuleBuilder` implements `IServiceCollection` and re-keys any unkeyed `IUnitOfWork` descriptor by the Module type; `AddPouryaKitModules` then adds one unkeyed router that reads the scope's `Operation.Module` (set by `IServiceProvider.BeginOperation`, which the Gateway calls). `EfRepository` takes `IUnitOfWork` and uses its DbContext. Persistence must `Add` (not `TryAdd`) its `IUnitOfWork`: a second `AddPouryaKitModules` call sees the first call's unkeyed router and TryAdd silently skips.
- **Allowed-references trap:** Postgres may not reference Modularity, so `module.UsePouryaKitPostgres<T>()` only works because ModuleBuilder *is* an IServiceCollection.
- Default schema comes from `RelationalOptionsExtension.Extract(options).MigrationsHistoryTableSchema` in `PouryaKitDbContext.OnModelCreating`.
- `IgnoreAny<DomainEvent>()` in ConfigureConventions stops `AggregateRoot.DomainEvents` becoming a navigation.
- A converted (typed-ID) numeric key is never made identity by convention; it needs `ValueGeneratedOnAdd()` per entity. With it, EF inserts with identity and reads the id back through the converter; the instance's Id stays null until save (no 0 or temporary value constructed).
- EFCore.NamingConventions snake-cases the history table's columns (`migration_id`) but not its name (`__EFMigrationsHistory`).
- `UseNpgsql("Name=ConnectionStrings:x")` resolves from DI `IConfiguration`; a design-time factory must register one or dotnet-ef fails.
- Ardalis.Specification.EntityFrameworkCore 9.3.1 restores and evaluates fine on EF Core 10; its `RepositoryBase.AddAsync` calls SaveChanges, so use only `SpecificationEvaluator.Default.GetQuery`.
- dotnet-ef 10.0.12: `--namespace` puts the model snapshot in a folder named after the namespace; pass `--output-dir` only. A test-project migration was generated with a temporary `IDesignTimeDbContextFactory` + temporary Design package, both removed after.
- `dotnet new tool-manifest` on SDK 10.0.401 writes `dotnet-tools.json` at the repo root; move it to `.config/`.
- `HostFixture` migrates from a scope of the built, not yet started Host, then starts it (review F2): a hosted service (Wolverine, #15) must find its tables at start. The Proving Sample's own packages are recorded in `docs/provenance/ModularMonolith.md`.
- #12: `EfRepository<,>` is public and unsealed; a specific repository derives from it and builds on `protected ListAsync<TResult>(ISpecification<TAggregate, TResult>)`, which materialises. Review F1 (high): never hand a derived class an `IQueryable` — an empty Ardalis spec returns the DbSet itself (cast → `Entry(x).Context.SaveChanges`), and any EF query allows `ExecuteDelete/ExecuteUpdate`, which write around the Unit of Work's sequence. Ardalis's projection `GetQuery<T,TResult>` has no criteria-only flag (full spec, then Select) and no Distinct. Registered with `module.AddScoped<IProductRepository, ProductRepository>()`; ModuleBuilder re-keys only `IUnitOfWork`, so both repositories share the scope's DbContext.
- Test technique (one container): a command/handler in the test assembly registered by `StubModule`'s `AddPouryaKitCqrs` scan is refused by Catalog's Gateway. In a test-owned scope, call `BeginOperation(ctx, typeof(CatalogModule))`, then send the probe through that scope's `IDispatcher` to run in Catalog's Unit of Work (`RepositoryTests`, `Stub/ProductRepositoriesProbe.cs`). This test technique does not permit cross-Module Feature calls to bypass the Gateway.
- Avoid sample Features premised on duplicate product names: #11 is expected to put a unique constraint on `products.name`. Avoid row locks (`FOR UPDATE`) as an example: a second concurrency mechanism beside versions.
- `dotnet ef` from the worktree root needs absolute `--project`/`--startup-project` paths (relative ones fail with "Unable to retrieve project metadata").

## Dapper and the read connection (#9, 2026-10-05; Dapper 2.1.89, Npgsql 10.0.3)

- `NpgsqlDataSource.OpenConnectionAsync(token)` with an already-cancelled token returns an idle pooled connection without throwing; the Kit's `ReadConnectionFactory` calls `ThrowIfCancellationRequested` first.
- Dapper 2.1.89 `SqlMapper.AddTypeHandlerCore` takes a lock (source at commit eb47546); re-registering a type replaces the handler. No Kit-side lock needed. Positional records with typed-ID constructor parameters map fine once handlers exist.
- Npgsql runs a command inside the connection's active transaction even when `command.Transaction` is null, so a test cannot detect a seam that drops the transaction; only a separate connection would escape it.
- Npgsql's net10.0 closure is Logging.Abstractions -> DI.Abstractions only. Reading a connection string by name needs `Microsoft.Extensions.Configuration.Abstractions`, outside plan C's table: #9 added it after asking main by SendMessage; the owner approved it (2026-10-05). Asking main mid-package via SendMessage worked; the reply arrived after the first report.
- #9 review: a transaction check alone is not a write guard: a query nested in a command, or a nested command's validator, runs inside the active transaction, and a failed query marks nothing rollback-only. `IUnitOfWorkConnection.Join()` also checks `Operation.MayChangeState` (no query or check running, and no Unit of Work step opened with `Operation.OnlyReading`).
- A transitive package that a Kit package's public API compiles against (DI.Abstractions via Npgsql) is a review finding; reference it directly.
- `ModuleBuilder` re-keys only `IUnitOfWork`; any other per-Module service registered with Add is last-wins Host-wide. Shared services (repository, `IUnitOfWorkConnection`) take the unkeyed `IUnitOfWork` (the router) with TryAdd.
- A SQL-only EF migration (attributes `[DbContext]` + `[Migration]` on an internal class, no Designer) applies fine and leaves the snapshot unchanged.
- Never assert which pooled server connection (`pg_backend_pid()`) the next lease gets: the shared Host's background work (Wolverine durability agent, other test classes) takes pooled connections too; #54 removed such an assertion after a CI flake (run 37614975892).

## Persistence preparation and conflicts (#11, 2026-10-05; EF Core 10.0.12, Npgsql 10.0.3)

- **EF Core rolls back to its own savepoint when `SaveChanges` fails inside a user transaction.** A mutation "commit after a concurrency conflict" left no EF-tracked row behind, so EF-written rows never prove the Unit of Work rolled back. Prove it with a raw-SQL write on `IUnitOfWorkConnection` in the same Operation (Stub `HoldChangeCommand` writes a marker category).
- **Two-scope race technique:** a Stub command begun as a Catalog Operation (`BeginOperation(ctx, typeof(CatalogModule))` + `IDispatcher`) runs the real Feature nested, signals a `TaskCompletionSource`, then awaits a release. Wait for both signals before releasing the first, await it, then release the second. Holding *after* both nested changes ensures both Operations track the pre-commit row, so the loser conflicts at save. A spec query begun only after the winner commits may instead miss the row through the soft-delete filter.
- **TestClock never reaches a Gateway Operation:** the dispatcher rebinds `DomainClock` with the Host's `TimeProvider`. Build a second Host with `ModularMonolithHost.CreateBuilder([...connection string])` then `builder.Services.AddSingleton<TimeProvider>(clock.Time)` (Cqrs TryAdds; last wins). It may remain unstarted only for Operations needing no running hosted service. Notification, Integration Event or Snapshot delivery paths need a started Host; stop or dispose it afterward (`PersistencePreparationTests`).
- **`dotnet ef migrations remove` corrupted the Stub snapshot** because the last migration by ID was a hand-dated SQL-only one (no Designer). Never use remove there: delete the files and `git checkout` the snapshot. Rename a generated migration's timestamp (files + `[Migration]` id) to sort after hand-dated ones.
- Model snapshot drift with a schema effect makes `Migrate()` throw in EF 9+, so such a convention change needs a migration in every DbContext, the test-only Stub's too (temporary `IDesignTimeDbContextFactory` + temporary Design package, both removed after). A concurrency token alone on an existing column is not drift (#152, EF 10.0.12): `dotnet ef migrations has-pending-model-changes` reported none and every fixture migrated with the old snapshots.
- `Enumerable.Except` is a set operation: it silently deduplicates the left side.
- `CascadeDeleteTiming.OnSaveChanges` is what keeps a soft-deleted aggregate's owned parts and children; with `Immediate`, `Remove` marks them Deleted before the prepare step and the save fails.
- #11 fix round (review F1): the walk reads a child's holder from both the current and the original FK value, so a moved child bumps both aggregates and a nulled optional key bumps the one it left; an untracked holder throws (an unloaded aggregate cannot conflict). The Stub `Folder` has pages (required key), stickers (optional key) and `MovePage`; EF reparents a child moved between two tracked collections as an FK update, not an orphan delete.
- `PouryaKitDbContext`'s constructor touches `ChangeTracker`, which builds the model: a model-convention refusal throws from `new MyContext()`, not from `.Model`.
- Converting a removed soft-deletable entry Deleted -> Unchanged keeps the Operation's earlier changes to it (checked: a rename before removal was saved).
- `AppFixture.RowsAsync` returns `DBNull.Value` for SQL null, not null.
- #11 second fix round (F5): with `CascadeDeleteTiming.OnSaveChanges`, EF cascades hard deletes inside `SaveChanges` (dependent Deleted, or optional key cleared -> Modified), after the prepare step. The prepare step now calls `ChangeTracker.CascadeChanges()` after the soft-delete conversion. `CascadeChanges` also deletes severed orphans, so `DeleteOrphansTiming` must stay `Immediate` (pinned in `PouryaKitDbContext`): orphans are then Deleted at the prepare step's first DetectChanges and a soft-deletable one is converted.
- Observing save-time mutation honestly: subscribe `DbContext.SavingChanges` (raised before the save's DetectChanges and cascades) and `ChangeTracker.StateChanged`, and record any transition to Added/Modified/Deleted after saving began (Stub `EditTrayCommand`). Accepting changes after the save goes only to Unchanged/Detached.
- An EF base type with `ToTable` and derived types configured without one defaulted to one table per derived type in EF 10 here; say `UseTphMappingStrategy()` to get one table. Keys to sibling derived types share the base's `IKey` (F6).
- A domain transition that raises an event (Product.Remove) needs its own once-guard: a removed aggregate is still found by later queries in the Operation until the prepare step marks it.

## Paging (#35, 2026-10-07; Dapper 2.1.89, Npgsql 10.0.3, EF Core 10.0.12)

- **Page validation runs in the Feature's validator**, as `RuleFor(q => q.Page).Cascade(CascadeMode.Stop).NotNull().AllowedBy(Query.Paging)` (`PageRuleExtensions.AllowedBy` in `PouryaKit.Validation`, #123, 2026-10-16, which adds each Error of `PageDeclaration.Validate` as a failure with its target and code), not in a Dispatcher edit: the advisor judged a Kit check beside `IValidationStep` a second validation path (G.8, ADR 0002) and a likely high review finding. The helpers re-run `Validate` and throw before any SQL, so a forgotten validator fails loudly.
- **Npgsql types a null parameter only from its DbType**: `@x is null or col = @x` with an untyped null fails ("could not determine data type"); pass `DynamicParameters.Add(name, null, DbType.X)`. A `DateTimeOffset` must be UTC (`ToUniversalTime()`), or Npgsql refuses it for timestamptz.
- EF Core + Npgsql translates `Name.Contains(param)` to `name LIKE @p` with the parameter pre-escaped (case-sensitive, wildcards neutral), matching SQL `strpos(name, @p) > 0`. `product.CategoryId == new CategoryId(id)` inside a predicate factory translates: the funcletizer makes the typed ID a parameter.
- Ardalis 9.3.1: `SpecificationEvaluator.Default.GetQuery(set, (ISpecification<T>)projectionSpec, evaluateCriteriaOnly: true)` gives criteria only for a projection spec; reject `OrderExpressions.Any()` and `spec is { Skip: > 0 } or { Take: > 0 }`.
- Ardalis 9.3.1 marks a Skip or Take that was never set with **-1**, not 0 or null (probed by running a spec): "set at all" is `spec is not { Skip: -1, Take: -1 }`. A `> 0` guard silently drops `Take(0)`.
- #35 review: normalise a typed value (DateTimeOffset to UTC) once, where the declaration parses it (`FilterField.Read`), not in one helper; otherwise EF Core passes a `+03:30` value Npgsql refuses. A test with a non-UTC offset through both helpers catches it.
- Mutating the Dapper helper to inline filter values as quoted literals makes the injection tests fail by PostgreSQL syntax/type errors, not by a visible leak; still red, but say so.

## A repository write outside a Unit of Work (#67, 2026-10-08; EF Core 10.0.12)

- **`EfRepository.AddAsync` and `Remove` refuse where `Operation.IsUnitOfWorkActive` is false**, after the `MayChangeState` check (ADR 0003's #66/#67 amendment). A test that seeds through a repository in a scope it opened now throws: seed through the Gateway, a command sent through `IDispatcher` in the scope, or raw SQL (`insert into stub.notes (text, version) values ('x', 0) returning id`). Reads need no Unit of Work, so `FindAsync` in a bare scope gives a tracked aggregate to hand to `Remove`; an untracked `Note` with a null database-generated id is no good for that.
- **Which scopes resolve a repository:** in a Host of Modules a scope never begun throws at `GetRequiredService<IRepository<,>>()` with the router's "The Unit of Work was needed in a scope whose Operation names no Module" (untested before #67); in an application without Modules a scope never begun resolves it and reads through it, and a command sent there still commits a note (`SingleModuleTests`).
- **Red-once of a refusal's order:** the two older "code that only reads" tests (a query nested in a command, a Snapshot mapper) both run with a Unit of Work active, so swapping the two checks leaves them green. Only a query sent on its own that writes (`WriteNoteInQueryQuery` through the Stub's Gateway) pins the order. Put the "nothing was stored" assertion before the exception assertion: the red run with the check off then shows the rows held and the call returned, in one run. A second mutation (guard left out of one of two members) shows the other member's red, since the first failed assertion hides it.

## A change to a loaded aggregate outside a command (#68, 2026-10-09; EF Core 10.0.12)

- **Run against PostgreSQL in an application without Modules** (`SingleModuleTests`): an aggregate found through the repository and changed in a begun scope is dropped when the scope sends no command, also when a query follows (the tracked-state comparison's baseline is the query's start, so the change is already in it); a command the scope sends after it, if it succeeds, saves it, because the commit saves the whole DbContext. "No commit would save it" is therefore exact only for a scope that sends no command or whose command has returned; a scope runs one outermost command, so nothing follows a returned one.
- **Showing a silent comparison is not a missing guard:** in the same composition, have the query itself make the change (`ReadFolderQuery(id, null, ReadingChange.OwnedValue, false)`): it throws `A query changed a Label the Operation saves. …`. A throwaway probe is enough; record its message.
- **Stub shapes for it:** `Note` has no mutator. `Folder.Relabel(colour)` changes a value and raises nothing (`Rename` raises `FolderRenamedDomainEvent`, whose handler adds a page in a later command's drain). A folder is auditable, so create it with `CreateFolderCommand` in a begun scope of its own, then read `label_colour` from `stub.folders`.

The generated `columns: new[] { ... }` fails IDE0300 under TreatWarningsAsErrors: write `["tenant", "name"]`. `AddColumn(..., defaultValue: "")` leaves the column's DEFAULT in place, so the tests' raw `insert into catalog.categories` without the new column still works.

## The save's tenant ownership check (#117, 2026-10-17; EF Core 10.0.12)

- **Gate the check on the entity (`ITenantScoped`), not on `HostComposition.IsTenantScoped`**: the tenant filter is ungated too, and a bare `ServiceCollection` (`TenancyTests.CatalogAsTheApplication`, `SingleModuleTests`) has no `HostComposition`. Capture each tenant-scoped entry's loaded and current tenant at the top of `PersistencePreparation.Run`, judge after `CascadeChanges` and the attribution, before the version bump; `Run` returns `Result<IReadOnlyList<EntityEntry>>` (`Result.Success<IReadOnlyList<...>>(list)`, since a value of an interface type never converts implicitly).
- **Fixtures:** the Stub's `Binder` (tenant-scoped, hard-deleted, sheets on a required key) and `Docket` (key `(Tenant, Id)`), migration `TenantBinders`; a product's reassignment runs as a Stub command in a scope begun for `CatalogModule`, setting `dbContext.Entry(product).Property(p => p.Tenant).CurrentValue`. A mutation judging only directly changed entries leaves the child and both move cases red, so the attribution is what proves them.
- **Read the Operation's tenant only when a tenant-scoped entity changed** (#117 review F3), as the stamp reads its Actor: an unchanged tracked one must not need a context. A scope nobody began runs commands only in a bare `ServiceCollection` (`SingleModuleTests`), where the regression lives.
- **A migration that adds a tenant to a copy refuses a populated table** (#117 review F2): a copy that kept no tenant cannot learn it, and the applied Snapshot versions stop a replay. A `do $$ ... raise exception ... $$` block in `migrationBuilder.Sql` aborts the migration's transaction; a test undoes it with `dbContext.GetService<IMigrator>().MigrateAsync("<previous migration>")`, writes a row, expects `PostgresException.MessageText`, then empties the table and migrates forward in `finally`.
- An entity attached with a forged tenant is judged by that tenant; #152 closed it with `Tenant.NotLoaded` (prepare step: a changed tenant-scoped entity, part or attributed aggregate no query loaded) plus `Tenant` as a concurrency token behind it (no migration needed, see above).

## Attached-entity ownership (#152, 2026-10-17; EF Core 10.0.12)

- **A forged-attach test must give the stored version**, or the `Version` token alone stops the write and the red run with the tenant token off stays green: the Stub's `ForgeCategoryCommand` sets the entry's `Version` current and original values to 1. Use Catalog's `Category` (no Domain Event on create, hard-deleted) so a removal is a real `DELETE`. Put the row assertion before the Error assertion: the red run then shows the row counted, re-tenanted and deleted.
- **A token on the root does not guard its parts** (#152 review F1, high): a child has no tenant column, and an attached child's current and original FK name the same (the caller's own) holder, so its UPDATE or DELETE hits another tenant's row by key alone. The fix: `PouryaKitDbContext` records `ChangeTracker.Tracked` entries with `FromQuery` in a reference-equality set, and the prepare step refuses any non-added changed entry of a tenant-held aggregate that is not in it. DbSet.Find, AutoInclude children and owned types all arrive with `FromQuery` true: the full suite stayed green.
- **The loaded record must be revoked on re-tracking** (#152 review F3, high): every Detached-to-tracked transition that is not a query raises `ChangeTracker.Tracked` with `FromQuery` false, whether through a new entry after `Detach`/`ChangeTracker.Clear()` or through the retained `EntityEntry`, so `else _loaded.Remove(entity)` closes it; `Clear()` needs no event of its own. Keying by `entry.GetInfrastructure()` (`InternalEntityEntry`) fails the build with EF1001, and even suppressed leaves the retained-entry re-attach loaded (same internal entry). A re-attach through the retained entry keeps the queried original FK, so the holder walk throws for the other tenant's unloaded holder unless the forger also sets `OriginalValue`.
- **A loaded part's holder as loaded is forgeable too** (#152 review F4, high): set the FK's `OriginalValue`, or move it and call `ChangeTracker.AcceptAllChanges()`, and the holder walk lands on the caller's own root while the part stays query-loaded, so both refusals pass and the UPDATE/DELETE is key-only. Fixed by making each FK of a navigation-held part (`PrincipalToDependent` not null, walked up to an `ITenantScoped` holder, PK columns excluded) a concurrency token in the model convention; a legitimate move changes only the current value and still saves. No migration: the Stub migrated with its old snapshot. Red-once is a one-word `sed` flip of `IsConcurrencyToken(true)` to `false`.
- Forging a part under a loaded holder: `var entry = dbContext.Entry(sheet); entry.Property("BinderId").CurrentValue = binder.Id; entry.State = EntityState.Unchanged;` then change it. Construct it with a text the change differs from, or nothing is Modified and the test fails for the wrong reason.
- `PouryaKitModelConvention.cs`, `PouryaKitDbContext.cs` and `UnitOfWorkErrors.cs` are cited by no diagram (a brief said otherwise): grep the `*.json` diagram sources before planning a pin.

## A filter over another entity's set, built in a convention (#153, 2026-10-17; EF Core 10.0.12)

- **`Set<T>()` over the DbContext constant fails in a Kit convention's filter**: EF Core's `QueryFilterRewritingConvention` (model finalizing) turns `ctx.Set<T>()` and DbSet properties in filters into `EntityQueryRootExpression`, but a convention added through `ConfigureConventions` runs after it, so the call stays, the funcletizer makes it an `@ef_filter__p` context accessor, and translation fails ("could not be translated"). Build `new EntityQueryRootExpression((IEntityType)conventionEntityType)` yourself, exactly what EF's convention writes. Decompile with `ilspycmd -t <type> ~/.nuget/packages/microsoft.entityframeworkcore/10.0.12/lib/net10.0/Microsoft.EntityFrameworkCore.dll`.
- The holder's root picks up the holder's own filters at query time (tenant, soft delete), so a part filter chains, and `IgnoreQueryFilters([name])` on the outer query sets aside the nested one too. A part of a soft-deleted holder is hidden from its own set.
- **Two parts whose filters read each other's set overflow the stack** at the first query (uncatchable); a self-reference does not (EF reads its own set unfiltered inside its filter). #153's fix refuses holder cycles at finalization with a path walk (not the `seen` set, which would also refuse diamonds). The same unfiltered self-read makes a self-key useless as a judge (review F6, a cross-tenant read through a null optional aggregate key): the filter drops keys to the part's own root and refuses a self-held part with no required key to another holder.
- Test-type names in `ModularMonolith.Tests` share one namespace with the Stub's (`Note`, `Sheet`, ...): a clash breaks `RepositoryTests` at build, not the class you edit; grep the name first.
- **`ToQueryString` of a tenant filter with no Operation folds every `EXISTS` to `WHERE FALSE`** (null parameter vs a non-null column). Give the context an Operation: `new ServiceCollection().AddPouryaKitCqrs().BuildServiceProvider().CreateScope().ServiceProvider`, `BeginOperation(new OperationContext(actor, "north"))`, and `UseApplicationServiceProvider(scope)` on the options (`ModelConventionTests.LedgerContext`).
- The ModelConventionTests contexts apply every `IEntityTypeConfiguration` of the test assembly (the Stub's too), so map a test model in `OnModelCreating`, never in a configuration class, or it lands in `StubDbContext`.

## A migration test on a database of its own (#150, 2026-10-17)

- **Test a sample migration's refusal without touching the shared fixture's tables**: `create database x` through `Fixture.RowsAsync`, `AppFixture.ComposeHost("Development", <string for x>, new RecordedLogs())` built but not started (nothing migrates before start), resolve the Module's DbContext in a scope, `GetService<IMigrator>()`, `MigrateAsync("<previous migration id>")`, write a row with `Sql.RowsAsync(<string>, ...)`, then `MigrateAsync()` throws `PostgresException` whose `MessageText` is the `raise exception` text. Catalog's tables are written by parallel classes, so down and up on `Fixture.Host` (as Inventory's #117 test does on near-empty tables) would race them. `information_schema.columns` with `column_name = 'tenant'` also lists `pouryakit_idempotency_keys`: name the tables.

## A dropped column default and the tests that leaned on it (PR #143 review, 2026-10-24)

- **Dropping a migration's `defaultValue` can break a test's plain SQL insert** that left the column out: the Stub's `HoldChangeCommandHandler` inserted into `catalog.categories` without `tenant`, so `ConflictTests`' two races hit `ReportNotNullViolationError` and timed out at 60 s (the race waits on a hold the failed insert never released). Grep every `insert into <schema>.<table>` in `tests/` before dropping a default, and run the class that uses it, not only the targeted ones.

## A delivered tenant on a mapped entity of a Module that is not tenant-scoped (#169, 2026-10-24; EF Core 10.0.13, dotnet-ef 10.0.12)

- **Inventory's migration from its own Host:** `ConnectionStrings__app=… ConnectionStrings__broker=amqp://… dotnet ef migrations add <Name> --project <abs Inventory.csproj> --startup-project <abs Inventory.Host.csproj> --context InventoryDbContext --output-dir Infrastructure/Data/Migrations` (RabbitMQ reads its string at registration; the bearer section is not needed, nothing starts). It writes a Designer and the snapshot (ProductVersion moves to the runtime's 10.0.13; the 10.0.12 tool only warns), timestamped after the hand-dated SQL-only migrations.
- **The lease's tenant serves a Module that is not tenant-scoped too:** `ReadConnectionFactory` sets `pouryakit.tenant` for every lease, `''` with no tenant, so `tenant = current_setting('pouryakit.tenant')` over a nullable column answers no tenantless Operation and no row stored without a tenant. `DapperTenantTests` judges only `ITenantScoped` tables, so such a read is held by its runtime test alone.

**Why:** each cost a run, a design detour or a wrong claim in a provenance record, or would have let a test pass vacuously; #9 to #18 build on these seams.

## Number sequences: cancellation (#146, 2026-10-16; Npgsql 10.0.3)

- **Cheapest cancellation shape:** `HoldChangeCommand` with an unreleased `Hold`, run with a linked `CancellationTokenSource`'s token; wait for `Changed`, cancel, and the handler's `Released.Task.WaitAsync(ct)` throws, so the Unit of Work rolls back. Assert `ThrowsAnyAsync<OperationCanceledException>`.
- **Red runs of held tests poison the class:** under the own-connection mutation the "second waits" test times out and never releases its held Operation, whose open transaction then blocks later tests (a 30 s Npgsql read timeout, not the intended assertion). Show a held test red alone with `--filter-method <fully qualified method>`.
- Own-connection mutation that compiles: `((NpgsqlConnection)connection).CloneWith(connectionString)`, `OpenAsync`, then `new NpgsqlBatch(own)`.

## The Dapper lease binds the tenant (#155, 2026-10-17; Npgsql 10.0.3)

- **A singleton cannot see the scope's Operation**, so `IReadConnectionFactory` became scoped over a keyed singleton `NpgsqlDataSource` (key `typeof(ReadConnectionFactory)`, so the Host still disposes the pool and no unkeyed `NpgsqlDataSource` clashes with another package's). Development's `ValidateScopes` then refuses every root resolution: `DapperTests`, `PagingTests` and `ReadProbe` (now `AddScoped`, no disposal forwarding) moved to a scope. Never make the scoped factory disposable: the pool would die at the first scope's end.
- **`current_setting('pouryakit.tenant')` on a physical connection that never set it throws 42704**; after Npgsql's `DISCARD ALL` it reads `''`. So a red run with `set_config` removed fails by exception or by empty rows, depending on pool reuse; the lease must set it on every open, tenant or not.
- **Session state needs session affinity** (#155 review F1, high): with `Multiplexing=true` Npgsql binds a command to a physical connector only while it runs, so a `set_config` and the next read can land on different sessions. The Kit refuses it in `ReadConnection.Refusal`, shared by `ReadConnectionCheck` (build) and the data source factory (first lease). `NpgsqlConnectionStringBuilder(cs).Multiplexing` parses it.
- **Prove a lazy read directly, not through the Gateway** (#155 review F2): the Gateway begins the Operation before it resolves the handler, so a value captured at construction passes. Resolve in a scope, then `BeginOperation`, then open; and open in a scope that never began.
- Red runs used: the rule over Catalog's unchanged `@Tenant` literals (three violations), `set_config` removed (Stub `ReadBindersQuery` test, 42704), Catalog's `p.tenant` conjunct removed (two `TenancyTests` red).

**Why:** the lease shape and the error mode decide whether a missing binding fails closed. **How to apply:** any later read seam (gRPC, a projection reader) that must see the Operation is scoped the same way. Related: [[core-json-and-architecture-test-facts]].
