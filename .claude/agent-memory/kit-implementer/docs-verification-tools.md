## Docs settle-up package (#90, 2026-10-10)

- **`check-docs.py`'s ordered-sections rule outranks a brief's placement:** the `## Pre-Wave 3 …, ticket #N` headings of `docs/acceptance.md` must run in ascending ticket order (`ORDERED_SECTIONS`), so a late-numbered package that lands after higher tickets goes between its neighbours, not at the end. A link to the new section from older rows fails until the section exists, a free slug check.
- **A ticket whose acceptance is a literal grep** ("the key phrase finds only X and Y") also catches run records (`acceptance.md`) and the plan's other sections: reword each to a pointer at the owner, and describe the phrase in prose in your own section. A path cited inside a backticked command span (`unittest discover -s tests/releases/...`) is not a Kit path to `check-docs.py`, so a moved folder leaves no failure there: grep for it.
- **Before cutting status text, prove each claim lives elsewhere:** a scratchpad script with one term list per claim over `references/*.md` found every README status claim in a reference; the three misses were wording ("always validated", "unit `s` ... keeps fractions", a tag table), checked by hand.
- **A brief's docs correction can be wrong:** #94's reviewer read `NoHandlerContinuation` alone and missed the `IMissingHandler` the Kit's `UnknownMessageBehavior` registers; the brief for #90 carried that reading. Check a "False in Wolverine X" correction against the decompile and the ADRs before writing it, and report a contradiction instead of applying it.

## Archify diagrams (#108, 2026-10-11; Archify 3.0.1)

- **The browser gate needs Chrome:** without it `finalize` exits with `browser-check: skipped` (`viewer/chrome-unavailable`), which is not a pass. Playwright's Chromium works: `ARCHIFY_CHROME="$HOME/Library/Caches/ms-playwright/chromium-1243/chrome-mac-arm64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing"`.
- **Only nodes carry `sources`** in a workflow (max 3, label max 48 chars); edges and cards have none. Only repository files at the pinned revision are citable, so a fact proven by a decompile needs an in-repo line that states it (a test comment served for Wolverine's start order).
- **A node `tag` renders only at the zoomed "fine" detail level** (`data-detail="fine"`); put what the reader must see in `sublabel` or a card. Override the default legend labels ("Agent logic", "Tool action") with `meta.legend.entries.<type>.label`.
- **Readability floor:** at the 930px desktop budget a workflow's viewBox must be at most 1240px wide, or its 8px context text projects under 6px (`composition/desktop-readability`); six columns of 170px nodes fit, 184px did not.
- **Stacked nodes** (two `yOffset` values in one column) need each port used once: an incoming edge on the top node's bottom port made the pinned bottom-to-top drop infeasible (`workflow/explicit-pin-conflict`). Give a lone neighbour the same `yOffset` so its edge is a straight facing one.
- **Iterate with the output in the scratchpad**, then run the final `finalize` into the repository path. It writes four receipts beside the HTML (`finalize`, `finalize-summary`, `browser-check`, `delivery`); the summary holds absolute local paths. `visual-check --out-dir <dir> --summary --require-provenance` writes 1440 and 2048 screenshots to read.

**Why:** a docs brief requires every snippet to compile and the diagram to stay valid, and none of the repo's checks cover either.
**How to apply:** at workflow steps 6 and 7 for any ticket, and for any record amendment. Related: [[persistence-and-dapper-facts]], [[worktree-shell-and-check-gotchas]].
