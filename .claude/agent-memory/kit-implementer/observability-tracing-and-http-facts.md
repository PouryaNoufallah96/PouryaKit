## W3C propagation (Spike #46, 2026-10-07; WolverineFx 6.46.0)

The record is `docs/adr/0009-*.md`; check it is current.

- Wolverine writes `Activity.Current.Id` as envelope `parent-id` at `PublishAsync` (the Unit of Work's `WriteAsync`, during commit), not at flush; stored in the body; no tracestate anywhere.
- Its execution span exists only if a listener samples the `Wolverine` ActivitySource; otherwise nothing is current in `SubscriptionDelivery` and a new activity starts a new trace (no ExecutionContext leak through the local queue).
- Wolverine starts spans with a *string* parent: a test listener must set `SampleUsingParentId` too, or the Wolverine span vanishes for the wrong reason.
- A `ScheduleRetry` attempt gets no `ActivityLink` to the failed one: the previous-attempt header is in memory only; the store's reschedule UPDATE does not rewrite the body.
- Spike mechanics that worked: csproj directly in `spikes/<name>/` (so `dotnet build spikes/<name>` finds one entry), stopper props, `ProjectReference` to the sample Host and `PouryaKit.Testing`; per-test `create database` on one container; the sample's commands are `internal`, so build them by name with `Activator.CreateInstance` instead of touching the sample. A scoped `IDispatcher` decorator wraps both Gateway and delivery Operations (stand-in Operation activity).

## Observability (#47, 2026-10-07; WolverineFx 6.46.0, .NET 10.0.12)

- **A listener never gets a static `ActivitySource` that its own `ShouldListenTo` creates first.** `source == SomeClass.Upstream` in `ShouldListenTo` runs the class's static initializer while `AddActivityListener` is still iterating, and the new source never asks this listener. So `StartActivity` returned null, but only in the first test of a run. Match sources by name.
- **The decorator must be registered after the dispatcher.** `AddPouryaKitCqrs` uses `TryAddScoped<IDispatcher, Dispatcher>`. `AddPouryaKitObservability` replaces the last `IDispatcher` descriptor with a factory that wraps `ActivatorUtilities.CreateFactory(implementationType, [])`, and throws when there is none. Idempotence: the factory is a method on a private class, so check `descriptor.ImplementationFactory?.Target is ObservedDispatcherFactory`. AppFixture's second `AddPouryaKitModules` (StubModule) keeps the wrapper, because `TryAdd` sees it.
- **Why `Operation.TraceParent` and not a scoped holder:** Observability cannot reference Messaging.Wolverine. A holder in Messaging would make the Kit's transport-neutral contracts package register DI, and the brief left Messaging out. `ContinuedOperationContext` returns `(Context, TraceParent)`, so a new delivery path that still expects an `OperationContext` fails to compile. That is the point: #45 has to pass the parent too.
- **`Operation.Context` went public.** Resolving `OperationContext` from a scope that has not begun throws, so the decorator reads `operation.Context?.Actor.Kind`.
- **Two test seams:** `DeliveryProbes.ActivitiesOf(subscription)` records `Activity.Current` in `HeldReceipts.RecordAsync`, which runs inside the Deliver Operation activity. `FailOnceAfterReceipt` uses `Interlocked.CompareExchange` for a race-free single failure. Disposing `FailAfterReceipt` after the first attempt races the throw check.
- **Mutations** (`scratchpad/mutate47.py`): disposing the activity right after its start, which ends it before the Outbox write, makes all 4 tests red. Dropping the header makes 3 red. Removing the fallback makes the Kit-only trace test and the retry test red; with `Wolverine` sampled the test stays green by design. Recording `.Seconds` makes the outcome test red.

## Outgoing HTTP (#48, 2026-10-07; Microsoft.Extensions.Http.Resilience 10.10.0, WireMock.Net 2.18.0)

- **HttpClientFactory builds `DelegatingHandler`s in its own handler scope**, never the calling Operation's, so a handler cannot inject the scoped `OperationContext`; reading `IHttpContextAccessor` is the ambient read ADR 0007 rejects. The Kit's handler reads the context from `request.Options` (`WithOperationContext(context)`); a typed client (transient, resolved in the caller's scope) can inject `OperationContext` itself.
- `AddStandardResilienceHandler()` returns `IHttpStandardResiliencePipelineBuilder`, which does not chain back to `IHttpClientBuilder`; its `.Configure(Action)` needs `using Microsoft.Extensions.Http.Resilience;`. Its options are named by `pipeline.PipelineName`, so `services.PostConfigure<HttpStandardResilienceOptions>(pipeline.PipelineName, o => o.Retry.DisableForUnsafeHttpMethods())` runs after every application `Configure`.
- The default standard retry retries POST. The Kit's rule is an allow-list wrapping `Retry.ShouldHandle`: only GET, HEAD, OPTIONS and TRACE are retried unless the client opts into `HttpReplay.AllRequests` (review of #48 rejected `DisableForUnsafeHttpMethods()`, an exclude-list that still retries PROPPATCH). The allow-list also stops a retry after a reset connection (an exception outcome, no response), proved with a raw `TcpListener` that resets each socket (`LingerState = new(true, 0)`).
- WireMock.Net 2.18 `WithFault(FaultType.EMPTY_RESPONSE / MALFORMED_RESPONSE_CHUNK)` answered 200 in a probe: it cannot stand in for a broken connection. Scenarios: a mapping with no `WhenStateIs` matches only the start state; `ResetScenario(name)` and `ResetLogEntries()` exist on `IWireMockServer`. The full `WireMock.Net` package brings Roslyn 4.8 (ProtoBuf part) and GraphQL; it restored and ran beside `WolverineFx.RuntimeCompilation` with no conflict.
- **`DisableForUnsafeHttpMethods()` is an exclude-list** (POST, PUT, PATCH, DELETE, CONNECT): an extension write such as PROPPATCH is still retried. The Kit wraps `Retry.ShouldHandle` with an allow-list of GET/HEAD/OPTIONS/TRACE read from `arguments.Context.GetRequestMessage()` (namespace `Polly`, from the resilience package); an undefined enum value must throw, not fall into "everything else". (#48 fix round, F3/F4.)
- **`TryAddWithoutValidation` takes CR/LF** from a claims-derived value; check every context header value before writing any (the Kit's rule: 1-256 visible ASCII, no edge space) and apply the same rule when reading a trusted peer's headers (TestServer passes raw header strings through, so `TryAddWithoutValidation` in the test reaches the server unchanged).
- The `WireMock.Net` test closure holds `XPath2` 1.1.5 (MS-PL) and several packages with only a licence URL; `LicenceTests` reads `RestoredPackage.All`, the `src/` packages only, so it never sees test closures. Recorded in `docs/provenance/ModularMonolith.md`.
- **`RemoveAllResilienceHandlers()` (EXTEXP0001) only drops `ResilienceHandler`s from the handler list** through `ConfigureAdditionalHttpMessageHandlers`; it leaves every `Configure`/`PostConfigure` of the `{client}-standard` options name and the Polly registry entry. A second `AddStandardResilienceHandler()` on a client stacks a second handler over the same options name (no throw). So a Kit choice expressed as options state is read from a found-or-added `ImplementationInstance` (`HttpReplayPolicies`, keyed by `pipeline.PipelineName`) by one `PostConfigure` per name at options-build time: last call wins. Tests need `#pragma warning disable EXTEXP0001`. (#48 re-review F9.)

## Cross-process tracing and ServiceDefaults recipes (#52, 2026-10-07; WolverineFx 6.46.0, Microsoft.Extensions.Http(.Resilience) 10.0.12/10.10.0, OpenTelemetry 1.19, Serilog.AspNetCore 10.0.0)

- **Fan-out copies lose the parent inside the receiving Host, not on the broker.** `parent-id` and every `pouryakit-` header cross RabbitMQ. `DestinationEndpoint.SendAsync` applies `DeliveryOptions.Override` and then `TrackEnvelopeCorrelation(envelope, Activity.Current)`, which overwrites `ParentId` (no DeliveryOptions field can set it). Fix: `pouryakit-traceparent` written in `CopiesOf`, read as fallback in `ContinuedOperationContext`. With `Wolverine` sampled there are two Wolverine spans (broker envelope, then copy) between the publishing Operation and the delivery.
- **`ConfigureHttpClientDefaults` builder has `Name == null`**: `AddStandardResilienceHandler` there names its options and pipeline `-standard`, one pipeline (and circuit breaker) for every client keeping it. Its `IConfigureOptions<HttpClientFactoryOptions>` are inserted before any named client's (`DefaultHttpClientBuilderServiceCollection` + tracker), so a named client's `RemoveAllResilienceHandlers()` always removes the default handler, whatever the registration order.
- **503 with `Retry-After: 0`** makes the standard pipeline retry immediately: the default limit (3 retries, 4 requests) is testable in milliseconds.
- **`""` collides with the defaults (fix round F1):** `AddHttpClient(string.Empty)` is allowed and its pipeline is `-standard` too, the same options name, registry key and Kit replay slot, so they cannot be keyed apart; `AddPouryaKitResilience` refuses `builder.Name is ""` (not `IsNullOrEmpty`: null is the defaults). Without the refusal a named default-keeping client's POST went 4 times.
- **Cancel-on-timer is flaky on a cold client:** the first request can take >300 ms to reach WireMock (a 1.3 s timer still saw one request while uncancelled retries came 1.02 s apart). Poll `LogEntries.Any()`, then cancel; `Retry-After: 1` gives a 1 s retry window.
- **Telemetry after a delivery:** rows commit before the Operation logs, records its duration and ends its activity; `WaitUntilSettledAsync` (Handled after the handler returns) closes it. Proof: `HoldAfterCommit` + a 2 s delayed `Release()` makes the rows-only wait red.
- **A Host's OpenTelemetry TracerProvider/MeterProvider is a process-wide listener.** In a test process every started recipe Host samples its sources for all Hosts. Never add `Wolverine` to the recipe, or the "Wolverine not listened" proof becomes impossible in-process. Filter exported data by trace id or `pouryakit.module`. Test exporter: `ConfigureOpenTelemetryTracerProvider(t => t.AddProcessor(new SimpleActivityExportProcessor(exp)))`, `ConfigureOpenTelemetryMeterProvider(m => m.AddReader(new BaseExportingMetricReader(exp)))`, then `MeterProvider.ForceFlush()`.
- **Readiness proof per test database:** `alter database X with allow_connections false` + `pg_terminate_backend` from the `postgres` database, then `true` again. Npgsql EF's `CanConnectAsync` runs `SELECT 1`, so a dead pooled connector cannot fake health. A Module's DbContext is internal: enumerate `GetServices<DbContextOptions>()` and resolve `ContextType`. WolverineFx 6.46 has an internal `WolverineTransportHealthCheckAdapter` but registers no health check.
- **Serilog `AddSerilog` replaces the logger factory**: every `builder.Logging` provider (RecordedLogs, the OTel logging provider) receives nothing. `ReadFrom.Services(services)` picks up `ILogEventSink` registrations, which is how a test observes. Keep the opt-in out of a composition the broker fixture shares.
- **Web Host without Sdk.Web:** `Microsoft.NET.Sdk` + `FrameworkReference Microsoft.AspNetCore.App` avoids Sdk.Web copying `appsettings.json` into a referencing test bin. A test-composed WebApplication needs `UseTestServer()` (two Inventory Hosts would fight over Kestrel's 5000); a child process gets `ASPNETCORE_URLS=http://127.0.0.1:0`.
- **Smoke containers:** `rabbitmq` refuses `guest` through a host port mapping; set `RABBITMQ_DEFAULT_USER/PASS`. `docker stop` of the PostgreSQL container gave `/alive` 200 and `/health` 503 at once.

## Health endpoints outside Development (#64, 2026-10-08; ASP.NET Core 10.0.12)

- **What is mapped where.** `MapDefaultEndpoints()` maps `/alive` in every environment (`AllowAnonymous()`, `DisableRateLimiting()`, the default writer) and `/health` in Development only. In Production `/health` answers 401 in a Host with the Web defaults (the fallback policy covers an unmatched path) and 404 in one without (probed on a bare `WebApplication` with the recipe).
- **Every older `/alive` test ran in Development**, so each passed with or without the change: a guarantee about every environment needs a Host started in Production. A bare Host does not exercise `AllowAnonymous()`, having no fallback policy; compose authentication and `AddPouryaKitWeb` as the templates do, or a removed `AllowAnonymous()` stays green.
- **Aspire's page** (`aka.ms/aspire/healthchecks`, now `aspire.dev/fundamentals/health-checks/`, "Non-development environments"): both endpoints off outside Development; where enabled, host filtering, authorization or both, and a request timeout with an output cache (its sample puts a 5 s timeout and a 10 s cache policy on a group of both). What the recipe takes and leaves is in `host-recipes.md`, "Liveness and readiness".

## Npgsql's source in the recipe (#80, 2026-10-09; Npgsql 10.0.3, OpenTelemetry 1.19)

- **`AddSource("Npgsql")` is all `AddNpgsql()` of `Npgsql.OpenTelemetry` does** (`npgsql/npgsql@d376839 src/Npgsql.OpenTelemetry/TracerProviderBuilderExtensions.cs`); Npgsql's tracing page names no source. To read a package's source name and build commit: a scratchpad `dotnet run file.cs` with `#:package Npgsql@10.0.3` that reflects over `NpgsqlActivitySource`'s static fields; the source's version string ends in `+<commit>`, citable as `repo@commit`.
- **What it adds under an Operation's span:** one span per command (`db.query.text`), EF's `SAVEPOINT`/`RELEASE SAVEPOINT`, the Outbox's inserts into `wolverine_incoming_envelopes`/`wolverine_outgoing_envelopes` and the delete after the send, a `CONNECT` span per physical open. **No COMMIT span**: the transaction's commit is no command. Do not document "the commit" as traced.
- Sampling `Npgsql` process-wide broke no trace-shape test (566 green): `DeliveryProbes` still records the Operation activity, since Npgsql's span never stays current after an awaited command.
- A dump of `exported.Activities` by trace id with `TestContext.Current.TestOutputHelper?.WriteLine` under `--output Detailed` shows what a recipe exports before asserting on it.

**Why:** #47 implements only tracestate and the parent fallback from the #46 Spike; each other fact decided a #47, #48 or #52 design point or cost a run.
**How to apply:** any test that listens to activities or runs a recipe Host alive; any new delivery path, which must pass the parsed parent; any outgoing HTTP, trusted-peer or default-client composition, and the ServiceDefaults a template carries.
