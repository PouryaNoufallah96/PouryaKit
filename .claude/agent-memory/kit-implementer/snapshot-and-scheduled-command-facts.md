## Snapshots (#18, 2026-10-05; WolverineFx 6.46.0, EF Core 10.0.12)

- **Step 4 lives in the Outbox write.** `PersistencePreparation.Run` returns its `changed` list; `IUnitOfWorkOutbox.WriteAsync` got a `changedAggregates` parameter; `SnapshotStep` (Wolverine.EFCore) maps them through the public seam `ISnapshotMappers` (Messaging.Wolverine). Any new decorator of `IUnitOfWorkOutbox` (tests' `CommitProbe`, `DeliveryProbes`) must pass the list through.
- **Version gate:** `IReceipts.RecordVersionAsync` = one `insert ... on conflict (subscription, aggregate_id) do update ... where applied.version < excluded.version` on `pouryakit_snapshot_versions` (created by `CreateSnapshotVersionTable(schema)` in a hand-written migration). PostgreSQL waits on the conflicting row and re-checks the WHERE against what committed, so it holds under concurrency.
- **The Receipt masks the gate in redelivery tests.** Redelivering a handled envelope stops at its Receipt before the gate. Wipe the receiver's copy, version row and that subscription's Receipts first (`ForgetCopiesAsync` in `SnapshotTests`), then redeliver in the order wanted. `HoldAfterReceipt` holds before the gate; use `DeliveryProbes.HoldAfterVersion` for the race.
- **Mutations that proved the tests:** no `where` -> reverse order, after-Tombstone and newer-first concurrency fail; select-then-upsert -> only newer-first concurrency fails; no `DistinctBy` in prepare -> 11 fail; snapshot before prepare -> 13 fail; no mapper guard -> the mapper test fails; a random identity per delivery -> only the duplicate test's Receipt count fails (the gate alone hides it). Mutation runner: scratchpad `mutate.py` pattern (copy, replace, run `--filter-class`, restore in `finally`).
- Wolverine's envelope `body` column is its binary envelope format, not message JSON: identify a Snapshot's envelope by diffing envelope ids per step, and assert content through a recording handler or the receiver's table.
- A key the database generates is temporary at step 4; `SnapshotStep` throws for it. The Stub `Note` (long, `ValueGeneratedOnAdd`) therefore has no Snapshot.
- Merging #16's fix round and #17 (2026-10-05): a new subscription on Product reorders Inventory's commits (its Snapshot delivery commits before the Integration Event's), so a test hold keyed on the Module alone catches the wrong delivery; `DeliveryProbes.HoldAfterCommit` now takes the subscription. Unfiltered Receipt queries across a Module's subscriptions break the same way. A failed hold test once knocked on into `InboxStaleTimeTests`; it passed in four clean runs after.
- The Outbox resolves `IReceipts` from the scope at use time (a constructor dependency made an undetected cycle and hung the run); `ISnapshotMappers` in the Outbox's constructor is safe because its mappers are resolved at map time.
- #18 fix round (2026-10-06): the mapper guard must copy each value with `property.GetValueComparer().Snapshot(...)` (a `PropertyValues.Clone()` shares a `List<string>`) and walk `GetFlattenedProperties()` (complex properties are not in `GetProperties()`); `entry.CurrentValues[property]` reads a complex type's nested property fine in EF 10. Declarations are matched by the Operation's Module. A test that reads the singleton `IntegrationEventLog` must filter to its own aggregates: a mutation that lets another test's Operation commit leaks entries into it.
- Generating a Stub migration: a temporary `IDesignTimeDbContextFactory<StubDbContext>` that builds `AppFixture.ComposeHost("Development", "Host=localhost;...", new RecordedLogs())` and resolves the DbContext from a scope, plus a temporary `Microsoft.EntityFrameworkCore.Design` reference in the test csproj; `dotnet ef migrations add X --project <abs csproj> --startup-project <abs csproj> --context StubDbContext --output-dir Stub/Migrations`; then delete both.
- #18 last round (2026-10-06): the Unit of Work rechecks rollback-only after the Outbox write (mappers can send nested commands); refusing a mapper's nested command at the source needs a public read-only scope on `Operation` in Cqrs (its counters are internal). A test that starts a second Host must stop it in a `finally`: when its assertion fails, an unstopped Host keeps deliveries and every later test waits 30 s for the store (one mutation turned 1 failure into 11). A mutation run over the Snapshot class exceeds the 600 s Bash limit when it cascades: run it in the background.
- `SnapshotStep` (static, Wolverine.EFCore) has no `Operation`: it gets only the DbContext, the changed entries and `ISnapshotMappers`. Opening `Operation.OnlyReading` around the mappers needs `SnapshotMappers.cs` (holds the Operation) or a one-line change in `WolverineOutbox.cs`; the DbContext's application service provider is not a sound route. A refused outermost command still leaves its scope's Operation unusable for a later command (Cqrs unit tests: assert state, do not send again).
- Resolved: `Operation.OnlyReading(step)` (Cqrs) is opened by `SnapshotMappers.Map` around each mapper call; `MayChangeState` is false inside, so commands, repository writes and `IUnitOfWorkConnection.Join` refuse. A refused command still marks the Operation rollback-only (the dispatcher's catch), which is the one honest way left to reach the Unit of Work's recheck after the Outbox write: a mapper that swallows the refusal.
- #18 docs pass: both declaration refusals fire at commit inside `SnapshotStep.Build`, never at startup; `CheckKeySpaces` checks every declaration of the Module once any declared aggregate changed, so a bad declaration fails commits of a good one's aggregates too. `IUnitOfWorkConnection.Join` works in Notification and Integration Event Handlers (the delivery runs as the `Deliver` command), which older docs left out. The Kit's refusal wording for read-only code is one sentence ("Code that only reads, such as a query, an authorizer, a validator or a step of the Unit of Work that only reads, ..."); docs listing where `MayChangeState` is false use it.

## Delayed commands (#44, 2026-10-07; WolverineFx 6.46.0)

- **Scheduled publish through the EF outbox works as is.** `DeliveryOptions { ScheduledTime = at }` makes `DeliveryOptions.Override` set `Status = Scheduled`; `DbContextOutbox.PublishAsync` writes the incoming row in the Unit of Work's transaction with status `Scheduled`, `owner_id` 0, `execution_time` = at, same commit timestamp as the business row. The flush does nothing for a durable sender ("relying on durable inbox scheduling"); the scheduled-job poll promotes it, same envelope id.
- **Firing uses `DateTimeOffset.UtcNow`, not `TimeProvider`.** Only `RecurringMessageAgent` (Wolverine.Runtime.Recurring, relevant to #45) reads a TimeProvider. Tests use short real delays (300 ms to 3 s with the 100 ms test polling); a FakeTimeProvider on the Host would put the due time in fake time.
- **`AddMessageHandler(type, handler)` sets `handler.Chain`** (WolverineOptions.cs:1022): one `MessageHandler` instance per message type, never shared, or every type gets the last one's chain. No behaviour test shows it while all chains carry the same global policies.
- **A delayed command due later than `InboxStaleTime` is stale from its first attempt.** Promotion (`PostgresqlMessageStore` `_reassignIncomingSql`, V6.46.0 lines 132-137) sets owner and `Incoming` but keeps `timestamp` (insert time); the stale bump releases owned rows by that time. The Receipt keeps one effect; documented in ADR 0006's #44 amendment, not pinned by a test.
- **Pending vs not yet due (fix round F2):** a stored retry is also a future `Scheduled` row, so "skip Scheduled rows not yet due" broke a dozen retry tests at once. The rule is `status = 'Scheduled' and attempts = 0 and execution_time > now()` = a delayed command never attempted; a retry has `attempts > 0`. `StoredDeliveriesSchemaTests`' hand-made tables need `attempts` and `execution_time` columns. A test needing the effect now waits on the row's `Handled` status itself.
- **Rename simulation (F3):** moving a not-yet-due `Scheduled` row's `received_at` to an undeclared `local://x/` before it fires: the scheduled poll promotes it there, Wolverine builds the queue on demand, and the type's handler gets `Destination.Host = x`.
- **A refused save after the Outbox step (F4):** a second `OpenQuote` of one id fails on `pk_quotes` with `DbUpdateException`, after step 8 wrote the expiry; the bus-publish mutation leaves a second row.
- `Subscriptions.Check` is the one name rule (made public in the internal class) for wire, subscription and delayed command names.
- **Restart proof needs a database of its own** (`create database` on the fixture's container, `NpgsqlConnectionStringBuilder { Database }`): a scheduled row has owner 0, so the fixture Host, alive throughout, would run it. `HostFixture.StartHostAsync` migrates the new database.
- **Context per attempt:** `DeliveryProbes.ContextsOf(subscription, messageId)` records the scope's `OperationContext` in the `IReceipts` decorator.
- **Mutations that went red:** Outbox drops delayed commands (no row); no `ScheduledTime` (row `Incoming`, ran at once); delivery as `Actor.System` (`last_changed_by`); no Receipt check (second expiry fails, dead letter); `Schedule` through `IMessageBus.PublishAsync` instead of the Outbox (rolled-back Operation leaves a row). `mutate44.py` in the session scratchpad.
- **Why a separate registry:** the brief kept #49's files (`Subscriptions`, `Subscription`, `PouryaKitWolverineExtension`, `WireNaming`) out of reach, so delayed commands have `DelayedCommandDeclarations`, `DelayedCommandExtension` and `DelayedCommandDelivery`, and Wolverine's default full-type-name naming. Folding them into `Subscription` later is possible.
- The contract `IDelayedCommands` lives in Messaging.Wolverine, not Messaging: `Command` is in Cqrs, and section C gives Messaging only Domain.
- A delayed command's first attempt is read back from the store (no flush for a scheduled envelope), so `DeliveryProbes.ActivitiesOf("billing.expire-quote")` filtered by trace shows the restored parent; wait on the row's `Handled` status, since `WaitForDeliveriesAsync` does not wait for a row not yet due.

## Recurring commands (#45, 2026-10-07, and final review R2, 2026-10-08; WolverineFx 6.46.0)

- **Wolverine 6.46 ships recurring messages** (`opts.Schedules`, `RecurringMessageAgent`, a singular agent, cron via Cronos, 5 s minimum cadence, a `wolverine_recurring_messages` tracking table when `Durability.EnableRecurringMessages`). Not used: it publishes from its own loop outside any Unit of Work, so the next occurrence cannot commit with the effect, and it brings its own dedup policy. The Kit chains occurrences through the Outbox instead (ADR 0006 amendment for #45). Record this if a reviewer asks "why not the platform's".
- **`Envelope.ScheduledTime` is cleared when a scheduled envelope fires** (Wolverine's own doc comment on `RecurringMessage.OccurrenceHeaderKey`), so the occurrence time travels in the Kit header `DelayedCommandHeaders.Occurrence`, written only for occurrences (`IDelayedCommandOutbox.AddOccurrence`); it also marks the kind, and the delivery dead-letters a delivery whose kind does not match its declaration (review F1: a delayed command stored before its name became recurring would otherwise run as the system Actor).
- **Store query without SQL:** `runtime.Storage.ScheduledMessages.QueryAsync(new ScheduledMessageQuery { MessageType = type.ToMessageTypeName(), PageSize = 0 })` returns only `status = 'Scheduled'` rows (stored retries included), with `Destination` = `local://name/`; PageSize 0 = all. An occurrence promoted to `Incoming` and running is invisible to it, hence the second-chain limit.
- **Occurrences on an epoch grid** (`Recurrence.After`) make two chains collide on the same Receipt key; the turned-away delivery stores no next one, so chains collapse. Mutation "turned-away still stores next" stays red only if the test checks the waiting count before the grid collision collapses it (3 s cadence in the redelivery test).
- **Fixture interference:** every Host start seeds a `Scheduled` row; the fixture's reset deletes it, so only tests that start a second Host on the fixture DB and read all incoming rows break (`NotificationTests` died-before-sending: filter by queue). Also update `PersistenceTests` table list and `DapperWriteTests` Inventory literal list for a new plain-SQL table.
- **Second-chain proof:** `DeliveryProbes.HoldAfterReceipt(name)` holds the running occurrence inside its transaction, then start the second Host: it sees no `Scheduled` row and seeds. Deterministic.
- **Next stored in the same commit:** compare `pg_xact_commit_timestamp(xmin)` of the waiting `Scheduled` envelope and the effect row; only the untouched waiting row keeps its insert xmin (promotion/handling update it).
- `ValidateOnStart` on named options fails `host.StartAsync` before any hosted service runs, so a no-cadence test needs no database of its own.
- #47 landed mid-ticket: `ContinuedOperationContext` returns `(Context, TraceParent)` and `BeginOperation` takes a third `ActivityContext`; a recurring occurrence passes `default`, so its activity parents on Wolverine's span when sampled, else a new trace.
- **Deterministic gates (review F3):** `HoldAfterCommit(typeof(InventoryModule), name)` stops an occurrence right after its commit (its next occurrence just stored, captured by id and `execution_time`), then quick-stop; `HoldAfterReceipt(name)` armed while that hold is held keeps every later occurrence from committing during the assertions. A seed check needs no timing at an hourly cadence.
- **The dead-letter attempt (Wave 2 final review R2, 2026-10-08).** Inside a Wolverine handler, `envelope.Attempts` is already this attempt's number: `Executor.ExecuteAsync` increments it before `HandleAsync` (6.46.0 `src/Wolverine/Runtime/Handlers/Executor.cs:235`, `:247`), and on a throw `FailureRule.TryCreateContinuation` takes the slot whose `Attempt == Attempts`; `ScheduleRetry(delays)` adds one slot per delay, `.Then.MoveToErrorQueue()` the next, and past the last slot the rule returns `MoveToErrorQueue` itself. So `Attempts > RetryDelays.Length` is the attempt that dead-letters. `DelayedCommandDelivery` catches with that filter and calls `RecurringCommandStart.StoreFirstUnlessWaitingAsync` on `context.Runtime.Cancellation` (the handler's token is the execution-timeout CTS). A 6.46.0 source tree sat in another session's scratchpad (`c004d81d.../scratchpad/wsrc/wolverine-6.46.0`); `Directory.Build.props` confirms the version.
- **The unless-waits query hides an early store.** With "store on every failed attempt" or `>=`, the dead-letter test stays green: the first store wins and later ones see it waiting. Only a test where every attempt but the last fails, then reads the store while `HoldAfterCommit` holds the successful commit (two `Scheduled` rows when an early attempt stored one), pins the moment. `DeliveryProbes.FailAfterReceipt(name, deliveries)` gained a count for it.
- **A dead letter's occurrence** is readable through `runtime.Storage.DeadLetters.QueryAsync(new DeadLetterEnvelopeQuery { PageSize = 0 })`: `DeadLetterEnvelope.Envelope.Headers[DelayedCommandHeaders.Occurrence]` survives. Do not assert exactly one dead letter at a short cadence: the next occurrence can come due milliseconds after the first dead letter, before the test disarms the failure.

## Proofs before fixes: stale time and a shape change (#82, 2026-10-10; WolverineFx 6.48.3)

- **`DeliveryProbes`' attempt log and `_receiptHold` are process-wide statics.** A new test that delivers under a name another test asserts "no attempt" for (`ContextsOf(KindChanged)` empty) breaks it, depending on run order: declare the command under a name of the test's own (`stub.stale-note`). Only one `HoldAfterReceipt` exists at a time, so hold two deliveries in turn, never together.
- **A delivery due later than `InboxStaleTime`** (P7): the release takes only owned rows, so a waiting `Scheduled` row is never handed out early; an attempt is copied only when a recovery poll lands while it runs. Proof shape: hold after the Receipt, wait for `pg_stat_activity` `wait_event_type = 'Lock' and query like 'insert into "<schema>".pouryakit_receipts%'` with `datname = current_database()`, release. Unheld occurrences due 1-2 s after store with a 500 ms stale time ran once (7 of 7, three runs). Red: ignore `RecordAsync`'s result in `RunDelayedCommandHandler` (two notes, two reconciliations).
- **An occurrence whose body no longer reads** (T2): Wolverine's `HandlerPipeline.TryDeserializeEnvelope` returns `MoveToErrorQueue` before any Kit code, so `DelayedCommandDelivery`'s dead-letter branch never stores a next one; the cadence waits for a Host start. Rewrite a stored body with `Wolverine.Runtime.Serialization.EnvelopeSerializer.Deserialize(body)`, set `Data`, `Serialize`; `DatabasePersistence.ReadIncomingAsync` takes `ScheduledTime` from the `execution_time` column, not the body. Make the row due only after the restarted Host's start returned: a poll at start (`ScheduledJobFirstExecution` 0) could promote it before `RecurringCommandStart` looks, and that query reads `Scheduled` rows only, so it would seed. Red: drop `RespectRequiredConstructorParameters` from `UsePouryaKitWireJson` (the old body reads with a default occurrence).

## Database-generated values and the model read (#85, 2026-10-10; EF Core 10.0.12, WolverineFx 6.48.3)

- **A static cache keyed by (DbContext type, Module) cannot hold the key-space verdict:** `SnapshotTests.WithDeclarationAsync` composes a second Host whose StubModule adds a bad declaration over the same `StubDbContext`, so a verdict cached by the fixture Host's commits would skip that Host's check. Only the model read (aggregate types, roots, generated properties) is cached per DbContext type; `CheckKeySpaces` still runs per commit on the Host's declarations. `ISnapshotMappers` is public, so its signature cannot carry the DbContext type.
- **Order is observable:** the key-space refusal lists roots in the dictionary's enumeration order; a `FrozenDictionary` reordered them (`Case` before `Folder`) and the exact-message test went red. Keep `ToDictionary` where the order reaches a message.
- **EF 10 metadata, probed with a throwaway test that dumped every property to the scratchpad:** a TPH discriminator (`Case.Discriminator`) is `ValueGenerated.Never` with a client value generator; `Version` is `Never`; FK and owned shadow keys are keys; `GetFlattenedProperties()` includes inherited and complex-type properties; `GetReferencingForeignKeys()` on a derived type lists its own navigations' FKs (`BookCase` → `Book`).
- **Red-once that shows the stale value:** `Record.ExceptionAsync` the command, `WaitUntilDeliveredAsync`, then first `Assert.Equal(committed column values, received Snapshot values)` (both empty when refused), then the message, then the row count. With the guard off it printed `Expected ["printed by the database"]`, `Actual [null]`. A string property with `HasDefaultValueSql` must stay null in the CLR (EF sends `""` otherwise and the database default never applies).
- **Review F2: `ValueGenerated != Never` is not "the database generates it".** Decompiled EF 10.0.12 (`ilspycmd -t <type> ~/.nuget/packages/microsoft.entityframeworkcore/10.0.12/lib/net10.0/Microsoft.EntityFrameworkCore.dll`): `PropertyExtensions.RequiresValueGenerator` gives a non-key property a client value at Add only when `GetValueGeneratorFactory() != null` (it covers `HasValueGeneratorFactory` types too); `ValueGenerationManager` takes it from `IValueGeneratorSelector.TrySelect(property, property.DeclaringType)` and sets it for good unless `GeneratesTemporaryValues`. `HasValueGenerator` does not set `ValueGenerated`; the Stub's `Badge` says `ValueGeneratedOnAdd().HasValueGenerator<GuidValueGenerator>()`. The refusal now allows exactly `OnAdd` + factory + a non-temporary selected generator (`dbContext.GetService<IValueGeneratorSelector>()`). `ValueGenerated`'s `ForAdd`/`ForUpdate` helpers are internal: compare the enum. A comment saying something is "taken from" EF trips check-docs' provenance rule.
- The Stub migration recipe above still works (temporary factory + temporary `Microsoft.EntityFrameworkCore.Design` reference, build, then `dotnet ef migrations add … --no-build`); a new Stub table also edits `PersistenceTests`' table and migration lists.

## A recovery at start, gated, and the forwarder question (#94, 2026-10-10; WolverineFx 6.48.3)

- **No 6.48.3 store API reads one queue's `Scheduled` rows with their bodies**, so a start-time readability check of a waiting occurrence is a no-go without raw SQL or a whole-table read. Decompiled 6.48.3 (`JasperFx/wolverine@c1eab2a7`; another session left it at `00cca649-e6c4-44eb-8549-8c8dbeae846f/scratchpad/decomp/{core,rdbms,pg}`): `IScheduledMessages.QueryAsync` selects `body` but keeps only `TryReadTenantId` of it (`Wolverine.RDBMS/MessageDatabase.cs:1987`, `:2038`); `IMessageStore.LoadPageOfGloballyOwnedIncomingAsync(uri, limit)` is the one destination-filtered body loader and pins `status = 'Incoming'` and owner 0 (`Wolverine.Postgresql/PostgresqlMessageStore.cs:347`, `:708-711`); `IMessageStoreAdmin.AllIncomingAsync` reads the whole table (`MessageDatabase.cs:421-424`); `IMessageDatabase.WriteLoadScheduledEnvelopeSql` only writes SQL (all queues, `execution_time <= now`, `RecoveryBatchSize`) for the caller to run. A grep for public members returning `Envelope`, a list or an array of them over core, RDBMS and Postgresql finds nothing else that reads the inbox.
- **`IForwardsTo<T>` never reaches a Kit delivery.** `HandlerGraph.AddForwarders` (`Wolverine.Runtime.Handlers/HandlerGraph.cs:629-643`) builds a `ForwardingHandler` only when `_chains` holds the destination type; `AddMessageHandler` (`:113-122`) writes `_handlers` only, and the Kit turns conventional discovery off, so no forwarder is built toward a pre-built `MessageHandler`. 6.x registers forwarders with `RegisterMessageForwarder<TFrom, TTo>()`; `UseAutomaticForwarderDiscovery()` is obsolete.
- **An unknown message type is dead-lettered in a Kit Host, not completed** (corrected by #90, 2026-10-10; #94's review read it the other way and #94's fix wrote that into `messaging.md`): `HandlerPipeline.TryDeserializeEnvelope` returns `NoHandlerContinuation` when `TryFindMessageType` misses (`Wolverine.Runtime/HandlerPipeline.cs:176-192`), which runs every `IMissingHandler` before `CompleteAsync` (`Wolverine.ErrorHandling/NoHandlerContinuation.cs:24-51`). The Kit sets `UnknownMessageBehavior.DeadLetterQueue`, whose setter registers `MoveUnknownMessageToDeadLetterQueue` as one (`Wolverine/WolverineOptions.cs:519-535`); it calls `MoveToDeadLetterQueueAsync` with an `UnknownMessageTypeNameException`, which writes the dead-letter row (`MessageDatabase.cs:1427` deletes the incoming row and inserts it), so the later `CompleteAsync` updates nothing. ADR 0006 lines 304-306, 324, 375 and 879 say the same. Read the missing-handler list before calling a no-handler path completed. An unreadable body is `MoveToErrorQueue` (`:194-198`).
- `IDeadLetters.DiscardAsync(DeadLetterEnvelopeQuery)` deletes by `ReceivedAt`, `ExceptionType`, `MessageType` (`MessageDatabase.cs:1179-1232`); a replay only sets `replayable`, and the body is read strictly again.
- `check-docs.py`'s Names corpus is every word of the code files, comments and XML summaries included, so a Wolverine name the Kit's own summary writes (`IForwardsTo`, `IDeadLetters.DiscardAsync`) passes in the skill and the architecture README; a dotted name rooted at `IMessageStore` (in `ALLOWED`) is skipped.

**Why:** each would let a Snapshot, delayed-command or recurring test pass vacuously or decided a design point; #45 builds on #44's store and delivery.
**How to apply:** when touching Snapshots, the Outbox seam or write, Receipts, the delivery step, delayed or recurring commands, or tests that start extra Hosts. Related: [[wolverine-runtime-and-delivery-facts]], [[persistence-and-dapper-facts]], [[observability-tracing-and-http-facts]].
