## Composition checks and the Module seam (#61, 2026-10-07; .NET 10.0.12, WolverineFx 6.46.0, JasperFx 2.80.2)

- **Composition checks run when the container is built, not at start** (fix round, review F1, high): a built, unstarted Host runs Operations through `IGatewayProcessor` (tests do), so a `StartingAsync` check let a `[RequiresPermission]` operation run unchecked. `ValidatingServiceProviderFactory` runs every `ICompositionCheck` on the built provider before returning it; at `StartingAsync` the runner fails first for a replaced factory, then runs #62's `IStartupCheck`s (what only the built application shows, such as mapped endpoints). Any Kit guarantee about composition belongs to the build.
- **The Kit's delivery commands** (`Deliver`, `RunDelayedCommand`, `StartRecurringCommand`) are registered by `UsePouryaKitWolverine` in every Host, so a check over "every registered command" misfires (review F3). Registering them per declaration was rejected: on a Module's builder `HostModules` would record a Kit command as the first declaring Module's. The Unit of Work check counts only commands whose type or registered handler (`ImplementationType`) is in a recorded Feature assembly: a scanned handler of a Contracts assembly's command counts too (second review, F7). Fixture: `Misnamed/SeparateCommandHandler` handles `Unowned`'s `UnownedCommand`; the command must sit in an assembly nothing `AddPouryaKitCqrs`-scans without its handler (else "has 0 handlers"), and the handler in one no Module `AddPouryaKitCqrs`-scans (#62's `EndpointForgettingModule` scans `Unversioned`, so a handler there broke it).
- **`AddPouryaKitModules` no longer calls `AddPouryaKitCqrs()`**: anything a Unit of Work resolves in a factory (the Domain Event drain, review F2) must come with `AddDispatcher`, since `ValidateOnBuild` cannot see inside factories.
- **`Host.StartAsync` order:** it resolves every `IHostedService` first (constructing `WolverineRuntime`, so `WolverineOptions` and every Kit `IWolverineExtension` check run then), then `IStartupValidator` (`ValidateOnStart` options), then each `IHostedLifecycleService.StartingAsync`, then `StartAsync`. Composition checks run at `Build()`, before all of that, so they come before any Wolverine start-time refusal (missing publication, wire-name clash) or options failure; at `StartingAsync` come the replaced-factory sentinel, then #62's startup checks, still before Wolverine or the web server starts. One `StartingAsync` exception is rethrown unwrapped (assert `InvalidOperationException`, not `AggregateException`); nothing needs stopping after it.
- **JasperFx `RunJasperFxCommands` with `AutoStartHost`** starts the pre-built Host synchronously in `buildExecutor`, with no catch, so a start failure leaves `Main` as is and `WebApplicationFactory<Program>.Services` rethrows the same `InvalidOperationException` (the generated `HostTests` passed under `validate.py`).
- **Decision A trap:** `module.AddPouryaKitCqrs()` with no assembly on a test Module defined in `ModularMonolith.Tests` scans that whole assembly (every Stub handler), and `EnsureUnitOfWorkForCommands` then throws. Test-only Modules register their one handler by hand; `AddPouryaKitModules` registers the dispatcher.
- **Null-owned declarations fail at build in a Host of Modules**, and Module-named ones fail at build in a Host without Modules that calls `AddPouryaKitCompositionChecks` (the commit-time Snapshot refusal is only the backstop of a Host without the checks). A test that adds `builder.Services.Publish/Subscribe/...` to an `AppFixture.ComposeHost` Host and builds it must name the Module (`typeof(StubModule)`, `typeof(CatalogModule)`); a test that only asserts an earlier failure (Wolverine extension at hosted-service resolution) still gets its own message.
- **A valid Notification Handler, or a Feature command, no Module declares** needs an assembly nothing scans: `tests/ModularMonolith.Tests/Unowned` (its own csproj, excluded from the test project's sources, in the slnx). Every handler in the Stub's assembly belongs to the Stub, so declaring them again without a Module is refused at registration, not at start.
- **Every Module `AddPouryaKitModules` adds is recorded** in `HostComposition.Modules` (`ModulesBuilder.Add` calls `IModuleServices.ModuleOf`), whatever its Composition Root registers (test `QueryOnlyModule`); its Feature assemblies are recorded only by a Kit registration that scans.

## Misconfigured Hosts: build and start checks (#62, 2026-10-08; ASP.NET Core 10.0.12, Microsoft.Extensions.Http 10.0.12 and .Http.Resilience 10.10.0, WolverineFx 6.46.0)

- **Wolverine endpoint modes are final only after Wolverine starts.** `Endpoint.Compile` (run in the runtime's start) applies `Transports.EndpointPolicies` (`UseDurableLocalQueues`) then the endpoint's delayed configuration (`LocalQueue(x).BufferedInMemory()`). A composition check at `StartingAsync` reads every queue's default, so the queue/broker durability check stays in `StartupCheck.StartedAsync`; only its Outbox part became `OutboxCheck` on the runner.
- **Authentication-ran signal:** `AuthenticationMiddleware.Invoke` sets `IAuthenticationFeature` first, for every request, anonymous too. `WebApplicationBuilder.ConfigureApplication` adds `UseRouting` (when data sources exist and the app did not call it), `UseAuthentication` and `UseAuthorization` (when their services exist and the app did not call them) ahead of the app's pipeline, so a limiter-order trap needs an explicit `UseAuthentication()` after `UseRateLimiter()`. Routing sets nothing on a no-match, so a limiter before routing is undetectable.
- **Completed HttpClient chain:** `DefaultHttpClientFactory.CreateHandlerEntry` wraps `HttpMessageHandlerBuilderActions` (where `RemoveAllResilienceHandlers` acts, through `ConfigureAdditionalHttpMessageHandlers`) in every `IHttpMessageHandlerBuilderFilter`; a filter that calls `next(builder)` then reads `AdditionalHandlers` sees the final chain. The entry is a `Lazy`, so a throw there repeats on every `CreateClient` of that name. `ResilienceHandler` is public.
- **The test bin has the sample Host's appsettings.json** (`ConnectionStrings:app` = localhost): a plain `Host.CreateApplicationBuilder` in a test sees it, so a "missing connection string" test must use another name.
- A test Host without Modules that now needs the runner (`AddPouryaKitCompositionChecks`) also gets `ValidateOnBuild`: registering the whole Stub assembly's Notification Handlers then fails at `Build` on their dependencies; use the `Unowned` assembly. `UnitOfWorkCheck` also flags the Kit's own `CommandHandler<Deliver>` in a Wolverine Host with no Unit of Work (a second line, after the first problem).
- Group's `Finally` refusals (AllowAnonymous, RequireIdempotencyKey on GET) surface at `host.StartAsync` in the AppFixture Host.
- **Two moments since the #62 merge round (orchestrator decision 2026-10-08):** `ICompositionCheck` runs inside `ValidatingServiceProviderFactory` at `Build()`; `IStartupCheck` runs in `CompositionCheckRunner.StartingAsync` after the replaced-factory sentinel, for what needs the built app (routes mapped after `Build()`). `DurableQueuesCheck` (was `StartupCheck`) keeps Wolverine's `StartedAsync`. A test asserting a composition check uses `Assert.Throws(() => builder.Build())`; `AppFixture.ComposeHost` itself throws then.
- **`UsePouryaKitWolverine` installs `AddPouryaKitCompositionChecks`**, so every plain-services test Host with Wolverine gets `ValidateOnBuild`: scanning the whole Stub assembly there fails (its handlers need Catalog, Dapper and Gateway services); register the one handler by hand plus `DeliveryLog` and `AddPouryaKitDapper`. Wolverine-refusal tests on the transport-neutral overload need a stand-in `IOutbox` (a public marker, renamed in #81) or the Outbox check fails the build first; the EF Core overload needs a Unit of Work (`EfReceipts` needs `IUnitOfWork`).
- A bare Host with a declaration and no Wolverine reports `OutboxCheck` beside the ownership line: assert the line is among `Message.Split(NewLine)`.
- **#62 review F2/F6:** `CompositionCheckRunner` is registered by `AddDispatcher` (every Kit Host reaches it), and the entry adds the `CompositionChecksInstalled` marker, so a Host that never installed the checks fails at start naming the entry. The limiter refuses the order only when `IAuthenticationSchemeProvider` is registered; a no-authentication test Host needs `AddAuthorization()` (route metadata needs the middleware) and `AllowAnonymousAs(actor)` works on non-Module endpoints too.

## Store database check (#63, 2026-10-08; Npgsql 10.0.3, WolverineFx 6.46.0)

- **`new NpgsqlConnectionStringBuilder(s)` does not split `Host=a:5433`**: `Host` stays `"a:5433"` and `Port` reads 5432. The split (`TrySplitHostPort`, last colon unless a bare IPv6 address) runs in the internal `PostProcessAndValidate`, only when a connection opens; a check that parses must split each comma-separated host itself. With `Database` unset Npgsql sends no database parameter, so the server uses the user's name. `PostgresEnvironment` reads only `PGUSER`, `PGPASSWORD`, `PGPASSFILE` and the SSL variables: no `PGHOST`, `PGPORT` or `PGDATABASE` fallback to model. `ilspycmd -p -o <dir> <dll>` decompiles the whole assembly for grepping.
- **The store uses the string `UsePouryaKitWolverine(connectionName)` read at composition** (`PersistMessagesWithPostgresql(connectionString)`), while EF Core resolves a DbContext's `Name=ConnectionStrings:x` from the final `IConfiguration`. A check of "the store's database" compares the captured string with each DbContext's final one; final-vs-final would describe a database Wolverine never uses.
- **A record two packages read needs to be public**: the only `InternalsVisibleTo` between Kit packages is Cqrs's (pinned by `TrustedRestoreTests` and stated in `IRequiresAuthorizer`'s remarks). #63 moved #62's internal `PostgresConnection` to `PouryaKit.Persistence.EFCore` as the public `DbContextConnection`.
- `TryAddEnumerable(ServiceDescriptor.Singleton<ICompositionCheck>(new Check(args)))` works: an instance descriptor's implementation type is the instance's type, so the check can carry composition-time facts in its constructor instead of a marker record.
- **A composition check that opens no connection is tested without databases**: derive the strings from `AppFixture.ConnectionString` with another `Database`, `Port` or `Host` and assert `Build()`'s message; nothing connects while a Kit Host is built, so a check that connected would fail differently. A Host of only `UsePouryaKitPostgres<StubDbContext>` and `UsePouryaKitWolverine` builds under `ValidateOnBuild` with no other check firing.
- **Fix round (review of `99a6d0e`), mirror Npgsql fully or the review finds it**: database is `Database ?? Username` (a record's null == null had made two user-only strings equal); a rooted path or `@…` host is a Unix socket directory (case kept, no port split, separate `Port`); an embedded port is `int.Parse`d (`db:05432` = `Port=5432`), so compare (host, int port) pairs.
- **Read a DbContext's real connection through EF Core, never its options** (second review of `38c0dc1`, F5): `ConfigureDbContext<T>` after `AddDbContext` overrides it, and EFCore.PG 10's `UseNpgsql(dataSource)` sets only `NpgsqlOptionsExtension.DataSource`, leaving `RelationalOptionsExtension.ConnectionString` stale. Resolve the DbContext in an own `CreateScope()` and read `Database.GetDbConnection().ConnectionString`: unopened, EF resolves `Name=` itself, a data source gives its own string. It throws `InvalidOperationException` for a `Name=` the configuration lacks (catch it in a helper: an iterator cannot `yield` inside try/catch). With no string, connection or source at all, EFCore.PG gives an empty-string connection, no throw. Skip a DbContext whose configured name is blank first, or the missing-string check's line (`DbContextConnectionsCheck` since the final review D fix round, was `PostgresConnectionsCheck`) is doubled.
- **A missing `Name=` throws at DbContext construction, not in `GetDbConnection()`** (R6, 2026-10-08): `PouryaKitDbContext`'s constructor reads `ChangeTracker`, which builds the model and resolves the relational connection, so "A named connection string was used, but the name … was not found" and a model error ("requires a primary key") are both `InvalidOperationException`s from `GetRequiredService(dbContext)`. Moving construction out of the `try` turns the first raw too; try/catch placement cannot separate them. Orchestrator's decision: both surface unwrapped from `Build()`, the check catches nothing and has no "no connection" line.
- **Unknown is never a wildcard** (F1, orchestrator 2026-10-08): a string naming neither `Database` nor `Username` fails the build with its own line; Npgsql would take PGUSER, the GSS principal or the OS user.
- Connection names are `IConfiguration` keys, which ignore case: compare and group them with `OrdinalIgnoreCase` (final review D F4, "app" vs "APP" threw). A check line shared by several registration APIs names none of them (F6).
- A second DbContext for a build-time check test needs no new fixture: the Stub's `ReadCollectionDbContext` works beside `StubDbContext` under `UsePouryaKitPostgres`, since nothing builds its model at `Build()` (R7).
- A pass-case test of a check ("two names for one database build") is vacuous with the check off; pair it with a mutation that breaks the comparison (strings compared as written) for its red-once.

## Messaging checks at the build (Wave 2 final review B, 2026-10-08; WolverineFx 6.46.0)

- **`RoutingCheck` (an `ICompositionCheck` from `UsePouryaKitWolverine`) holds the routing refusals and calls `WireNaming.Declare`** at `Build()`, only when its own lines are empty. Declare is load-bearing: with the check unregistered, four delivery tests failed (wire names never declared), not just the refusal tests. A Host that fails another check still declares its names for the process; tests must keep one wire name per contract type across Hosts (they do; `tests.folder.v1` is declaration-time only).
- **Adding a line to the check gates Declare:** a test that proves a Declare refusal (named-before-declared) must have no other routing line, so a `Receive` there needs a subscription.
- **`SubscriptionUnitOfWorkCheck`** adds a line to any plain test Host that subscribes without a Unit of Work (`StandInOutbox` Hosts): assert `Contains(line, Message.Split(NewLine))`. EF Core-overload Hosts without one already fail `ValidateOnBuild` first (`EfReceipts` needs `IUnitOfWork`).
- **The Stub owns every handler in `ModularMonolith.Tests`** (its `AddPouryaKitCqrs()` scans the assembly), so `QueryOnlyModule` and similar cannot be composed beside the Stub in `AppFixture.ComposeHost` ("registers a handler for …, which belongs to StubModule"). A subscription-only Module can (`Subscribe` registers no command handler).

## Blank connection strings and a check that throws (#66, 2026-10-08; WolverineFx 6.46.0, Microsoft.Extensions.DependencyInjection 10.0.12)

- **A blank message store string was not caught at the build.** `PersistMessagesWithPostgresql("")` throws Wolverine's own `InvalidOperationException` ("needs to at least have either a connection string or NpgsqlDataSource") inside `UsePouryaKitWolverine`, because `AddWolverine` runs its configure delegate at once; a string of spaces is accepted, the Host builds, and `StartAsync` throws `ArgumentNullException` (Parameter 'Host'). Both registrations now refuse null or blank themselves (`UsePouryaKitWolverine(connectionName)`, `UsePouryaKitRabbitMq`). WolverineFx.RabbitMQ's parser applies nothing of a blank string and says nothing.
- A blank value in a test: `builder.Configuration.AddInMemoryCollection([new("ConnectionStrings:x", " ")])`, which needs `using Microsoft.Extensions.Configuration;` on a `HostApplicationBuilder`.
- **`ServiceProvider.Dispose` stops at the first disposable that throws**, and disposes in reverse order of creation. A test of "the container is disposed, and a failing disposal does not replace the check's exception" resolves the failing one first, then the probe, both registered by factory so the container owns them (an instance registration is never disposed).
- **`ServiceProvider.Dispose` itself throws `InvalidOperationException` for an owned service that is only `IAsyncDisposable`** (#67, T44), with a message that begins with the type's name in quotes, so `Assert.Throws<InvalidOperationException>` alone cannot tell it from the factory's own exception: assert the message. `AddSingleton(type, _ => Activator.CreateInstance(type)!)` with `[InlineData(typeof(...))]` runs one test over both kinds of failing disposal. Both failing paths of `ValidatingServiceProviderFactory` now go through one guarded `Discard(provider)`.

## Tenant requirement check (#145, 2026-10-17)

- **A test Module with a command and no Unit of Work fails while `AddPouryaKitModules` composes it** ("X handles the command ... but registers no Unit of Work"), before any composition check runs. To isolate one build-time problem, give it `module.UsePouryaKitPostgres<StubDbContext>("app", "stub")` and pass `--ConnectionStrings:app=<Fixture.ConnectionString>` to `CreateApplicationBuilder`: the build then fails with exactly the one line, so the test asserts `Equal`, not `Contains` over split lines.
- **`Unversioned` (one `IEndpoint`, no operation) is the neutral assembly to name to `AddPouryaKitTenancy`** in a "scans more than it names" fixture; `Unowned` is the extra Cqrs assembly (one command, its handler). Never scan `Misnamed` beside `Unowned` (two handlers of `UnownedCommand`).
- **Any edit to `CqrsServiceCollectionExtensions.cs`, even below its cited range 30-42, forces the execution-core diagram re-pin** ([[docs-verification-tools]], "Diagram source citations"): a check in its own file still gets registered in `AddDispatcher` there.

## A check that needs a declaration and the EF model (#117, 2026-10-17)

- **Messaging.Wolverine's declarations are internal and it has no `InternalsVisibleTo`**, while the Snapshot key lives in the EF model, which Messaging.Wolverine must not reference (`PackageGraph` closure). `SnapshotKeyTenancyCheck` lives in Messaging.Wolverine.EFCore, registered by `UsePouryaKitWolverine(connectionName)` beside `MessageStoreDatabaseCheck`, reads the declarations through one new public member, `ISnapshotMappers.DeclaredAggregates(module)`, resolvable in a scope with no Operation begun, and builds each DbContext in its own scope as the store check does; materialize inside the iterator, the scope dies with it.
- **Test Hosts:** `UsePouryaKitWolverine("app")` needs `using PouryaKit.Messaging.Wolverine.EFCore`, or CS1503 binds the `Action<WolverineOptions>` overload. Publish a type under the Stub's own wire name (`stub.shelf-snapshot.v1`): a type keeps one wire name per process. A tenant-scoped test Module with `AddPouryaKitTenancy(Unversioned)`, `UsePouryaKitPostgres<StubDbContext>` and the declarations builds to exactly one problem line. With the Guid rule removed, the shared fixture itself fails to build (Catalog's Guid-keyed `Product` Snapshot), which shows the rule matters.
- **A check over a Module's declarations judges that Module's own DbContext only** (#117 review F1): the commit reaches only the committing DbContext, so a shared interface or base type declared by one Module must not match another Module's aggregates. Resolving the Module's keyed `IUnitOfWork` in a composition check to reach its DbContext builds `WolverineOutbox` and so `IWolverineRuntime`, which names every message type before `WireNaming` declares it: the shared fixture failed to start with `Wolverine named it ... before it was declared`. Instead `AddPouryaKitEfCore` records a keyed `DbContextConnection` per Module (`IModuleServices.ModuleOf`), and the check resolves only that DbContext. Use `AddKeyedSingleton<DbContextConnection>(module, record)`: the non-generic overload is ambiguous (CS0121). Regression fixture: a tenant-scoped Module over `CatalogDbContext` (Guid keys) declaring `PublishSnapshot<IAggregateRoot, ...>` beside a Module over `StubDbContext`.

## Tenant check over what Cqrs scanned (#150, 2026-10-17)

- **`HostComposition.FeatureAssembliesOf` holds every registration's assemblies** (Validation, Security, Web, Localization, Dapper, Tenancy itself), so a check of "what the dispatcher runs" must not read it: `AddPouryaKitCqrs` now records its own scan in `ComposedFeatures.Dispatching`, read through the internal `HostComposition.DispatchingAssembliesOf`. Fixture: a tenant-scoped Module with `AddPouryaKitCqrs(Unversioned)` and `AddPouryaKitLocalization(Unowned)` builds; `Localization` in a plain `Host.CreateApplicationBuilder` Host builds under `ValidateOnBuild`.
- **A SQL literal in a sample migration reaches `DapperTenantTests`' listing** of literals that read a tenant table: the rule itself skips migrations (`IsMigration`), the listing did not. A `migrationBuilder.Sql` naming `catalog.products` moved it; filter `Migration` owners there.

**Why:** each decided a design point or a test of #61, #62, #63 or final review B, which all add checks on the same runner.
**How to apply:** when adding a composition or start-time check, an HTTP pipeline order check, an outgoing-client rule or a Wolverine endpoint inspection; when a check reads connection strings or a record two Kit packages share; when composing a test Host with Host-level declarations, a test-only Module or a Module beside the Stub.
