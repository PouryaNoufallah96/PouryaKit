Verified in ticket #45 (2026-10-07), WolverineFx 6.46.0; check the merged code before relying on the design:

- **Wolverine 6.46 ships recurring messages** (`opts.Schedules`, `RecurringMessageAgent`, a singular agent, cron via Cronos, 5 s minimum cadence, a `wolverine_recurring_messages` tracking table when `Durability.EnableRecurringMessages`). Not used: it publishes from its own loop outside any Unit of Work, so the next occurrence cannot commit with the effect, and it brings its own dedup policy. The Kit chains occurrences through the Outbox instead (ADR 0006 amendment for #45). Record this if a reviewer asks "why not the platform's".
- **`Envelope.ScheduledTime` is cleared when a scheduled envelope fires** (Wolverine's own doc comment on `RecurringMessage.OccurrenceHeaderKey`), so the occurrence time travels in the Kit header `DelayedCommandHeaders.Occurrence`, written only for occurrences (`IDelayedCommandOutbox.AddOccurrence`); it also marks the kind, and the delivery dead-letters a delivery whose kind does not match its declaration (review F1: a delayed command stored before its name became recurring would otherwise run as the system Actor).
- **Store query without SQL:** `runtime.Storage.ScheduledMessages.QueryAsync(new ScheduledMessageQuery { MessageType = type.ToMessageTypeName(), PageSize = 0 })` returns only `status = 'Scheduled'` rows (stored retries included), with `Destination` = `local://name/`; PageSize 0 = all. An occurrence promoted to `Incoming` and running is invisible to it, hence the second-chain limit.
- **Occurrences on an epoch grid** (`Recurrence.After`) make two chains collide on the same Receipt key; the turned-away delivery stores no next one, so chains collapse. Mutation "turned-away still stores next" stays red only if the test checks the waiting count before the grid collision collapses it (3 s cadence in the redelivery test).
- **Fixture interference:** every Host start seeds a `Scheduled` row; the fixture's reset deletes it, so only tests that start a second Host on the fixture DB and read all incoming rows break (`NotificationTests` died-before-sending: filter by queue). Also update `PersistenceTests` table list and `DapperWriteTests` Inventory literal list for a new plain-SQL table.
- **Second-chain proof:** `DeliveryProbes.HoldAfterReceipt(name)` holds the running occurrence inside its transaction, then start the second Host: it sees no `Scheduled` row and seeds. Deterministic.
- **Next stored in the same commit:** compare `pg_xact_commit_timestamp(xmin)` of the waiting `Scheduled` envelope and the effect row; only the untouched waiting row keeps its insert xmin (promotion/handling update it).
- `ValidateOnStart` on named options fails `host.StartAsync` before any hosted service runs, so a no-cadence test needs no database of its own.
- #47 landed mid-ticket: `ContinuedOperationContext` returns `(Context, TraceParent)` and `BeginOperation` takes a third `ActivityContext`; a recurring occurrence passes `default`, so its activity parents on Wolverine's span when sampled, else a new trace.
- **Deterministic gates (review F3):** `HoldAfterCommit(typeof(InventoryModule), name)` stops an occurrence right after its commit (its next occurrence just stored, captured by id and `execution_time`), then quick-stop; `HoldAfterReceipt(name)` armed while that hold is held keeps every later occurrence from committing during the assertions. A seed check needs no timing at an hourly cadence.
- Mutation script: `mutate45.py` in the session scratchpad (10 mutations incl. kind check and repeat message, all red).

- **The dead-letter attempt (Wave 2 final review R2, 2026-10-08).** Inside a Wolverine handler, `envelope.Attempts` is already this attempt's number: `Executor.ExecuteAsync` increments it before `HandleAsync` (6.46.0 `src/Wolverine/Runtime/Handlers/Executor.cs:235`, `:247`), and on a throw `FailureRule.TryCreateContinuation` takes the slot whose `Attempt == Attempts`; `ScheduleRetry(delays)` adds one slot per delay, `.Then.MoveToErrorQueue()` the next, and past the last slot the rule returns `MoveToErrorQueue` itself. So `Attempts > RetryDelays.Length` is the attempt that dead-letters. `DelayedCommandDelivery` catches with that filter and calls `RecurringCommandStart.StoreFirstUnlessWaitingAsync` on `context.Runtime.Cancellation` (the handler's token is the execution-timeout CTS). A 6.46.0 source tree sat in another session's scratchpad (`c004d81d.../scratchpad/wsrc/wolverine-6.46.0`); `Directory.Build.props` confirms the version.
- **The unless-waits query hides an early store.** With "store on every failed attempt" or `>=`, the dead-letter test stays green: the first store wins and later ones see it waiting. Only a test where every attempt but the last fails, then reads the store while `HoldAfterCommit` holds the successful commit (two `Scheduled` rows when an early attempt stored one), pins the moment. `DeliveryProbes.FailAfterReceipt(name, deliveries)` gained a count for it.
- **A dead letter's occurrence** is readable through `runtime.Storage.DeadLetters.QueryAsync(new DeadLetterEnvelopeQuery { PageSize = 0 })`: `DeadLetterEnvelope.Envelope.Headers[DelayedCommandHeaders.Occurrence]` survives. Do not assert exactly one dead letter at a short cadence: the next occurrence can come due milliseconds after the first dead letter, before the test disarms the failure.

**Why:** each decided a #45 test or design point.
**How to apply:** for any change to recurring or delayed commands, the Outbox write, or tests that start extra Hosts. Related: [[delayed-command-facts]], [[dead-letter-and-stale-time-facts]], [[observability-facts]].
