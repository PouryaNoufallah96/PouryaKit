## Spike S1 (#2, 2026-10-05; WolverineFx 6.46)

The authoritative record is `docs/adr/0004-*.md`; check it is still current before relying on this.

- Wolverine 6 needs `WolverineFx.RuntimeCompilation`, or the Host fails at start (TypeLoadMode.Dynamic has no IAssemblyGenerator).
- In a raw Wolverine Host using conventional discovery, call `opts.Discovery.IncludeAssembly(...)` for handlers outside the entry assembly. The Kit disables conventional discovery in `WolverineHostApplicationBuilderExtensions` and registers subscription handlers explicitly with `AddMessageHandler` in `PouryaKitWolverineExtension`.
- To prove "same transaction", compare `pg_xact_commit_timestamp(xmin)`, not `xmin`. EF wraps `SaveChanges` inside a user transaction in a savepoint, so the rows get different xids. The container needs `-c track_commit_timestamp=on`.
- A killed node's envelopes take about 75 s to recover with Balanced default timers. Tests should shorten the `Durability.*` timers or use Solo mode.
- If a Notification is committed but not flushed while its Host stays alive, it is stuck until the Host stops. Recovery takes only rows with `owner_id = 0`. `InboxStaleTime` releases the stuck row, but it also re-dispatches rows whose handlers are still running and have been running longer than the stale time.
- An `IDbContextOutbox<T>` instance is good for one commit attempt only. A rolled-back envelope stays in its outstanding list. With the default `MultiFlushMode` of `OnlyOnce`, a second flush sends nothing.
- Disposing a Host logs `ObjectDisposedException` errors from Wolverine's DatabaseBatcher. They are noise.

## Spike S2 (#5, ADR 0006; WolverineFx 6.46.0, TypeLoadMode.Dynamic)

- Wolverine-generated handler code is compiled into an assembly with a random name (JasperFx.RuntimeCompiler 5.0.0 `AssemblyName ?? Path.GetRandomFileName()`), so a Wolverine handler type that names an `internal` type (even as a generic argument) fails with CS0122 at the first message, not at startup, and the message is dead-lettered. `InternalsVisibleTo("Internal.Generated")` does not help.
- `IMessageBus.EndpointFor(name).SendAsync` through an EF outbox to a durable local queue stores the row in `wolverine_incoming_envelopes` as `Outgoing`, owner 0; recovery only picks `Incoming`/owner 0, so it is lost after a kill. Use `PublishAsync` with a routing rule instead. **Only under an EF outbox:** from a handler's own `MessageContext` the durable local queue's `StoreAndForwardAsync` stores it `Incoming`, owned by the node, and it is recovered ([[integration-event-wire-and-rabbitmq-facts]], #51).
- `body` in the envelope tables is Wolverine's binary envelope, not UTF-8 JSON: `convert_from(body,'UTF8')` throws 22021; use `encode(body,'escape')` to regex it.
- `RetryWithCooldown` retries in memory; `attempts` stays 0 in the row, so counting restarts after a crash.
- Separated mode only separates when a message type has more than one handler; a lone handler goes to the message-type queue unless routed explicitly.
- Way around code generation: `opts.AddMessageHandler(type, new MyHandler())` with a `MessageHandler` subclass (WolverineOptions.cs:482). No codegen, so internal message types and handlers work; `OnException` policies still apply; middleware does not. ADR 0006 chose this (one `PublishMessage(type).ToLocalQueue(subscription)` route per subscription, subscription read from `Envelope.Destination`).
- Local queue names are lower-cased (`LocalTransport.QueueFor`); TCP destinations have host `localhost`, so map endpoint -> subscription by the endpoint (port), not by host.
- `InboxStaleTime` + in-memory `RetryWithCooldown` longer than it: the row is released, handed out again, and the in-memory retry still runs later, so a handler runs after it already succeeded. `ScheduleRetry` writes the row back as Scheduled, owner 0, attempts persisted, so it is skipped while waiting. Once promoted and running, it can be handed out again when its age from initial storage exceeds the stale time (`InboxStaleTimeTests`). `PouryaKitMessageStoreOptions.InboxStaleTime` must cover all retry delays plus every attempt's run and queue wait (ADR 0006, ticket #17 amendment).
- Default `UnknownMessageBehavior.LogOnly` marks a stored envelope Handled when its type has no handler any more (all subscriptions removed): silent loss. Set `DeadLetterQueue`.
- When counting owned lines for a comparison, count the file as it ran (whole-line removal of variant lines only), never an abridged snippet.

## Notification delivery (#15, 2026-10-05; WolverineFx 6.46.0)

- **Wolverine refuses to publish before its Host starts** (`WolverineHasNotStartedException` from `MessageBus.PublishAsync`). Any test Host that sends an Operation raising a subscribed Domain Event must be started (`HostFixture.StartHostAsync`) and stopped or disposed. Two Solo Hosts on one store worked side by side in the serial test run.
- **Timing:** `UseWolverine(lambda)` runs the lambda at registration; `IWolverineExtension`s from DI run when the `WolverineOptions` singleton is first resolved (after every Composition Root). The message store (`PersistMessagesWithPostgresql`) must be eager; routes, `AddMessageHandler`, failure policies and durability settings can sit in an extension, which is how Modules added after `UsePouryaKitWolverine` (AppFixture's Stub) still get routes.
- **Tests read the store, not a tracked session:** a Wolverine `TrackedSession` completes on `ExecutionFinished`, before a `ScheduleRetry` fires. Pending = incoming rows with status <> 'Handled' plus outgoing rows; `KeepAfterMessageHandling` (5 min) keeps handled rows for the baseline diff. Respawn must spare the store's own tables by name, not its whole schema (its node tables belong to the live Host; a Module may share the schema); delete envelopes and dead letters separately, after waiting until settled.
- **Redelivery trick:** `update wolverine_incoming_envelopes set status='Incoming', owner_id=0` on a handled row makes the recovery poll hand it out again (no dedupe; the no-receipt mutation doubled the effect). Rewriting `received_at` to an undeclared `local://name/` makes Wolverine build that queue on demand and the Kit throw `UnknownSubscriptionException`, which lands in `wolverine_dead_letters.exception_type`.
- **Between commit and flush:** a test-only decorator of `IUnitOfWorkOutbox` with an `AsyncLocal` probe (`tests/ModularMonolith.Tests/Fixtures/CommitProbe.cs`) reads commit timestamps or skips the flush; envelope rows are updated when handled, so compare `pg_xact_commit_timestamp(xmin)` before the flush.
- xUnit reports any exception implementing an interface named `IAssertionException`, in any namespace, as an assertion failure; `XunitException` lives in `xunit.v3.assert`, which `PouryaKit.Testing` does not reference.
- EF1002 (error under TreatWarningsAsErrors) flags an interpolated string passed straight to `ExecuteSqlRawAsync`. Building SQL in a local is appropriate only for trusted, appropriately quoted identifiers, as in `EfReceipts`; moving it to a local does not parameterise embedded values. Supply all values as parameters or use `ExecuteSqlInterpolatedAsync`.
- `IHostApplicationBuilder.UseWolverine` exists in 6.46; the Kit's entry is `builder.UsePouryaKitWolverine(connectionName: "app")`. `dotnet ef` with the Host as startup still works (the Host is built, never started).
- #15 fix round: Wolverine 6.46 creates the local queues `agents` (System, in memory), `default`, `durable`, `replies`, `scheduled`, `system` itself; a route to `agents` is never stored. `LocalTransport` is internal: read a queue's final `Role`/`Mode` with `runtime.Options.Transports.TryGetEndpoint(new Uri("local://name"))` after start (an `IHostedLifecycleService.StartedAsync` runs after every hosted service). An explicit `LocalQueue(name).BufferedInMemory()` wins over `UseDurableLocalQueues`.
- Dead-Host proof in-process: set `((WolverineRuntime)runtime).StopMode = StopMode.Quick` before `StopAsync`: no drain and no ownership release, as a kill leaves it. A Solo Host's start clears node records and releases *all* ownership, which recovers it.
- `Uri.TryCreate("x://12345/")`, a 64-char label, and 200-char names all round-trip as the host; only a trailing newline fails, and `^...$` regex accepts it (use `\A...\z`).
- #15 last round: a delivery helper must wait for a settled store before its baseline (a running handler's cascade lands later). The store's own tables come from `((IFeatureSchema)messageDatabase).Objects` (Weasel.Core.Migrations), so Respawn can spare them by name when a Module shares the store schema. A Host with its store in a Module schema needs its own database (separate HostFixture, one container, ~1.6 s).

## Dead letters and stale time (#17, 2026-10-05; WolverineFx 6.46.0)

Decompiled with `ilspycmd` into the scratchpad (`wv/`).

- **Stored retry past the stale time is handed out concurrently.** `ScheduleRetry` writes the row back `Scheduled`, owner 0; the scheduled poll promotes it with `owner_id = node` and never touches `timestamp` (insert time). Once a delivery is older than `InboxStaleTime`, every attempt that spans a recovery poll is released and handed out again. Reproduced with no row edits in `InboxStaleTimeTests` (stale 500 ms, retry 1 s, hold after Receipt, wait for a `Lock` wait on `pouryakit_receipts`); a 5-min stale time is the control (no copy). The Receipt keeps one effect. Rule: stale time > sum of `RetryDelays` + every attempt's run and queue wait.
- **Replay** = `runtime.Storage.DeadLetters.ReplayAsync(new DeadLetterEnvelopeQuery([id]))` sets `replayable`; the durability agent's recovery batch inserts it into incoming with the same id (status Incoming, owner 0, attempts 0) and deletes the dead letter. A test waiting for settle must count `replayable` dead letters as pending. Re-inserting a dead letter while its Handled row (kept 5 min) exists would hit the `(id)` primary key; `runtime.Storage.Inbox.MoveToDeadLetterStorageAsync(envelope, ex)` is the clean way to set a delivery aside again (it deletes the incoming row first); `DeadLetterEnvelope.Envelope` keeps its `Destination`.
- `DeadLetterEnvelopeQuery { PageSize = 0 }` reads every dead letter; `ReceivedAt = "local://{subscription}/"` finds a subscription's.
- **Receipts mask independence mutations.** "Run every subscription per envelope" still applies each effect once, so assert on delivery attempts (`DeliveryProbes.AttemptsOf(subscription, messageId)`, recorded in the `IReceipts` decorator), not only handler runs.
- **Dying Host in-process without a zombie:** hold the delivery after its Receipt, `pg_terminate_backend` the `idle in transaction` session on `pouryakit_receipts` (a kill closes it), `StopMode.Quick` + `StopAsync` (no drain, does not wait for the held task), then `ReceiptHold.Abandon()` (never release); releasing would run the handler in the dead Host's scope.
- Per-Host singleton logs miss runs in a second Host; process-wide statics keyed by a unique text (`Stub/StubCirculation.cs`) see all.

## Code generation for production (#58, 2026-10-07; WolverineFx 6.46.0, JasperFx 2.80.2)

- **Application assembly through a library.** Wolverine and JasperFx pick the first stack frame outside their own assemblies; called through `UsePouryaKitWolverine` that is `PouryaKit.Messaging.Wolverine` (`dotnet run -- describe` shows `(application)` and the ServiceName). `TypeLoadMode.Static` loads generated types and the handler registry from `CodeGeneration.ApplicationAssembly` only, so the Kit sets `WolverineOptions.ApplicationAssembly = Assembly.GetEntryAssembly()`. Setting it on WolverineOptions (not JasperFxOptions) leaves the ServiceName as before.
- **Static start check** is `HandlerGraph.AssertPreBuiltTypesExist` at `StartAsync` (before `tryMigrateStorage`), chains only; a missing registry only warns. `AssertAllPreGeneratedTypesExist` is JasperFx's environment check: `check-env` fails on the missing `HandlerRegistryCodeFile`. `check-env --file x` writes which check failed; the console says only "Some environment checks failed!".
- **`codegen write`** builds, never starts the Host, and needs no `IAssemblyGenerator` (only `codegen test` does), so a Release build without the compiler can run it. For a Kit Host it writes `Internal/Generated/WolverineHandlers/GeneratedHandlerRegistry.cs` alone (empty arrays plus an AotRoots class).
- **Debug-only PackageReference trap:** `dotnet restore` (Debug evaluation) then `dotnet build -c Release --no-restore` puts `Wolverine.RuntimeCompilation.dll` and `JasperFx.RuntimeCompiler.dll` in the Release bin; restore with `-p:Configuration=Release` before a publish. A Release-built Host cannot run Development at all (the Dynamic guard throws), so any child process started from a Release test build must run Production.
- **WebApplicationFactory + `RunJasperFxCommands`:** the factory passes its settings as `--key=value` args; JasperFx's `ArgPreprocessor` splits on every `=`, so the parse fails ("Unknown argument or flag"). Without `JasperFxEnvironment.AutoStartHost = true` the Host never starts; with it JasperFx starts the Host before parsing and the failed parse is only console noise. Wolverine's `docs/guide/http/integration-testing.md` asks for it.
- Until #64 `/alive` answered 401 in Production (ServiceDefaults mapped both health endpoints in Development only). Since #64 it is mapped in every environment; `/health` stays Development-only, so in Production it answers 401 in a Host with the Web defaults (the fallback policy covers the unmatched path) and 404 in one without ([[observability-tracing-and-http-facts]]).

## The Outbox's connection and recorded probes (#54 test gaps, 2026-10-08; WolverineFx 6.46.0, ASP.NET Core 10.0.12)

- **The Outbox write runs on the Module DbContext's own connection and transaction** (`EfCoreEnvelopeTransaction.PersistIncomingAsync`; the Kit's DbContexts map no Wolverine entities), in the store's schema. So a Module on another database than the store: the Host builds and starts, the first Operation that writes to the Outbox throws `PostgresException 42P01 relation "wolverine.wolverine_incoming_envelopes" does not exist`, nothing commits. If the Module's database still holds a copy of the store's tables (a moved store, or another Host's store), the write succeeds there silently, deliveries run once from the in-memory flush, and the rows stay `Incoming` where no store reads them. Raised with the owner (a build-time cross-check of connections); the probe is commit `3861dc9`.
- **A probe that records a deployment rule**: write it as an output-only Theory, commit it, remove it in the next commit, cite the first sha in `docs/acceptance.md`. Two fresh databases on the AppFixture's container (`create database`), never a new `HostFixture` (it starts its own container) and never the fixture's own database (its live store would absorb writes).

## Sent broker envelopes (Wave 2 final review D, 2026-10-08; WolverineFx 6.46.0)

Decompiled under the session scratchpad `decomp58/wolverine`.

- **An outgoing broker envelope is deleted once sent**, so a store read after the Operation misses it. Wolverine calls `IMessageTracker.Sent` when a sending agent takes the envelope (`SendingAgent.EnqueueOutgoingAsync`/`StoreAndForwardAsync`), inside the Unit of Work's awaited flush, before the broker send and the row delete. `WolverineRuntime.Sent` always adds 1 to the `wolverine-messages-sent` counter (`MetricsConstants.MessagesSent`) on `IWolverineRuntime.Meter`, a Meter per runtime, tagged `message.type` and `message.destination`. A `MeterListener` filtered by `instrument.Meter == runtime.Meter` sees one Host only. System endpoints use the `SystemTraffic` tracker (no counter); durable local queue sends are counted too (filter `local:`).
- **A latched sender hands nothing out**: `Envelope.QuickSendAsync` (the DbContextOutbox flush path, `Transaction != this`) calls `MarkProcessingFailureAsync` instead of `EnqueueOutgoingAsync` when `Sender.Latched`, so no `Sent`; the outgoing row stays. Both reads are needed. `SendingAgent.PauseAsync(TimeSpan)` (public; agent from `runtime.Endpoints.GetOrBuildSendingAgent(uri)`) latches it as an unavailable broker does, then resumes.
- `TrackedSession`/`ActiveSession` are internal; `TrackActivity().ExecuteAndWaitAsync` waits for handlers. `IWireTap` needs per-endpoint `UseWireTap()`.
- **A HostFixture with a broker:** a private subclass taking `environment.Broker`, `CreateHost` = `AppFixture.ComposeHost(..., $"--ConnectionStrings:broker={broker}")`, created and `InitializeAsync`'d in the test (own PostgreSQL, about 3 s). `RenameProductCommand` there writes only the Snapshot's broker envelope (`catalog.product-snapshot.v1` to `rabbitmq://exchange/catalog.product-snapshot.v1`). To force "sent and deleted before the Operation returns", await `WaitUntilDeliveredAsync` inside the operation lambda.
- **Mirror defect left open:** `WaitForDeliveriesAsync` still throws "sent nothing" on an outgoing-only publication.
- **One record per Unit of Work DbContext:** `AddPouryaKitEfCore<T>(connectionName = null)` records `DbContextConnection(string? Name, Type)` once; `UsePouryaKitPostgres` passes its name. Since the D fix round a name replaces an unnamed record (index set, `services[services.IndexOf(d)] = ...`, safe through `ModuleBuilder`) and two names throw. The missing-string check (`DbContextConnectionsCheck`, Persistence.EFCore) must skip a null name (`GetConnectionString(null)` reads `ConnectionStrings:` and reports a false missing line).
- **A check that guards a record is registered where the record is made** (D review F1, high): the record was public-API reachable (`AddPouryaKitEfCore(name)`) but its check was registered only by `UsePouryaKitPostgres`, and the other check skipped the case trusting it. When one check skips a case "because check X reports it", prove X is registered on every path that creates the case.

## The Eager line and the recovery timers (#82, 2026-10-10; WolverineFx 6.48.3)

- **`UseEntityFrameworkCoreTransactions(Eager)` was removed** (full suite green without it): it registers only what generated chains and callers of the scoped `IDbContextOutbox<T>` use, and the Kit has neither. Its removal orphans `using Wolverine.EntityFrameworkCore;` and `using Wolverine.Persistence;` (IDE0005).
- **Two timers, one block:** the recovery batch (`CheckRecoverableIncoming`, outgoing, replayable dead letters, then `BumpStaleIncomingEnvelopes`) and the scheduled-message poll run on separate timers, both at `ScheduledJobPollingTime`, posted to the durability agent's one running block. Decompiled 6.48.3 sources sit in the session scratchpad `p82/` (`rdbms`, `pg`, `core`, `efcore`, `hybrid`).

## Option validation at start (#83, 2026-10-10; WolverineFx 6.48.3)

- **An empty `RetryDelays` was never valid.** `PouryaKitWolverineExtension` passes it to `OnException<Exception>().ScheduleRetry(...)`, and Wolverine's `FailureActions.ScheduleRetry` throws `InvalidOperationException: You must specify at least one delay time` when `StartAsync` builds Wolverine's options. Spec #74 and the #83 ticket listed an empty schedule as a valid positive case; the session kept the validation to null and negative and recorded the empty case as an owner question. Run a "valid value" positive case on the unmodified tree before writing a validator around it.
- **Messaging and store options fail at the first read, not at `ValidateOnStart`.** Both `IWolverineExtension`s read `IOptions<T>.Value` when `StartAsync` resolves the hosted services, before `IStartupValidator` runs, and `IOptions<T>.Value` runs the validators itself: the test sees the same `OptionsValidationException`, unwrapped. So a red run removing only `ValidateOnStart()` stays green for those two; the switch that proves the guarantee is the `Validate` call.
- **#95 (2026-10-10) refuses the empty schedule** with a third `Validate` (`RetryDelays is null || RetryDelays.Length > 0`) between the null and the negative check. `OptionsBuilder` runs every `Validate` and reports every failure, so each predicate after the null check lets null through, or the null row reports two failures (the theory asserts exactly one). With that `Validate` removed, only the empty row goes red, with Wolverine's `InvalidOperationException` at `StartAsync`.
- **A Host with only `UsePouryaKitWolverine(connectionName)` fails at `Build()`** under the Kit's validating container: `EfReceipts` needs an `IUnitOfWork`. Test message store options through `AppFixture.ComposeHost`, whose `StartAsync` fails before the store is reached; the broker-less `UsePouryaKitWolverine()` Host starts with no database and no Unit of Work.

## Two different Hosts on one store schema (#96, 2026-10-10; WolverineFx 6.48.3)

- **Unsupported upstream, documented, not checked.** `JasperFx/wolverine` #4923 (open): two different applications on one envelope-store schema in Balanced mode, and a node without the handlers recovers the other's inbox rows and dead-letters them (the Kit sets `UnknownMessageBehavior.DeadLetterQueue`). The owner ruled out a runtime guard on 2026-10-10: Wolverine's node row has no application identity. The rule lives in four places that must stay in step: the `Durability` summary of `PouryaKitMessageStoreOptions`, the skill's `messaging.md` ("The message store", the `Durability` bullet and the schema bullet), the architecture README's `UsePouryaKitWolverine(connectionName, schema ...)` paragraph and ADR 0004's #96 amendment. The skill's `rabbitmq.md` has the matching broker rule (one service name per kind of Host).
- **The acceptance grep keeps the old phrase.** The ticket's check greps "any number of Host instances on one store" over `src/`, the skill, `docs/architecture/` and `docs/acceptance.md` and accepts only lines that continue with the exclusion, so keep the phrase and the exclusion on one physical line (the `.cs` summary wraps), and never quote the phrase in `docs/acceptance.md`.
- No test covers two applications on one store: `SharedStoreSchemaTests` is one Host whose store shares its Module's schema, `MessageStoreDatabaseTests` one Host's DbContexts against its own store, and `BrokerFixture` gives each Host its own database. A doc change to an XML summary under `src/` is not exempt from `validate.py --since`, so it runs in full.

## Which dead-letter branch a Kit Host takes (#90, 2026-10-10; WolverineFx 6.48.3)

- **Every listener of a Kit Host takes `DurableReceiver`'s native dead-letter branch**, the RabbitMQ Host queue included: a durable listener calls `pipeline.InvokeAsync(envelope, durableReceiver)` (`DurableReceiver.cs:133`), so `MessageContext`'s channel is the receiver, which reports `NativeDeadLetterQueueEnabled => true` (`:95`). `MoveToDeadLetterQueueAsync` then calls `MoveToErrorsAsync`, which sends to `endpoint.TryBuildDeadLetterSender`'s sender when there is one, else `_inbox.MoveToDeadLetterStorageAsync` (`:217-229`). The base `Endpoint` builds none; `RabbitMqQueue` builds one only in `DeadLetterQueueMode.Native` (read in WolverineFx.RabbitMQ 6.48.3, the pinned version; the reviewer confirmed it reads the same), which `DisableDeadLetterQueueing()` turns off. The other branch, with `IDeadLetterInterceptor`, never runs for a Kit Host; ADR 0006's #60 amendment described it until #90's note. A reviewer's "the Kit applies that branch at the RabbitMQ queue" missed that the channel is the receiver, not the listener.

## A second registration, unknown types and the dead-letter row (#100, 2026-10-10; WolverineFx 6.48.3)

- **A second `UseWolverine` throws**: `AddWolverine` refuses with `InvalidOperationException`, "IHostBuilder.UseWolverine() can only be called once per service collection", when `IWolverineRuntime` is registered (`Wolverine/HostBuilderExtensions.cs:127-130`). A second `UsePouryaKitWolverine` therefore throws at its last line, after adding the Kit's two `IWolverineExtension`s again (probe: 2 before, 4 after); `TryAddEnumerable` would not make it "add nothing".
- **Red-once lever for an unknown type's dead letter:** `builder.Services.RemoveAll<IMissingHandler>()` in `AppFixture.ComposeHost`'s configure hook works, since `UseWolverine`'s lambda runs at registration and the `UnknownMessageBehavior` setter `TryAddSingleton`s `MoveUnknownMessageToDeadLetterQueue` into the Host's own services. The interface is `Wolverine.IMissingHandler`, not in `Wolverine.ErrorHandling`.
- **`wolverine_dead_letters` has no `attempts` column.** Read a dead letter's attempts from its body: `EnvelopeSerializer.Deserialize((byte[])row["body"]).Attempts`. On the unknown-type path it stays 0: `HandlerPipeline.TryDeserializeEnvelope` returns `NoHandlerContinuation` before any executor counts an attempt.
- **Two Hosts in one test, the 53300-safe shape:** `await using (var a = AppFixture.ComposeHost(...)) { start; act; stop; }`, then the next Host in its own block; a `Scheduled` row due 2 s after the send outlives the first Host's stop.
- **A plain sample Host for a container test:** `ModularMonolithHost.Build(ModularMonolithHost.CreateBuilder(["--environment", "Development", $"--ConnectionStrings:app={Fixture.ConnectionString}"]))` builds without AppFixture's probes, and an unstarted Host's scope resolves `IUnitOfWorkOutbox` and `IOutbox` (`UnitOfWorkTests`).

**Why:** these decide how delivery is built, and each cost an investigation or would make a delivery test pass vacuously; the application-assembly fact would have made Static mode useless for any application handler.
**How to apply:** check these before writing Kit delivery code or tests that read Wolverine tables; also for dead letters and replay, any change to Hosts, `Program.cs` or the Wolverine registration, any check of the store's connection, any recorded probe, and any negative delivery assertion or broker-unavailable test. Related: [[snapshot-and-scheduled-command-facts]], [[integration-event-wire-and-rabbitmq-facts]], [[composition-check-facts]].
