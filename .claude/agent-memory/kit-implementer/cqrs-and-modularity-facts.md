## Cqrs and Validation (#7, 2026-10-05; FluentValidation 12.1.1)

- FluentValidation 12.1.1 is `Apache-2.0` on nuget.org (published 2025-12-03), no dependencies on net8.0+. The core package has `AssemblyScanner.FindValidatorsInAssembly(assembly, includeInternalTypes: true)`, so no `FluentValidation.DependencyInjectionExtensions` (not allowed by section C) is needed.
- Building a failed `Result<T>` for any `T` needs no Domain change: inside a class that knows `TResult`, `static errors => errors` typed `Func<ImmutableArray<Error>, TResult>` uses Domain's implicit conversion for both `Result` and `Result<T>`.
- `IUnitOfWork.RunAsync` is non-generic (`Func<CancellationToken, Task<Result>>` to `Task<Result>`); the dispatcher maps the outcome back with `outcome as TResult ?? fail(outcome.Errors)`.
- Design calls made in #7 and reported as deviations (check the merged code before relying on them): rolled-back Operation fails with the first failed nested command's Errors; one outermost command per scope (second throws); a nested command exception marks rollback-only with `Operation.CommandThrew`.
- Fix round (2026-10-05): the Operation now tracks whether the Unit of Work is active separately from command depth. A command sent from an authorizer or validator (before `RunAsync`) throws; queries there are fine. `IAuthorizer`/`IValidationStep` are invariant, and registration rejects authorizers not for one concrete operation.

## Domain Event drain (#10, 2026-10-05)

- The drain lives in `PouryaKit.Cqrs` (`DomainEventDrain`, public, internal ctor, registered by `AddPouryaKitCqrs` with a factory) because `Operation.MarkRollbackOnly` is internal to Cqrs and EFCore has no InternalsVisibleTo. EF only supplies `ChangeTracker.Entries<IAggregateRoot>()`. A failed handler marks the Operation rollback-only, so `IUnitOfWork`'s contract ("command's failure or RollbackErrors") held unchanged; first failure wins.
- During the drain the outer command is still inside `Run` (`_runningCommands == 1`, UoW active), so a handler's nested command joins the same Operation and Unit of Work; command depth and failed-command rollback propagation still apply.
- Dispatcher backstop: a Unit of Work success while `IsRollbackOnly` throws `InvalidOperationException` (it may already have committed, so a failed Result would lie).
- Mutation tricks: a handler with `await Task.Yield()` exposes `Task.WhenAll`; declaring handlers out of name order exposes a dropped sort; a "must not run" handler that throws exposes a drain that does not stop; a raw-SQL insert inside the transaction makes "0 rows" prove a rollback (EF-added rows never reach the DB); the cycle test needs `[Fact(Timeout=...)]` plus a real `Task.Delay(…, ct)` in a handler, or a removed depth guard hangs instead of failing.

## Modularity and the Operation Context (#13, 2026-10-05)

- **Startup validation needs `Microsoft.Extensions.DependencyInjection`** (since #61 referenced by Cqrs, whose `AddPouryaKitCompositionChecks` installs the validating factory; Modularity no longer references it). `ServiceProviderOptions` (ValidateOnBuild, ValidateScopes) and `DefaultServiceProviderFactory` live in the implementation package; `Microsoft.Extensions.Hosting.Abstractions` 10.0.12 (net10.0) depends only on *.Abstractions packages, and `HostApplicationBuilder` enables validation only in Development with no configuration key. The owner approved the reference for Modularity on 2026-10-05 (beyond section C); `AddPouryaKitModules` calls `ConfigureContainer(new DefaultServiceProviderFactory(...))`. A validation failure surfaces from `Build()` as an `AggregateException`.
- **The scope's Module lives on Cqrs's `Operation`** (`Operation.Module`, set with the Context by `IServiceProvider.BeginOperation(context, module)`); `ModuleTag` is gone. Delivery adapters (#15/#16) begin their scope the same way without Modularity.
- **Changing a public signature that parallel tickets call breaks their merge.** The Gateway gained a required `OperationContext`; C# 14 extension members in `PouryaKit.Testing` (`GatewayTestExtensions`) keep the old `SendAsync(cmd, ct)` form compiling: an instance method that is not applicable falls through to the extension.
- `Microsoft.Extensions.Hosting.Host` collides with the namespace `ModularMonolith.Host` inside `ModularMonolith.Tests`; qualify it fully.
- Host-wide composition state (Modules added, which Module owns each operation) is kept as a singleton `ImplementationInstance` in the service collection, found-or-added, because `AddPouryaKitModules` is called more than once per Host (the test fixture adds the Stub Module in a second call).
- A test can observe the context of another Module's Operation without changing that Module: an `IAuthorizer<ThatQuery>` in the test assembly is picked up by the Stub Module's assembly scan and runs in the other Module's scope.
- The Gateway ownership check refuses a test-assembly command sent through a sample Module's Gateway (the Stub scan registers it). To run such a probe in Catalog's Unit of Work, begin a scope with `BeginOperation(context, typeof(CatalogModule))` and send it through `IDispatcher`, as a delivery step does (RepositoryTests).
- Ownership is exclusive (#13 fix round): `ModuleBuilder` reports Add/Insert/indexer-set to `HostModules.Record` and Remove/RemoveAt/Clear/indexer-set to `Release`; a second Module touching an owned handler throws. A different handler arriving through `AddPouryaKitCqrs` hits Cqrs's `has 2 handlers` first; the same handler class scanned by two Modules is skipped by Cqrs, so no descriptor or ownership change happens (the first Module keeps it, the container agrees).
- `IHostApplicationBuilder.ConfigureContainer` from `AddPouryaKitModules` also turns validation on for a `WebApplicationBuilder` Host (checked with a Production web Host).

## Declared authorizer check (#56, 2026-10-07)

- **Security code does not run in every Host.** `AddPouryaKitPermissions` runs only where a Composition Root calls it (the failure case is exactly the one that did not), and the Host's `IActorPermissions` is a plain `AddScoped`. The only Kit code every Host runs after all Composition Roots is Modularity, which may not reference Security (plan section C). So the declaration travels on the attribute through a Cqrs contract, `IRequiresAuthorizer`, and the check reads it (in `HostModules` at #56, in Cqrs since #53, below).
- **Build-time hook:** `AddPouryaKitModules` passes `ModularServiceProviderFactory` (wraps `DefaultServiceProviderFactory`) to `ConfigureContainer`; its `CreateServiceProvider` sees the Host's final, still writable collection. A check at the end of `AddPouryaKitModules` would be wrong: the fixture adds Stub in a second call, and a later call may register the authorizer.
- **`ServiceDescriptor.ImplementationType` throws on a keyed descriptor.** Filter `IsKeyedService` first, in Kit code and in test helpers that walk the collection.
- **Resolving `IAuthorizer<T>` from a bare scope throws** ("No Operation Context was set"): `PermissionAuthorizer<T>` injects `OperationContext`. Prove a registered check by sending through the Gateway on a built, unstarted Host (an Actor without the permission gets `PermissionErrors.Denied`).
- Remove only the permission check in a test: descriptors of `IAuthorizer<T>` whose `ImplementationType.Assembly` is Security's; the Stub's own `RefuseSomeStampsAuthorizer` stays and must not satisfy the check (mutation "any authorizer counts" goes red that way).
- **Superseded by #61 (2026-10-07):** the check is now Cqrs's internal `DeclaredAuthorizersCheck`, a composition check `AddPouryaKitCompositionChecks` runs when the container is built; `EnsurePouryaKitDeclaredAuthorizers()` and Modularity's factory are gone ([[composition-check-facts]]).

## Continuation trust (#57, 2026-10-07)

- **Accessibility alone cannot give a cross-package Kit-only setter.** Security reads the mark, so it needs a public getter. Delivery (Messaging.Wolverine) and Web (#48 trusted peer) set it, so they need some entry point. Without `InternalsVisibleTo`, any API they can reach, an application can reach too. An in-process secret does not help, because application code can read configuration and DI. The orchestrator chose Cqrs's one IVT, to Messaging.Wolverine and Web only, for `OperationContext.RestoreTrusted`. `TrustedRestoreTests` pins the list and the internal members the IL may use.
- **G.6 wins over "never trust Continue()".** In the first round I made `Continue()` never trusted. The dual review rated that high: G.6 makes work created by an authorized Operation a trusted continuation, and the sample's `CatalogProducts` question depends on it. The rule now: trusted only on the exact context the dispatcher runs past its checks, called from inside that Operation (`AuthorizedOperation`, an ambient check set in `Dispatcher.Steps`). "Begun" is too weak, because `BeginOperation` is public. A handler continuing into protected work is G.6, a documented limit, not a gap.
- **Testing the ambient check:** checks clearing is vacuous on the outermost Operation, because its checks run before anything is set. Probe from the authorizer of a query *nested* in the authorized one. To prove the end bound, start a `Task.Run` inside the handler that waits on a TCS the test completes after the Gateway returns; `Task.Run` captures the ambient entry. A mutation that leaves a field unread breaks the build (CS0414 under TreatWarningsAsErrors), so mutate the assignment instead.
- **The dispatcher never calls `Continue()`.** A nested command shares the scope's context. Both #38 continuation tests go through delivery. The trust is set in `OperationContextHeaderExtensions.ContinuedOperationContext`, not in `SubscriptionDelivery`.
- `public bool X { get; private init; }` on a record plus an internal factory using `{ X = true }`: `with` from outside can only clone it, and STJ ignores a non-public init. `Actor`'s private constructor makes `OperationContext` non-deserializable anyway.
- IL rule for "uses no internal of assembly A": judge a constructed generic type by its definition. `CommandHandler<InternalCommand>` has `IsVisible == false`, and judging it as constructed is a false positive.

## Cqrs's internals, the Unit of Work window and same-named types (#66, 2026-10-08)

- **The `InternalsVisibleTo` of Cqrs compiles more than it allows.** `TrustedRestoreTests` reads the IL of `PouryaKit.Messaging.Wolverine` and `PouryaKit.Web` and fails for any call to an internal member of Cqrs but `OperationContext.RestoreTrusted` (ADR 0007). A brief or a scout that says "Messaging.Wolverine sees it through the IVT" is right for the compiler only: check that test before building on an internal of Cqrs, and ask the session when the member is needed. `Operation.IsUnitOfWorkActive` became public that way (the session's decision), and no other package is in the list at all (Caching, Persistence.EFCore).
- **`Operation.MayChangeState` is true before `Begin` and in a begun scope that sends no command**, so it does not mean "inside a Unit of Work"; `IsUnitOfWorkActive` does (set around the dispatcher's `IUnitOfWork.RunAsync` call only). A guard on a write a Unit of Work must commit checks `MayChangeState` first (the specific "only reads" message), then `IsUnitOfWorkActive`, then anything that reads `operation.Module`, which is null in an un-begun scope and gives a misleading ownership message.
- **Two types of one full name in one process:** keep both `internal`, each in its own assembly, and give the second assembly a public static factory that returns the base type (`Query<string>`, `Command<string>`); the dispatcher finds the handler by the runtime type. A public twin gives CS0433 at every mention. A bare `ServiceCollection` with `UsePouryaKitPostgres<StubDbContext>("app", "stub")`, `AddPouryaKitCqrs(stubAssembly, twinAssembly)` and `AddPouryaKitCaching()` is one application with one cache and one key table (`tests/ModularMonolith.Tests/SameNamedTypeTests.cs`); changing `StubModule`'s scan would ripple into every composition check of the fixture Host.
- **A type in a key is `FullName, assembly simple name`** in both the idempotency key and the query cache key (ADR 0002's #66 amendment), written at both call sites since they share no internal. `PouryaKit.Cqrs.Tests.IdempotencyTests` asserts the dispatcher's form in its trace lines.

**Why:** each cost investigation or is a seam later tickets build on: #8 to #16 on Cqrs and Modularity, #11 and #15 on the drain, #44 and #48 on continuation trust; #57 cost two rounds.
**How to apply:** when touching Cqrs, Validation, the Unit of Work, Domain Event Handlers, Modularity, Testing or the Gateway API; re-verify the licence when bumping FluentValidation; before adding a reference, check the package's nuspec dependency group. When adding another Kit attribute that requires a registration (reuse `IRequiresAuthorizer`) or testing authorizers. Delayed continuations must come back through `ContinuedOperationContext`, a trusted peer calls `RestoreTrusted`, and so does any later Kit-only cross-package seam or ambient check.
