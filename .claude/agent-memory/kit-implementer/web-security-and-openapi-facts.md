## Web and ASP.NET Core (#14, 2026-10-05; ASP.NET Core 10.0.12)

- **Minimal APIs bind service parameters before endpoint filters run**, so a filter cannot begin the scope's Operation in time for an endpoint that injects `OperationContext`. Web wraps the built `RequestDelegate` in a route-group `Finally` convention instead (runs after RequestDelegateFactory sets it). `Finally` is a default interface member: cast `RouteGroupBuilder` to `IEndpointConventionBuilder` to call it.
- **.NET 10 exception handler middleware does not log an exception an `IExceptionHandler` handled**; the handler must log it. Aborted requests (OperationCanceledException + RequestAborted) are answered 499 by the middleware before handlers run.
- With `RequireAuthorization` removed but the begin step kept, an anonymous request answers 500 (no Actor), not 200: a mutation test still fails, but read the status before claiming why.
- `HostFixture.CreateHost` returns `IHost`, which a `WebApplication` is: `builder.WebHost.UseTestServer()` plus `Host.GetTestClient()` (Microsoft.AspNetCore.TestHost) gives an HttpClient with no `PouryaKit.Testing` change. A second `AddAuthentication("Test")` call after the Host's overrides the default scheme.
- A test `AuthenticationHandler` subclass cannot declare a member named `Scheme` (CS0108 under TreatWarningsAsErrors).
- Typed IDs serialize as `{"value":...}` unless the HTTP options carry the Kit converter; since #34 `AddPouryaKitWeb` applies `UsePouryaKitJson` ([[core-json-and-architecture-test-facts]]).
- Check `dotnet ef` without writing into a Module's migrations: `dotnet ef dbcontext info --project src/Modules/Catalog/Catalog --startup-project src/ModularMonolith.Host --context CatalogDbContext` from `samples/ModularMonolith`.
- #14 fix round: `WebApplication` inserts routing/authentication/authorization ahead of app middleware, so `UseExceptionHandler()` must come first with the other three called explicitly. Outside Development a bind failure answers an empty 400; `PostConfigure<RouteHandlerOptions>(ThrowOnBadRequest = true)` sends it to the exception handler in every environment. `IProblemDetailsService.TryWriteAsync` declines when `Accept` excludes JSON; `ProblemHttpResult.ExecuteAsync` falls back to writing `application/problem+json`, so write exceptions through it too. The authorization middleware reads endpoints when the Host starts, so an endpoint-build convention that throws fails `StartAsync`.
- A test needing a different composition builds its own Host (`AppFixture.ComposeHost(environment, ...)`) and starts it without migrating; Modules touch the database only on use. A test-only endpoint that must not exist in the shared Host maps itself only when a marker service is registered.
- Sdk.Web globs appsettings*.json as content; an explicit `<Content Include="appsettings.json">` would duplicate it.

## Web defaults: CORS, compression, the limiter (#36, 2026-10-07; ASP.NET Core 10.0.12)

Verified by decompiling the shared framework with `ilspycmd -t <Type> <dll>` (write each to the scratchpad; one plain command per call, a variable in the path is refused).

- **`RequireCors(name)` on a minimal API endpoint answers no preflight.** `RouteEndpointDataSource` adds `HttpMethodMetadata(methods)` with `acceptCorsPreflight: false`, so an `OPTIONS` preflight routes to the 405 endpoint, which has no CORS metadata; with a fallback policy it then answers 401. Only a pipeline policy (`app.UseCors(name)` or a default policy) answers preflights. The Kit's sample uses `UseCors(BrowserPolicy)`.
- **Response compression cannot be present and inert.** `ResponseCompressionProvider` falls back to Brotli + gzip when `Providers` is empty and to `ResponseCompressionDefaults.MimeTypes` (JSON yes, `application/problem+json` no) when `MimeTypes` is empty. So the Kit adds `UseResponseCompression()` from an `IStartupFilter` only when enabled. Both providers already default to `CompressionLevel.Fastest`.
- **`ProblemDetailsDefaults` has no 429 entry:** a 429 problem response has `title` "Too Many Requests" and `status`, but no `type`.
- A rate limiter rejection with `RejectionStatusCode` set and no `OnRejected` leaves the body empty, so `ProblemStatusCodePages` writes the problem response: no second writer. `UseRateLimiter()` with no `GlobalLimiter` and no endpoint policy passes through; `UseCors(name)` with an unknown name passes through.
- `CorsService` reads `IOptions<CorsOptions>.Value` when the pipeline is built, so a `CorsOptions` configure that depends on validated Kit options fails `StartAsync` even without `ValidateOnStart` (the mutation stayed green; mutate the validator instead).
- `IStartupValidator` (ValidateOnStart) runs before hosted services, so a misconfigured test Host throws `OptionsValidationException` from `StartAsync` with nothing of Wolverine started.
- A test Host gets its own configuration through `AppFixture.ComposeHost(..., builder => builder.Configuration.AddInMemoryCollection(...))`: options bound with `Configure<T>(section)` read it when built. TestServer with an `https://` base address makes `Request.IsHttps` true, and the test client does not decompress.
- **Review F1: "partition by the Actor" means the Actor the Operation runs as**, not the raw claim: an `AllowAnonymousAs` endpoint's named Actor for anonymous callers, the continued Actor for a trusted peer. One internal `HttpCallerContext.Resolve` now feeds both the endpoint's `BeginOperation` and the partitioner (the limiter reads the endpoint's metadata through `GetEndpoint()`, since it runs after routing); it returns null instead of throwing for an unresolved caller, and the partitioner catches only the `BadHttpRequestException` of a peer's unreadable headers. Any later "by the Actor" feature (caching keys, idempotency) should reuse it.
- **The limiter's `BadHttpRequestException` catch cannot be shown by the status**: without it the exception escapes `UseRateLimiter` and `UnexpectedExceptionHandler` still answers 400. The discriminator is accounting: with the catch the call counts in the unresolved partition, so a second such call at permit 1 answers 429.

## Security and permissions (#38, 2026-10-07; ASP.NET Core 10.0.12)

- **The authorization `FallbackPolicy` also governs a path no route matches** (no endpoint at all): an anonymous request answers 401 instead of routing's 404; an authenticated one still 404. Pinned in `SecurityTests`.
- **Test a non-Module endpoint** by `AppFixture.ComposeHost(...)`, then `host.MapGet(...)` after `ModularMonolithHost.Build` and before `StartAsync`. Module route groups already `RequireAuthorization()`, so a fallback-policy test on a Module endpoint never goes red.
- `services.Configure<AuthorizationOptions>(o => o.FallbackPolicy ??= ...)` is the registration-time form; it keeps an application's own fallback set earlier and loses to one set later.
- **Permission source vs Gateway tests:** an `IActorPermissions` that reads `IHttpContextAccessor` grants nothing outside a request, so every Gateway test sending the protected command (as `GatewayTestExtensions.TestActor`) would be Forbidden. Pick the command whose existing call sites all run as TestActor (`RemoveProducts`, not `RenameProduct`, which one audit test sends as Person "bob"), and grant TestActor that one permission by name in a fixture-only wrapper (`TestActorPermissions`).
- Module commands are `internal`, so the Host cannot register a per-type authorizer: `AddPouryaKitPermissions(assembly)` goes in each Composition Root, as `AddPouryaKitValidation` does. A generic authorizer in the Security assembly is invisible to `AddPouryaKitCqrs`'s concreteness check.
- A Stub endpoint can drive a Catalog command over HTTP through `IGatewayProcessor<CatalogModule>` (InternalsVisibleTo); the Gateway ownership check accepts it because the command is Catalog's.

## JWT bearer (#39, 2026-10-07; Microsoft.AspNetCore.Authentication.JwtBearer 10.0.12)

- **The framework's config binder replaces `TokenValidationParameters`** whenever `Authentication:Schemes:Bearer` has children (`JwtBearerConfigureOptions`, decompiled with `ilspycmd -p -o <dir> ~/.nuget/packages/microsoft.aspnetcore.authentication.jwtbearer/10.0.12/lib/net10.0/*.dll`). It runs before the `AddJwtBearer(delegate)`; `SigningKeys[n]` is kept only when its `Issuer` string-equals `ValidIssuer`/`ValidIssuers`. `JwtBearerPostConfigureOptions` copies `Audience` to `ValidAudience` and builds a `ConfigurationManager` from `Authority`, so a validator must run after post-configure (an `IValidateOptions` does).
- **`ValidateOnStart` on the Bearer options fails every Host `AppFixture.ComposeHost` builds**, even with `TestAuthentication` the default scheme: `ComposeHost` passes `TestIssuer.HostArguments` on the command line. `StartAsync` throws a single `OptionsValidationException` before hosted services start, so start-failure theories are cheap (~70 ms).
- **A second started Host shares the durable local queues.** A test that creates data through the fixture, then starts its own Host, can have that Host take a delivery and be disposed holding it; the next test's `ResetAsync` waits 30 s and times out, cascading. Only showed in the full run, never with `--filter-class`. Fix: `Fixture.WaitUntilDeliveredAsync` before starting and before disposing the second Host.
- Mutations: to red the 401 rows, bypass the validator and set `ValidateIssuer/ValidateAudience/ValidateLifetime/RequireSignedTokens = false` plus a `SignatureValidator` returning `new JsonWebToken(token)`; without `RequireSignedTokens = false` every token fails with IDX10253. `if (false)` mutations fail the build (CS0162 under TreatWarningsAsErrors); use `if (name.Length < 0)`.
- **Review F1-F4 (fix round):** a flags-only start check is not enough. In IdentityModel 8.19.2 a set `AudienceValidator`, `IssuerValidator(UsingConfiguration)`, `LifetimeValidator` or `SignatureValidator(UsingConfiguration)` runs *instead of* the default check (`IssuerValidatorAsync` is internal), and `RequireAudience = false` accepts a token with no `aud`. A later app `PostConfigure` that assigns `Events`, or a `JwtBearerEvents` subclass overriding `TokenValidated`, silently drops a normalization installed by `PostConfigure`. Fix: the installed delegate is an instance method of the internal `VerifiedClaims`, and the start check requires `Events.GetType() == typeof(JwtBearerEvents)` and `OnTokenValidated.Target is VerifiedClaims`.
- **Re-review F5:** IdentityModel 8.19.2 also has `IssuerSigningKeyResolverUsingConfiguration` (checked before `IssuerSigningKeyResolver`); it counts as a key source in the start check. A test of it must clear `IssuerSigningKey(s)` in a `Configure` after the binder, else the bound `SigningKeys` pass the token. Red the claim drop in `VerifiedClaims` with `.Where(_ => names.ActorClaim.Length < 0)`: Web then reads the token's own `NameIdentifier` and `pouryakit:tenant`.
- `RestoredPackage.Frameworks` holds direct framework references only: the JwtBearer package's transitive `Microsoft.AspNetCore.App` does not appear, so the PackageGraph row needs no framework.

## Password hashing (#40, 2026-10-07; .NET 10 on macOS arm64)

- **A stored PBKDF2 key needs a length floor.** Verify derives `stored.Key.Length` bytes, and PBKDF2's shorter output is a prefix of its longer one. So a truncated key verifies, and an **empty** key verifies too, because `FixedTimeEquals` of two empty spans is true. Mutation proof: dropping the 32-byte minimum turned the "empty key" and "key truncated to 31 bytes" cases green.
- `Convert.TryFromBase64String` skips white space. Strict parsing means re-encoding the bytes and comparing the text ordinally. A `stackalloc` buffer of the maximum length rejects longer input on its own, because the call returns false.
- **`int.TryParse(text, NumberStyles.None, InvariantCulture, …)` accepts trailing NUL characters** (`"600000\0"` parses; review finding F2) and leading zeros. It refuses a sign, white space and non-ASCII digits. For strict parsing, check the length bound, no leading `'0'` and `!text.AsSpan().ContainsAnyExceptInRange('0', '9')` before calling it.
- `Rfc2898DeriveBytes.Pbkdf2(string/char span, …)` throws `EncoderFallbackException` for a lone surrogate. A Verify that never throws has to catch it.
- **Speed:** PBKDF2-HMAC-SHA256 at 600,000 iterations takes about 65 ms. 53 tests run in about 4 s, so tests keep the OWASP minimum and do not need a lowered floor.
- **Citing OWASP:** the cheat sheet page has no date. Pin it with `gh api "repos/OWASP/CheatSheetSeries/commits?path=cheatsheets/Password_Storage_Cheat_Sheet.md&per_page=3"` and read the content at that ref. The ref was `3c07d4a` on 2026-10-04: SHA256 at 600k, SHA512 at 220k, SHA1 legacy only.
- **Testing an internal singleton** from `PouryaKit.Security.Tests` without `Microsoft.Extensions.DependencyInjection`: register an instance and read `services.Single(d => d.ServiceType == …).ImplementationInstance`.
- **Constant-time red-once** is structural. Try every byte offset of each method's IL for `call`/`callvirt` plus a token, `Module.ResolveMethod` in a try/catch, then assert that `FixedTimeEquals` is present and `SequenceEqual` is absent. `ArchitectureTests/Il.cs` was outside allowed_files.

## OpenAPI and API versioning (#41, 2026-10-07; Asp.Versioning 10.2.3, Microsoft.AspNetCore.OpenApi 10.0.12, Scalar.AspNetCore 2.17.14)

- **Wiring:** `AddApiVersioning(...).AddApiExplorer(...).AddOpenApi(o => ...)` (the versioning builder's `AddOpenApi`) plus `MapOpenApi().WithDocumentPerVersion()` serves `/openapi/v1.json` per described version; no `services.AddOpenApi()` needed. Per-document transformers go on `o.Document` (the `OpenApiOptions`), notices on `o.DocumentDescription`. Read the library with `ilspycmd -p -o <dir> ~/.nuget/packages/asp.versioning.openapi/10.2.3/lib/net10.0/Asp.Versioning.OpenApi.dll`.
- **Default notices read the clock:** `OpenApiDocumentDescriptionOptions.SunsetNotice`/`DeprecationNotice` compare the date with `DateTimeOffset.Now` ("was"/"will be"). Replace both for ADR 0005; the description is then exact text a test can pin.
- **Sunset policies are per version in documents:** `GroupedApiVersionDescriptionProvider` resolves `TryGetPolicy(version)` only, so a document's sunset is Host-wide per version; response `Sunset`/`Link` headers come from the same policy.
- **A `v{version:apiVersion}` route can never be selected by header:** a header with a different version answers 400 ambiguous, none answers by URL. Header selection needs an unversioned group bound to the same version set; the Kit maps both inside the Module group. Consequence: each endpoint is mapped twice, so `WithName` would duplicate.
- **Without registration it fails at build, loudly:** `MapToApiVersion` on a group without a version set throws "does not have an associated API version set"; `WithApiVersionSet` without `AddApiVersioning` throws "No service for type IApiVersionParameterSource". The Kit's seam throws its own message first, during `MapPouryaKitModuleEndpoints` (i.e. in the test's Host-building call, not `StartAsync`).
- Unversioned endpoints (Stub) appear in every version's document. Asp.Versioning's empty 400/404 bodies become problem responses through Web's `ProblemStatusCodePages`.
- **Scalar:** only its static assets are `AllowAnonymous`; the page and `/openapi/*.json` hit the fallback policy (401) unless the Host allows anonymous. `/scalar` 302s to `/scalar/`; the page embeds `"sources":[{"title":"v1","url":"openapi/v1.json"},...]`.
- **A Web-only test Host** needs an assembly whose endpoints need no Module: the Stub's handlers need Catalog's `ICatalogProducts` and its endpoints Gateways. `tests/ModularMonolith.Tests/Unversioned/` is that assembly (pattern of `Misnamed/`: own csproj, `Compile Remove`, slnx row); `AddPouryaKitCqrs()` with no assembly gives `OperationContext`.
- The shared fixture clients send `api-version: 2.0` (`AppFixture.ApiVersion`), so other tests keep `/catalog/...` paths; versioning tests remove the header.
- **Review fix round (F1-F3):** a security requirement must follow the policy's `AuthenticationSchemes` or the default authenticate scheme; JwtBearer is not in the shared framework, so the handler is matched by type name up the base chain. The fixture's default scheme is `Test`, so the bearer test composes a Host with `AddAuthentication(JwtBearerDefaults.AuthenticationScheme)`. Double-mapped endpoints with `WithName` break the whole Host (8 tests red), so a `Finally` on the unversioned group strips `IEndpointNameMetadata`/`IRouteNameMetadata`. `ApiVersionLinkGenerator` adds the `version` route value only for URL-segment requests (`RouteParameter` is set by the route constraint), so pass `httpContext.RequestedApiVersion?.ToString("VVV", …)` (an extension property, not a method) yourself. An end-of-mapping check needs an `IStartupFilter`: the seam has no "last Module" signal.
- A plain `host.MapGet(...)` on a composed sample Host (outside any Module group) appears in every versioned OpenAPI document; the fixture Host has the JWT `Bearer` scheme (from `AddPouryaKitJwtBearer`) beside its default `Test` scheme, so an `AuthorizeAttribute { AuthenticationSchemes = "Bearer" }` shows the policy branch of `BearerSecurity`.

## Trusted peer over HTTP (Wave 2 final review A, 2026-10-08; ASP.NET Core 10.0.12)

- **Web's trusted peer now calls `OperationContext.RestoreTrusted`** in `OperationContextHttpHeaders.Continued`; `TrustedRestoreTests` requires a Web call beside Messaging.Wolverine's. Before, it used the public constructor for weeks unnoticed: the #48 tests read only the context's fields, never `IsTrustedContinuation`. A mark that changes authorization needs a test that crosses the permission check.
- **Proving it over HTTP:** the sample's `CallerPermissions` grants only when the HTTP caller's Actor claim equals the context's Actor, so a peer continuing "ada" into `/stub/catalog-products/removal` (`RemoveProductsCommand`, permission-protected) passes only through the trust mark. Assert `deleted_by = 'ada'` and use a unique product name: the command removes every product with that name, and other classes create "Lamp".
- **Endpoint `DisplayName` without methods:** `routes.Map("/x", handler)` inside a Module group is just `/stub/x` (no `HTTP:` prefix), also after `.WithMetadata(new HttpMethodMetadata([]))`; `MapGet` gives `HTTP: GET /stub/x`. An empty `HttpMethodMetadata` is accepted and answers every method.

## The unresolved partition and an exempt endpoint (#64, 2026-10-08; ASP.NET Core 10.0.12)

- **Who reaches the unresolved partition.** In the templates' order, authorization runs before the limiter, so an anonymous call to a protected endpoint or an unmatched path answers 401 before it counts. Only an endpoint that allows anonymous callers without `AllowAnonymousAs` (the recipe's `/alive`, `/health` and the OpenAPI documents in Development, a Host's own `AllowAnonymous()` route), or an authenticated caller without the Actor claim, lands there. A test spends the permit through a `MapGet(...).AllowAnonymous()` route, never through an unmatched path.
- **`DisableRateLimiting()` skips the global limiter too**: with it `/alive` answered 200 after the partition's one permit was spent, without it 429. It is in `Microsoft.AspNetCore.Builder`, and an endpoint that carries it is served by a Host with no rate limiter service or middleware (`Inventory.Host`, a bare Host). The middleware reads it from the matched endpoint, so it works only where routing ran before the limiter.
