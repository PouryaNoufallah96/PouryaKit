## Marten two-store spike (#120, 2026-10-16; Marten 9.46.0, WolverineFx(.Marten) 6.48.3, xunit.v3 4.0.1)

- **Marten 9 folds through a compile-time source generator** (`JasperFx.Events.SourceGenerator`, shipped in Marten's `analyzers/` folder, runs over every project that references Marten). It takes only **public** `Apply`/`Create`/`ShouldDelete`; the type may be internal. Internal `Apply` gives `InvalidProjectionException: No source-generated dispatcher found` at `FetchForWriting`, not at build. `AggregateStreamAsync` on a stream with no events returns null without building the dispatcher, so a negative test must call `FetchForWriting`.
- **The generator writes into the Module's assembly**: an evolver type naming `JasperFx.Events.Aggregation.IGeneratedSyncEvolver<,>`, `GeneratedEvolverAttribute`, `JasperFx.Events.IEvent`, and `JasperFxSourceGeneratorAppliedAttribute` on every assembly it runs over. The Kit's `TransportTypesUsedBy` (Wolverine*/JasperFx* type references) therefore rejects every Stream Module as written.
- **A Kit typed ID (a record class) is no Marten identity**: `InvalidDocumentException: No closed-shape id strategy is registered`. Marten strong-typed ids are immutable structs, and streams take Guid or string only.
- **One store**: `PersistMessagesWithPostgresql(cs, "wolverine")` plus `IntegrateWithWolverine(i => i.MessageStorageSchemaName = "wolverine")` on the same database gives two `IMessageStore` registrations and one store (`MessageStoreCollection` keys by Uri `wolverinedb://postgresql/<host>/<db>/<schema>`). Another schema or database: `InvalidWolverineStorageConfigurationException` at `StartAsync`, unless `Durability.ResolveMainStoreOnConflict` picks one (then two agents).
- **`new MartenOutbox(runtime, session)` adds a flush listener**: `SaveChangesAsync` commits, then flushes in that listener. A store listener (`StoreOptions.Listeners.Add`) runs before it: the stop point between commit and flush for probes and the crash child process. The Marten outbox writes envelopes into the runtime's **main** store tables on the session's connection.
- **Receipts that wait need the transaction first**: the statement `session.AdvancedSql.QueryAsync<int>("insert ... on conflict do nothing returning 1", ct, args)` (`?` placeholders) runs at once in the session's transaction, if it has one; otherwise it autocommits. Receipts as documents (`session.Insert`) are written only at the save: the duplicate's handler runs.
- **`SaveChangesAsync` commits nothing without queued work** (review F1 of #120, missed by the first spike run): an `AdvancedSql` statement is not queued work, so `session.BeginTransactionAsync` + a Receipt-only Operation was rolled back on dispose. Fix used: own an `NpgsqlConnection`/`NpgsqlTransaction`, open the session with `SessionOptions.ForTransaction(tx, shouldAutoCommit: true)` (Marten commits and disposes it after a batch, does nothing on session dispose), add a session listener whose `AfterCommitAsync` sets a flag (Marten calls listeners only after a real commit), and commit the transaction yourself when the flag is unset. `NpgsqlTransaction.IsCompleted` is internal and `.Connection` throws `ObjectDisposedException` once Marten disposed it. `Marten.Services.IUnitOfWork` clashes with the Kit's `IUnitOfWork` under `using Marten.Services;`.
- **A Stream's `Id` is settable** (Marten's fold sets it), so capture the identity when tracking begins and append to that; a count-only reading guard misses a repointed Stream (review F4).
- **Conflict exceptions** (all to `UnitOfWorkErrors.ConcurrencyConflict`): moved before fetch, `JasperFx.ConcurrencyException`; moved during the save, `JasperFx.Events.EventStreamUnexpectedMaxEventIdException` (MT003 from `mt_quick_append_events`, logged by Marten first as `MartenCommandException`); duplicate start after commit, `ConcurrencyException` from `FetchForWriting(id, 0)`; during the save, `Marten.Exceptions.ExistingStreamIdCollisionException`.
- **Conjoined tenancy**: one stream id is a separate stream per tenant; a tenantless session writes `*DEFAULT*`.
- **Extended schema objects** (`options.Storage.ExtendedSchemaObjects.Add(table)`) are created only with `ApplyAllDatabaseChangesOnStartup()` (or a migration); the `PostgresqlObjectName(schema, name)` ctor is obsolete (warning) in Weasel 9.41.
- **Wolverine handler types must be public**: `Discovery.IncludeType(internalType)` throws `ArgumentOutOfRangeException` inside `UseWolverine`'s lambda.
- **Harness traps**: xunit.v3 4.0.1 makes `CollectionBehavior.DisableTestParallelization` an obsolete error; use `xunit.runner.json` `parallelizeTestCollections: false` copied to output. `SendDiagnosticMessage` and Console output of passing tests do not show under MTP: write to a scratch file or fail with the value. In a Notification Handler test, wait for the welcome delivery before a version-sensitive command, or the concurrent append makes a red run pass by Conflict.
- **`validate.py --since` does not exempt `spikes/`**: a spike's code commit runs the full validation. Validate the clean code commit, then one Markdown record commit keeps `validated` true for `merge-package.py`. It refuses a dirty checkout ("Validate a clean committed checkout"): in a fix round, copy the record's edits aside, restore the files, validate, copy back. A fix round on a spike rebuilds the branch as code, code fix, one record commit (`git reset --mixed <first code commit>` keeps the record as working changes).

**Why:** each cost a failed run or a retry in #120, and #121, #131 and #132 build on the same libraries.
**How to apply:** before writing Marten aggregates, the Marten Unit of Work, its Receipts or tests, the Stream structure rule, or a spike's validation step. Related: [[wolverine-runtime-and-delivery-facts]], [[caching-and-idempotency-facts]], [[worktree-shell-and-check-gotchas]].
