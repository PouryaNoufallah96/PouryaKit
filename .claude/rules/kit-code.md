# Kit code

## Design

- **Package boundaries.** Plan section C, "Allowed references", says what each package may reference. An MIT-licensed `Microsoft.Extensions.*` package may be referenced where a package needs it, added to that table in the same change; any other reference outside the table is an owner decision. `PackageGraph` in `tests/PouryaKit.ArchitectureTests` is the enforced copy of that table. `PackageGraphTests` checks every Kit package's references and restored closure against it. Change `PackageGraph` with the table; the architecture document's references follow `PackageGraph`.
- **Namespaces.** A Kit package has folders by responsibility and one namespace, the package name, in every folder; application code (the Proving Sample, the templates' content, the test projects) has namespaces that follow its folders (ADR 0010).
- **Registration names.** `Use*` mirrors the verb of the framework call it wraps, applies a representation, or configures existing behaviour (`UsePouryaKitTestDelivery`); `Add*` adds a Capability's services; `Map*` maps; the Host builder is the receiver only when the call needs it. The one exception is the Module's messaging vocabulary of ADR 0006: `Publish<T>`, `Receive<T>`, `Subscribe<T, THandler>`, `PublishSnapshot` and `ReceiveSnapshot` keep their names in the Composition Root, beside `AddPouryaKitDelayedCommand` and `AddPouryaKitRecurringCommand`.
- **Dispatch.** Commands and queries go through the Kit's own dispatcher and its fixed pipeline (ADR 0002).
- **Isolation.** One host container; a Module is isolated by its assembly, `internal` types, its own DbContext and schema, and architecture tests (ADR 0001).
- **Commit.** The Unit of Work owns every commit, in the fixed sequence in plan section C. Handlers and Feature code return a `Result` and leave saving, committing and the Outbox to it (ADR 0003).
- **Failures.** Expected business failures are a `Result`; exceptions are for bugs and infrastructure (G.1).
- **Reactions and communication.** A reaction is a Domain Event Handler, a Notification Handler or an Integration Event Handler, and the three stay distinct (G.2). Modules talk to each other only in the ways G.5 lists.
- **Also settled.** Typed IDs (G.3), repositories and specifications (G.4), authorization at trust boundaries (G.6), explicit mapping with no mapper (G.7), validation as one pipeline step (G.8).
- **Adopted code.** Extend the existing seam. Code adopted from a reference project follows plan section E, "Provenance and licensing".
- **Current idioms.** .NET 10 only and the latest C# (plan section F, item 6): write the C# 14 and .NET 10 form where one exists. The build enforces collection expressions, primary constructors, auto properties with the `field` keyword and `System.Threading.Lock` (`.editorconfig`); review judges the rest, such as extension members, `TimeProvider` and `Guid.CreateVersion7`, and an older idiom there is a finding. Every public member of a Kit package carries a one-sentence `<summary>` in the glossary's terms, or `<inheritdoc />` where it implements or overrides a documented member: CS1591 fails the build otherwise (`Directory.Build.props`).
- **Boundaries.** A step that stores, locks, flushes or shares a run across callers states in its comment what happens when the other party commits, rolls back, dies, cancels or expires between its statements, and the ticket's tests show each case its guarantee depends on: a concurrent duplicate, a crash between the store and the acknowledgement, a caller that leaves a shared run, a row that expires mid-step.
- **The Proving Sample and the templates.** `PouryaKit.Templates` packs the sample's business code at pack time and keeps only the composition-specific files of its own, so a new Composition Root, Gateway endpoint or Gateway-bound adapter in the sample needs the monolith template's own `IDispatcher` replacement under `src/PouryaKit.Templates/content/monolith`, and a changed sample csproj of a Module, of Catalog's Contracts or of the ServiceDefaults needs the matching template csproj: `TemplateTests` compares those paired projects, and each replacement's calls with its sample file's, and fails until both match. The Host projects are each template's own; `TemplateTests` compares only their pipeline order with the sample Host each follows: `ModularMonolith.Host` for the monolith and the modular monolith, `Inventory.Host` for the service.
- **Smallest design that fits the ticket.** A comment earns its line only by stating a non-obvious constraint that names and types cannot carry.

## Tests

- **Test behaviour that matters:** an invariant, a failure path, an ordering, or a guarantee the ticket states. One test per behaviour; leave out coverage that restates another test or the compiler.
- **Red once.** A test of a guarantee the ticket states is run once with that behaviour switched off, and must fail. A fix adds a regression test for each fixed finding a test can express.
- **Structure tests with the rule.** A ticket that introduces a rule Feature code must follow adds its structure test to `tests/PouryaKit.ArchitectureTests` in the same ticket, with a negative case: an offending type the test must catch, as `Offending/` holds.
- **Runtime proof.** A ticket that claims a runtime guarantee is proven against PostgreSQL in Testcontainers (`AGENTS.md`, workflow step 5). A Phase is done when its tests pass there, never on compilation alone (section E).
- **Stack.** xUnit v3, Testcontainers and Respawn, through `PouryaKit.Testing`; three seams under `tests/`: `PouryaKit.Domain.Tests` for the Domain seam, plus `PouryaKit.Cqrs.Tests`, `PouryaKit.Validation.Tests`, `PouryaKit.Core.Tests` and `PouryaKit.Security.Tests` without a database; `ModularMonolith.Tests` for the Gateway seam; `PouryaKit.ArchitectureTests` for the Structure seam (section C as corrected); `PouryaKit.Storage.Tests` for a storage provider against its container (RustFS, Azurite); `PouryaKit.Reporting.Tests` for the report renderer, each format read back by its standard reader, without a container; `PouryaKit.Aspire.Tests` for the Proving Sample's AppHost, built and started headless with Aspire's testing builder; and each generated template's HTTP smoke test, a `HostFixture` of `PouryaKit.Testing` over the generated Host's `AppHost` (`src/PouryaKit.Templates/content/shared/tests/ModularMonolith.Tests` for the monolith and the modular monolith, `content/service/tests/ModularMonolith.Tests` for the service, whose fixture also starts RabbitMQ), which `scripts/packaging/validate.py` runs on the solutions it generates. Test projects run on Microsoft.Testing.Platform (set in `global.json`) with the `xunit.v3` package only, never the VSTest packages (`Microsoft.NET.Test.Sdk`, `xunit.runner.visualstudio`); a test project with no test fails the run.
- **Spikes.** A Spike is deleted once its decision is recorded; one that proves an invariant worth protecting becomes a permanent integration or architecture test (G.10). Building one, or writing or reviewing its decision record: `docs/agents/spikes.md`.
