# Docs site

`website/` is the Kit's public documentation site, a Next.js static export. Everything it renders is read outside this private repository.

## What a page may say

- **English only.**
- **Nothing private in rendered text.** No link or text pointing at the private repository (`github.com/PouryaNoufallah96/PouryaKit`), no local machine path, no name of the owner's private projects (Cybernod, Ultrabusiness), no delivery vocabulary (Wave, Phase, spike in any case, a story's or session's number), no tracker code (`W4`, `spec #<n>`, `ticket #<n>`, an issue number such as `#<n>`) and no citation of the private plan (`G.6`, `section G`, `plan I.3`, `plan section D`). The build enforces each ("Content from the Kit's sources" below); the public reference projects may be named.
- **Facts live in the Kit skill.** A Capability's guarantees, options and rules are in `.agents/skills/pourya-kit/` and a package's purpose and quick start in its `src/<Id>/README.md`; a page explains and renders them, and never holds a fact the skill lacks. A new how-to fact goes into the skill first. A page restates no literal the skill owns (a status code, a default, a port, a count, a configuration or connection key, a header, a route, a check or exception message, SQL, an option list, a delivery guarantee): it explains the behaviour and links the section that states it, so the value has one home. An error code's name may title a failure message, and a command copied from the skill stays.
- **Only where a reader can go.** A site page sends the reader only where they can go: no test class or ADR as proof, no "the skill" as a place to read, and nothing on how the site is built.
- **Names are real.** `check-docs.py` checks the backticked names of every `website/content/**/*.mdx` page against the code; the pre-commit hook refuses an `.mdx` file staged in part.

## How it is built

- **No `public/` directory**, top-level or nested, and no `.vscode/`: `check-tree.py` refuses either segment anywhere. The icon uses the Next.js app-directory file convention (`app/icon.svg`), images are static imports, and each Open Graph image is a static `.png` route drawn with `next/og` (`app/og/image.png/route.tsx`, `app/og/docs/[...slug]/route.tsx`).
- **A static export** (`output: 'export'`): every route handler is a force-static `GET`, with `generateStaticParams` where its path has segments; no rewrite, redirect, header, proxy or handler that reads the request, which Next.js refuses in an export. A page's Markdown is the static file `/llms.mdx/docs/<slugs>/content.md`, which "Copy as Markdown" fetches, and search runs in the browser on the static index `/api/search.json`; there is no AI chat.
- **Design**: the docs layout fills the window (`--fd-layout-width` on `#nd-docs-layout`), so the sidebar sits at its left edge, and the theme switch fills the sidebar's footer bar; shadcn tokens in OKLCH with Fumadocs' `shadcn.css` and `preset.css`; light background `oklch(1 0 0)`, dark `oklch(0.16 0.004 285)`; one accent, Cobalt Indigo `oklch(0.585 0.233 277.117)`; Geist and Geist Mono through `next/font`; radius 0.625rem; cards rounded-xl with a 2px muted border and no shadow at rest; a neutral focus ring; reduced motion respected. No gradient text, side stripes, glassmorphism or em dashes. Fumadocs Cards, Steps, Tabs, Accordions and titled code blocks, with the site's own Card and Callout in MDX (`components/card.tsx`, `components/callout.tsx`), since Fumadocs' draw a 1px border, a shadowed icon and a side stripe; "Copy as Markdown" on each page; the theme toggle on Mod+Shift+D; static Open Graph images through `next/og`. Badges are native components; no external badge host.
- **Page skeleton**: title and one-line description; what it is; the key caveat; when to use it; steps with code; a guarantee table; failure messages; next steps.
- **Dependencies**: exact versions in `website/package.json`, pnpm pinned by its `packageManager`, the committed `website/pnpm-lock.yaml` installed with `--frozen-lockfile`. pnpm's settings are in `website/pnpm-workspace.yaml` (pnpm 11 and later read no `pnpm` field in `package.json`): a dependency's install script runs only when `allowBuilds` lists it `true`, and an unlisted one fails the install; `ignoredOptionalDependencies` keeps out `sharp`, whose libvips is LGPL-3.0-or-later and which an export never loads.
- **Licences** (ADR 0002): `pnpm --dir website check-licences` (`scripts/check-licences.mjs`) holds every package of the npm closure, dev dependencies included, to the licence its own `package.json` declares. It admits MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC and 0BSD, an `OR` with one admitted side and an `AND` of admitted terms. The whole expression must be choices (`OR`) of conjunctions (`AND`) of terms in an SPDX identifier's shape before any branch counts, so every other shape fails, beside an admitted `MIT` too: a missing, unknown or custom licence, an empty branch, parentheses, `WITH`. Two exceptions are admitted for their named packages only: `caniuse-lite` under CC-BY-4.0, browser-support data that browserslist reads at build time, a hard dependency of next, attribution only; and `lightningcss` with its platform binaries under MPL-2.0, Tailwind 4's CSS compiler, run only at build time, nothing of it in `out/`. Neither reaches a reader, so neither owes a notice today; a change that copies either into `out/` or the public repository carries its licence notice with it. A new licence or exception is an owner decision.
- **Covers** (`covers/`, `scripts/covers.ts`): one textless artwork per Capability family, the Kit's hero and a 1024px icon artwork, generated once with Codex and kept in `covers/art/` (1280x640, the icon 1024x1024, each at most 1 MB, re-encoded losslessly); the model never draws a letter. `pnpm --dir website covers` typesets each package ID of the inventory, read by `readPackageIds` (`lib/kit-sources/packages.ts`, the list the site and the public repository read too), and its tagline from `covers/covers.json` onto its family's artwork with `next/og`'s `ImageResponse` and the Geist fonts committed in `covers/fonts/` (OFL-1.1, unmodified, beside `OFL.txt`), and writes the Kit's and every package's cover to the gitignored `covers/out/` and the packages' shared icon to `src/icon.png`. The same artwork gives byte-identical files, and the script refuses a cover over 1 MB or of another size. `covers.json` names each package of `scripts/packaging/inventory.json` exactly once, and every string a cover sets is printable ASCII, which the committed fonts hold, because `next/og` fetches a glyph they lack from Google Fonts (`scripts/covers.test.mjs`); a tagline is one true line from the skill's Capability table or the package's reference. How to make a new artwork: `covers/README.md`.
- **CI**: the `website` job installs, checks the licences, runs the site's tests (`pnpm --dir website test`: the licence check's, the covers', the content pipeline's and the public repository's), lints with Biome and builds the export, then typesets the covers, fails when that render differs from the committed `src/icon.png` (`git diff --exit-code -- src/icon.png`) and checks the public repository's tree against its manifest ("The public repository" below); `.agents/scripts/ci-local.sh` runs the same steps.
- **Ultrabusiness** (the owner's docs app) is a pattern source only: reimplement its patterns, never copy its code, and run nothing in its checkout.

## Content from the Kit's sources

- **One reader.** `lib/kit-sources/` is the only code that reads the Kit's sources (the skill, `GLOSSARY.md`, `src/`, the Proving Sample and the tests) and rewrites their links: the site build and the public repository's sync (`scripts/sync-public.ts`) use it. `pnpm --dir website build` runs `scripts/kit-content.ts generate`, then `next build`, then `scripts/kit-content.ts check-export`. The generated pages are written into ignored folders, `content/docs/capabilities/`, `content/docs/reference/` and `.generated/`, emptied on every run: never edit them, and never edit a source for the site.
- **What is published.** The skill references on `PUBLISHED_REFERENCES` (`lib/kit-sources/references.ts`): every file under `references/` but the maintainer guides `packages.md` and `publication.md`. A file on neither list, of any kind, fails the build, so a new reference is published only once it is listed. Each gets a Capability page in the order of the skill's Capability table, the Host recipes under Guides. The Reference pages are the package matrix with a page per package (what follows the title of its `src/<Id>/README.md`, an MDX page whose alerts are the site's Callout), the glossary, the Error codes (read from each package's `*Errors` and `*ErrorCodes` types; a member shape the reader does not know fails) and the Host checks, which link to the skill's sections, since the checks' messages are interpolated strings no reader extracts reliably.
- **A Capability page's top.** The hand-written part of a Capability page is `content/capabilities/<reference>.mdx`, with an optional `description` in its frontmatter and no `import` or `export`. The generated page includes it, then a "Reference" heading and the skill reference. A top heading whose anchor would renumber one of the reference's fails the build, since links between references name the reference's own anchors. Every published reference has a top, and since the generator renders a reference without one, a newly published reference gets its top in the same change. Each top keeps one skeleton: an opening that links each glossary term on its first use, a Callout with the key caveat, `## When to use it`, `## How it works` (Steps), `## In the Proving Sample` or `## In the Kit's tests` (each code block a `<Snippet>`; the project templates' top shows commands copied from the skill in its steps instead), `## Guarantees and failures` (a table that links the reference's own sections below it, never restating them) and `## Next steps` (Cards).
- **The public projection.** The glossary loses exactly its Wave, Phase and Spike entries (`EXCLUDED_ENTRIES` in `lib/kit-sources/glossary.ts`; a selector that matches no entry fails), and every other term gets an anchor. The ADRs are not projected: they stay private, no page renders one, and a link into `docs/adr/` becomes its own text; the skill references state the rules they decided.
- **Links.** A link to a rendered source becomes its page, with its anchor carried over, or dropped when its heading is not on the page; a link into the repository with no page becomes its own text. A link to the private repository, or to an anchor the target lacks, fails.
- **Package READMEs.** A package's `src/<Id>/README.md` ships inside its version, so only another publication changes it, and nuget.org, GitHub and the site read one file. `allReadmeViolations` (`lib/kit-sources/readmes.ts`), which `generate` runs, fails a package of the inventory with no README and a README that leaves the template: the cover at `<ASSETS_URL>/covers/<Id>.png` and the three badges, by equality, the `# <Id>` title and one paragraph, then Install, When to use it (with a package it pairs with, linked), Quick start, What you get, one or two `[!TIP]` or `[!WARNING]` alerts, and Learn more, in pure Markdown, with no fifth image, HTML or reference-style link. A link names a page of the site or an inventory package on nuget.org and nothing else; a fence is `bash` or `csharp`; each line of a `csharp` fence, trimmed, is in a `.cs` file of `samples/`, `tests/` or `src/PouryaKit.Templates/content/` (blank and comment lines excepted), so a renamed API fails the build instead of publishing a stale snippet. `check-export` then holds each link to the site to `out/`: `<route>/index.html` exists and holds the anchor. A README's prose is rendered on the site, so everything under "What a page may say" applies to it; a package's install line is `dotnet add package <Id> --prerelease`, and a version literal fails, since it stales the moment the next version ships the README. The templates' README keeps `dotnet new install PouryaKit.Templates@<version>` and links the install page.
- **Snippets.** `<Snippet file="samples/ModularMonolith/..." region="name" />`, on a line of its own, quotes a region of the Proving Sample's or the tests' code, marked `#region name` and `#endregion` (or `// #region name` where the language has no directive), as a code block titled with the file's name. A missing file or region fails the build. The templates pack the sample's Module code, so a marker in a file that a template replaces needs the template's copy too. The landing is TSX, so it quotes a region with `KitSnippet` of `components/kit-code.tsx`, the same reader.
- **The published version, once.** The templates' install command, with the version every generated solution pins, is `content/docs/get-started/install-templates.sh`: a page includes it as a code block with `<include lang="bash" meta='title="Terminal"'>` and its relative path, which keeps it in the page's Markdown, and the landing reads it through `templatesInstall()` of `lib/templates-install.ts`, which fails the build when the file holds no versioned install command. A new published version changes that one file.
- **The rules over the export.** `check-export` reads every file of `out/` for a private repository link (each GitHub URL shape, the jsDelivr package page's included, and an owner/repo name, alone, after a `/` or followed by a path, compared as a browser sends them and GitHub resolves them, ignoring case, with the percent escapes of an address's characters decoded and any other left in its path segment, an escaped `/` read both decoded and kept in its segment, a `\` read as `/`, a URL's `.` and `..` segments resolved, escaped or not, a climb past the root stopping there, and a line break after a `/` or `:` undone, the name read as its run of name characters, so the punctuation that ends a sentence is no part of it) a local path (`/Users/`, `/home/`, `/private/tmp/`, a Windows drive, `D:\`, or `D:/` outside JavaScript, where `{a:/re/}` has its shape) and a private project's name (Cybernod, Ultrabusiness, whole words in any case), with string escapes undone and, in HTML and Markdown, each character reference undone once as the HTML parser reads it (`decodeEntities`, on `parse-entities`: named, numeric, and the legacy names, numeric ones too, without a semicolon), and reads the same rules over rendered text, where neither inline markup nor a soft hyphen or zero-width character can split a name. It reads only rendered text for delivery vocabulary (the capitalised `Wave` and `Phase`, `spike` in any case, inside a word or a path too, and `story <n>` or `session <n>`), tracker codes (`W<n>`, `spec #`, a ticket, issue or PR number, `#<n>` of two digits or more) and the private plan's citations (`G.<n>`, `I.<n>`, `section G` in any case, `plan section <letter>`): an HTML page's text outside scripts and styles, read by `parse5` as a browser reads it, each page's Markdown and `llms*.txt` (text, code and link and image titles, not link destinations or heading ids) and every string of the search index. A phrase is read across a soft line break, any other white space (a no-break space too), inline markup and a comment, never from one block into the next, such as a table's cells; `generate` also holds each page to the rules block by block before it writes it, with `nodeViolations` (`lib/kit-sources/markdown.ts`), which reads a link's, an image's or a definition's title, a code fence's info string and a reference's label as rendered text, each a block of its own, and a URL as markup. A finding fails the build. "Orchestrator" is an ordinary infrastructure word and is not refused.

## The public repository

- **What it holds.** `scripts/sync-public.ts` assembles the tree of `PouryaNoufallah96/pouryakit-pub` through `lib/kit-sources/distribution.ts`: `.claude-plugin/marketplace.json` (the marketplace `pouryakit` and its one plugin `pourya-kit`, from the root, `"strict": false`, `"skills": ["./skills/pourya-kit"]`, at the skill's `metadata.version`), `skills/pourya-kit/` (SKILL.md, `agents/openai.yaml` and the references on `PUBLISHED_REFERENCES`), `assets/` (`kit.png`, `covers/<id>.png` for each package of the inventory and `icon.png`, the packages' `src/icon.png`), `README.md` from the template `distribution/README.md.template` (no `.md` file, since its relative links name the public repository's files, which `check-docs.py` would look for here), and the repository's `LICENSE`. A file in the skill's folder the sync does not know fails it.
- **The site's projection.** Each skill file is parsed, its links rewritten and held to the site's rules as a page is, titles, fence info strings and labels included, and SKILL.md keeps its frontmatter. A link to another file of the copy stays relative and must name one of that file's headings; SKILL.md's rows for the maintainer guides (`packages.md`, `publication.md`) leave the copy, and a link to a maintainer guide, an ADR or any other path of this repository becomes its own text. Table cells are written unpadded, as the sources write them; the delimiter row is written `| - |`. The marketplace, the agent metadata, the licence and the README are held to the rules too, and each relative link of the README must name a file of the tree.
- **One home per address.** `lib/kit-sources/addresses.ts` holds the site's address (also the site's own default address, `lib/shared.ts`), the repository, the tag `assets-v1` that README image URLs pin (`https://raw.githubusercontent.com/PouryaNoufallah96/pouryakit-pub/assets-v1/assets/...`), and the marketplace's and plugin's names. MSBuild cannot read it, so `PackageProjectUrl` in `Directory.Build.targets` and the cover URLs of the READMEs are literals, which `lib/kit-sources/readmes.test.ts` and the README check hold to it. The README template names them as `{{site}}`, `{{repository}}`, `{{assets}}`, `{{marketplace}}` and `{{plugin}}`, and a name it does not know fails.
- **The manifest.** `distribution/manifest.sha256` lists every file of the tree with its sha256, in `sha256sum`'s format. `pnpm --dir website sync-public --check`, after `pnpm --dir website covers`, regenerates the tree and fails on a file missing, extra or changed; after a reviewed change of a source, `pnpm --dir website sync-public --write-manifest` rewrites the manifest, so a change of the skill carries the manifest it publishes. The covers are deterministic, so only a regenerated artwork changes theirs.
- **Writing and verifying.** `pnpm --dir website sync-public [<directory>]` writes the tree to the gitignored `distribution/out/`, which it empties first, or to an absent or empty directory, then compares it with the manifest. After the owner pushes and tags, `pnpm --dir website sync-public --verify-remote <tag>` resolves the tag and the default branch with `git ls-remote`, fetches the tagged commit into a temporary directory, and fails unless the default branch is that commit and it holds exactly the manifest's files and hashes (`--remote <url>` names another repository).
- **Versioning.** The skill's `metadata.version` is the plugin's `version`, and Claude Code keeps an installed plugin until that string changes: before a published sync whose skill files changed since the last tag, bump it in SKILL.md and rewrite the manifest.
