# PouryaKit

PouryaKit lets Feature code hold only business behaviour. The Feature supplies the aggregate, the command or query, its validator and handler, its data access and its endpoint. The Kit dispatches the Operation, validates it, owns its single commit, runs its reactions and delivers its Integration Events and Snapshots to other Modules.

These hold in every Capability:

- A handler returns a Result. An expected business failure is an Error in that Result; exceptions are for bugs and infrastructure.
- The Unit of Work writes the Outbox, saves and commits, and sends what it wrote only after the commit. Feature code returns its Result and leaves all of it to the Unit of Work.
- Anything outside a Module reaches it through its Gateway, and every Gateway call is one Operation in its own scope, run with the `OperationContext` the caller passes. There is no anonymous or default Actor.
- A reaction is one of three kinds, kept distinct: a Domain Event Handler inside the Module and its Unit of Work, a Notification Handler after the commit for anything that reaches outside the Module's data, and an Integration Event Handler in the receiving Module.
- Modules talk through Domain Events inside a Module, Integration Events and Snapshots across Modules, and a synchronous question through the owning Module's Contracts only when the answer is needed before the Operation can go on.
- HTTP access is authenticated by default, and a public endpoint says so. Work an authorized Operation causes, delivered by the Kit or continued with `Continue()` inside that running Operation, is a trusted continuation (`IsTrustedContinuation`) that runs on its recorded authority: a declared permission is not checked again for it, while every authorizer the application registered still runs. A context application code builds, or continues outside the Operation that ran it, is never trusted; `CausationId` is informational ([security.md](references/security.md#continuations)).
- A query, an authorizer, a validator and a Snapshot mapper only read: every write the Kit guards is refused there ([commands-queries-validation.md](references/commands-queries-validation.md#code-that-only-reads)).
- A Module references no other Module's implementation, makes public only its Composition Root and what its Host implements, and never names a transport type, clears Domain Events or writes an aggregate's table with SQL. No application type implements a contract the Kit fills for its pipeline. Structure tests reject each of these, and any save or commit in a Module's code ([testing.md](references/testing.md#structure-tests)).
- Names follow the Kit's `GLOSSARY.md`: Module, Feature, Operation, Operation Context, Actor, Domain Event, Notification Handler, Integration Event, Snapshot, and for messages the wire name, the subscription and, on a broker, the service name, Wolverine's name for a Host there. A composition check stops a Host when its container is built, a startup check when it starts ([modules.md](references/modules.md#the-hosts-checks)).
