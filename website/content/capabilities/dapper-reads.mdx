---
description: "Read for display in plain SQL with Dapper on a pooled PostgreSQL connection, with typed IDs as parameters and results and a Page helper that never turns caller input into SQL."
---

A query's handler that reads for display usually reads in SQL. `PouryaKit.Persistence.Dapper` gives each handler `IReadConnectionFactory`, which leases an open connection from the Host's one PostgreSQL pool, and makes every typed ID of the Module work as a Dapper parameter and result. For a list, `PageSql` and `QueryPageAsync` read one [Page](/docs/reference/glossary#page) of it, sorted and filtered only by what the query declared.

Beside it, `IUnitOfWorkConnection` of `PouryaKit.Persistence` lets a command write a Module-internal table in plain SQL inside the [Unit of Work](/docs/reference/glossary#unit-of-work), so the write commits or rolls back with the Operation.

<Callout type="warn" title="Dapper runs exactly the SQL you write">
  No EF Core query filter reaches a plain SQL read. A read of a soft-deletable table leaves out the removed rows itself, and in a tenant-scoped Module a read of a tenant-scoped table states the tenant the lease bound, never a tenant the handler passes ([Reading](#reading)).
</Callout>

## When to use it

- A query reads rows for display, by ID or by a filter you write.
- A query answers a sorted and filtered Page of a list.
- You read or write typed IDs with Dapper.
- A command, a Domain Event Handler or a delivery writes a projection, a tally or a copy that no aggregate maps.

## How it works

<Steps>
<Step>

### Register the read connection

Call `AddPouryaKitDapper` in the Composition Root of each Module that reads with Dapper. Every Module of a Host names the same connection, and the Host fails when it is built if its configuration does not set it.

</Step>
<Step>

### Lease a connection in the handler

Open a lease with `connections.OpenAsync` inside the query's handler and dispose it when you are done. The lease binds the Operation's tenant as a session setting when it opens, and reads only what is committed.

</Step>
<Step>

### Write the SQL against your own schema

Name each table with its Module's schema, alias snake_case columns to your DTO's members, and pass the cancellation token through a `CommandDefinition`. Another Module's data comes through its Contracts, never through its tables.

</Step>
<Step>

### Map a Page's names to your columns

A Page read writes its `SELECT` and `COUNT` once in a `PageSql` and maps each declared sort key to a column. Each declared filter arrives as a parameter, so no text a caller sends ever becomes SQL.

</Step>
</Steps>
