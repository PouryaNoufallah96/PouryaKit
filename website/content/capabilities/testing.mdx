description: "Test against the hosted application: PostgreSQL in a container, data reset between tests, Operations sent through a Gateway, deliveries awaited and asserted, dead letters read and replayed."
---

`PouryaKit.Testing` tests your application the way it runs. One `HostFixture` per test assembly builds the real Host with the same composition `Program` uses, starts PostgreSQL in a container, applies every Module's migrations and starts the application on it. Each test class derives from `HostTest<TFixture>`, which waits for the deliveries an earlier test caused and then empties every table, so no test sees another's data. A test sends its Operations through `Fixture.Gateway<TModule>()`, exactly as the application does, and asserts on the returned [Result](/docs/reference/glossary#result) and on the rows it reads back.

The same package waits for the deliveries an Operation caused, reads and replays dead letters, fixes the time, and lets a test abandon a Host. The structure rules every Module follows are stated for you to write as your own architecture tests: no package ships them, and the Kit's own tests are not published.

<Callout type="warn" title="The fixture needs Docker">
  `HostFixture` runs PostgreSQL in a Testcontainers container, so the machine that runs the tests needs Docker. Tests that share a fixture run one at a time.
</Callout>

## When to use it

- You test a Feature against the hosted application, through its Module's Gateway or over HTTP.
- A test needs a particular Actor, tenant or correlation, or a fixed time.
- You wait for the deliveries an Operation caused and assert what they did, or read and replay a dead letter.
- You abandon a Host mid-delivery to test a crash.
- You check the structure rules a Module follows, or write them as tests of your own project.

## How it works

<Steps>
<Step>

### Derive one fixture for the assembly

A `HostFixture` subclass builds the application's Host, not started, from the same builder and pipeline methods `Program` uses, and registers with `AssemblyFixture`. The fixture runs the container, migrates every Module and starts the Host before the first test.

</Step>
<Step>

### Derive each test class from HostTest

Before each test, `HostTest<TFixture>` waits until every delivery of earlier tests has finished, then deletes every row and every stored delivery.

</Step>
<Step>

### Send Operations through the Gateway

`Fixture.Gateway<TModule>()` runs each call as one Operation in its own scope. Called without a context, it runs as the test Actor with no tenant; pass an `OperationContext` of your own when the Actor or the tenant matters.

</Step>
<Step>

### Assert Results and rows

Assert on the Result's `Errors` for business and validation failures, never on exceptions, and read rows back with your own SQL on the fixture's connection string.

</Step>
</Steps>
