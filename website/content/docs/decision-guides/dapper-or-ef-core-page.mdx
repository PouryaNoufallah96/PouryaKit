## What it decides

How a query's handler reads one [Page](/docs/reference/glossary#page) of a list. Both reads take the same `PageRequest`, the same `PageDeclaration` of what a caller may sort and filter by, and answer the same `Page<T>`. They differ in who writes the query: you write the SQL for Dapper, and EF Core translates a repository's expressions.

<Callout type="warn" title="Dapper runs exactly the SQL you write">
  No EF Core query filter reaches a Dapper read. A read of a soft-deletable table leaves out removed rows itself, and in a tenant-scoped [Module](/docs/reference/glossary#module) a read of a tenant-scoped table holds it to the [tenant](/docs/reference/glossary#tenant) itself, in the shape the structure test accepts: [Reading](/docs/capabilities/dapper-reads#reading). An EF Core Page applies the global query filters for you.
</Callout>

## When to choose each

| | Dapper | EF Core repository |
| --- | --- | --- |
| When | A query's read, normally: the [Proving Sample](/docs/reference/glossary#proving-sample)'s `ListProducts` reads this way | When a [Feature](/docs/reference/glossary#feature) reads its Page through its aggregate's EF Core mapping instead |
| What you write | The `SELECT` and `COUNT` once, in a `PageSql`, with each sort key mapped to a column | A specific repository member on `PageAsync`, with `PageExpressions` mapping each declared name |
| Soft delete and tenant | Stated in your SQL | Applied by the global query filters |
| What it reads | What is committed, on a connection of its own | Through the Module's [Unit of Work](/docs/reference/glossary#unit-of-work) |

Both map the declared names to your own columns or expressions, so no text a caller sends becomes SQL, and both throw before any query runs for a request that never passed validation.

## Read a Page

<Steps>
<Step>

### Declare the paging

The query carries a `PageRequest`, declares its sort keys and filters, and checks the request in its validator: [Paging](/docs/capabilities/commands-queries-validation#paging).

</Step>
<Step>

### Read it with one of the two

[Reading a Page with Dapper](/docs/capabilities/dapper-reads#reading-a-page), or [Reading a Page through a repository](/docs/capabilities/persistence#reading-a-page).

</Step>
<Step>

### Bind it from the query string

An endpoint binds the request with `HttpPageRequest`: [A Page over HTTP](/docs/capabilities/web#a-page-over-http).

</Step>
</Steps>

## What the Kit guarantees

| | Stated in |
| --- | --- |
| The Dapper and EF Core reads of one declaration answer the same Page | [Dapper reads, testing](/docs/capabilities/dapper-reads#testing) |
| A tenant-scoped Module's SQL holds each tenant-scoped table to the tenant | [Structure tests](/docs/capabilities/testing#structure-tests) |

## Failure messages

<Accordions>
  <Accordion title="A Page Error from validation">
    The request asked for more than the declaration allows. The validator refuses it with the Error's code and target before the handler runs: [Paging](/docs/capabilities/commands-queries-validation#paging).
  </Accordion>
  <Accordion title="PageSql throws when it is built">
    The SQL does not match the declaration it serves, and the exception says how: [Reading a Page](/docs/capabilities/dapper-reads#reading-a-page).
  </Accordion>
  <Accordion title="A structure test names the conjunct a read needs">
    A Dapper read of a tenant-scoped table in a tenant-scoped Module does not hold that table to the tenant in the shape the rule accepts. The failure names the conjunct to add.
  </Accordion>
</Accordions>
