## What it is

An [Operation](/docs/reference/glossary#operation) is one command or query running inside one [Module](/docs/reference/glossary#module), from entry to outcome. A command changes state and a query only reads. Each is a sealed record with exactly one handler, and every handler returns a [Result](/docs/reference/glossary#result): a value on success, one or more [Errors](/docs/reference/glossary#error) on failure.

An Error is a named business reason the Operation did not succeed. It has a stable code, a message and a kind, and it carries no HTTP status: the Web [Capability](/docs/reference/glossary#capability) turns its kind into one when the Result becomes a response. [Result and Error](/docs/capabilities/domain-primitives#result-and-error) lists the kinds, and [Problem responses](/docs/capabilities/web#problem-responses) the status each answers.

<Callout type="warn" title="A business failure is an Error, never an exception">
  Return an Error when the Operation cannot succeed for a reason the business knows, such as a missing product or a name already in use. Exceptions are for bugs and infrastructure. A test of a business or validation failure asserts on the Result's Errors, never on an exception.
</Callout>

## When it matters

Every [Feature](/docs/reference/glossary#feature) has one. A command that changes something, such as renaming a product, is a `Command` or a `Command<TResponse>`. A read, such as one product or a page of them, is a `Query<TResponse>`. Each passes the same fixed steps, so a Feature supplies only its record, its handler and, when it needs them, a validator and an authorizer.

Every command and query passes the same fixed pipeline before and around its handler; [The pipeline](/docs/capabilities/commands-queries-validation#the-pipeline) lists its steps. A command's handler runs inside the [Unit of Work](/docs/reference/glossary#unit-of-work), which commits once for the whole Operation: see [Unit of Work](/docs/concepts/unit-of-work). A failure at any step, a nested command's included, fails the Operation with its Errors.

- Pass a failed Result's Errors on rather than ignoring them: every Error is kept.
- Check `IsSuccess` or `IsFailure` before you read `Value`.
- Check a business rule that depends on state in the aggregate, with `CheckRule`, and input shape in a validator.

## Failure messages

<Accordions>
  <Accordion title="A command or query with no handler, or several">
    The [Host](/docs/reference/glossary#host) stops while it is composed. Give each one exactly one handler.
  </Accordion>
  <Accordion title="Value read from a failed Result">
    Reading `Value` from a failure throws. Check `IsSuccess` first.
  </Accordion>
  <Accordion title="Operation.ReadingChangedState">
    Code that only reads, such as a query's handler, changed tracked state, so the command it ran in fails with this Error and nothing commits. See [code that only reads](/docs/capabilities/commands-queries-validation#code-that-only-reads).
  </Accordion>
  <Accordion title="Every Error code the Kit declares">
    The [Error codes](/docs/reference/error-codes) page lists each one with its kind and message.
  </Accordion>
</Accordions>
