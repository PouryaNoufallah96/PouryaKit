## What it is

PouryaKit is a set of NuGet packages and `dotnet new` templates for applications built as a [Host](/docs/reference/glossary#host) of [Modules](/docs/reference/glossary#module) on .NET 10 and PostgreSQL. Each Module is a business boundary that owns its data, its rules and its public [Contracts](/docs/reference/glossary#contracts).

Inside a Module, your code is [Features](/docs/reference/glossary#feature). A Feature supplies the aggregate, the command or query, its validator and handler, its data access and its endpoint. The Kit runs everything around it: it dispatches the [Operation](/docs/reference/glossary#operation), validates it, owns its single commit in the [Unit of Work](/docs/reference/glossary#unit-of-work), runs its reactions and delivers its [Integration Events](/docs/reference/glossary#integration-event) and [Snapshots](/docs/reference/glossary#snapshot) to other Modules.

The packages are grouped into [Capabilities](/docs/reference/glossary#capability): one or a few packages each, such as Messaging, Web or File storage. A Host references the ones it uses.

<Callout type="warn" title="Feature code never commits">
  The Unit of Work writes the Outbox, saves and commits, and sends what it wrote only after the commit. A handler returns its Result and leaves all of it to the Unit of Work; code that saves or commits by itself is refused by the structure tests.
</Callout>

## When to use it

Start a new .NET 10 application on the Kit when its business code should be split into Modules that each own their data, and you want the commit, the Outbox, the deliveries between Modules and the checks on your composition handled for you. One Module is a fine start: the [monolith template](/docs/templates/monolith) grows into a [modular monolith](/docs/templates/modular-monolith) when a second Module arrives, and a Module can later run as a [service](/docs/templates/service) of its own.

## What the Kit guarantees

These hold in every Capability. Each is stated in full on the page it links, and proven by the test class named beside it.

| Rule | Stated in | Proven by |
| --- | --- | --- |
| Feature code never saves, commits or touches the Outbox | [The Unit of Work](/docs/capabilities/persistence#the-unit-of-work) | `FeatureCodeTests` |
| A Notification Handler runs only after the commit | [Persistence guarantees](/docs/capabilities/persistence#what-the-kit-guarantees) | `NotificationTests` |
| Every failure answers one problem response | [Problem responses](/docs/capabilities/web#problem-responses) | `WebTests` |
| There is no default Actor | [The Operation Context](/docs/capabilities/modules#the-operation-context) | `OperationContextTests` |
| A tenant-scoped Module keeps to its Operation's tenant | [Multi-tenancy guarantees](/docs/capabilities/multi-tenancy#what-the-kit-guarantees) | `TenancyTests` |
| A declaration that cannot work fails the Host when it is built | [The Host's checks](/docs/capabilities/modules#the-hosts-checks) | `CompositionCheckTests` |

## Failure messages

The Kit refuses a mistake as early as it can, and its messages name what to change.

<Accordions>
  <Accordion title="The Host does not build">
    A [composition check](/docs/reference/glossary#composition-check) found a declaration that cannot work, such as `RemoveProductsCommand declares RequiresPermissionAttribute, but its check is not registered`. Every check is listed in [Host checks](/docs/reference/composition-checks).
  </Accordion>
  <Accordion title="The Host does not start">
    A [startup check](/docs/reference/glossary#startup-check) or an options validation failed, naming the setting or the call. A generated Host without `Authentication:Schemes:Bearer` is the first one most people meet: [Your first Host](/docs/get-started/first-host) fills it.
  </Accordion>
  <Accordion title="A call answers 403 Tenant.Required">
    Catalog is tenant-scoped in the monolith and the modular monolith, and the caller's token carries no `tenant` claim. See [Multi-tenancy](/docs/capabilities/multi-tenancy).
  </Accordion>
</Accordions>
