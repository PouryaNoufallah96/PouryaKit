## What it is

A [Module](/docs/reference/glossary#module) is a business boundary inside a Host: its own project, data, rules and public [Contracts](/docs/reference/glossary#contracts). Its [Composition Root](/docs/reference/glossary#composition-root) declares everything it needs and offers, and the Host adds it once. Anything outside the Module reaches it through its [Gateway](/docs/reference/glossary#gateway).

<Callout type="warn" title="The monolith has no Modules yet">
  The monolith registers Catalog on the Host's own services, without `PouryaKit.Modularity`. A second Module needs the modular monolith's composition. No aggregate, command, query, handler, validator, repository, read or event handler changes when you grow into it; the Composition Root, the endpoints and the Host's composition do.
</Callout>

## When to use it

When a part of your business has data and rules of its own that other parts should reach only through its Contracts. Calls between Modules of one Host stay in-process: Integration Events and Snapshots through the Host's Outbox, and a question through the owning Module's Contracts, never HTTP.

## Add it

<Steps>
<Step>

### Start from the modular monolith

Generate it, or grow the monolith into it. Growing changes nine files, listed in [Growing the monolith into a modular monolith](/docs/capabilities/templates#growing-the-monolith-into-a-modular-monolith).

```bash title="Terminal"
dotnet new pouryakit-modular-monolith -n Acme.Shop
```

</Step>
<Step>

### Create the Module's projects

Give the Module a folder under `src/Modules/` with its project, and a Contracts project when other Modules use what it publishes, as Catalog has `Catalog.Contracts`. Its project references `PouryaKit.Modularity` and the Kit packages its Features use; a Contracts project references nothing from the Kit and no Module. Add the project to the solution and reference it from the Host.

</Step>
<Step>

### Write its Composition Root

One public sealed class that implements `IModuleDefinition`, whose `Configure(ModuleBuilder module)` declares the Module's data, Features, handlers, publications, subscriptions and endpoints. It never names its own Module or assembly: the Kit infers both. [The Composition Root](/docs/capabilities/modules#the-composition-root) shows Catalog's.

</Step>
<Step>

### Add it to the Host

In `AppHost.cs`, add it beside the others with `modules.Add<…>()` in `AddPouryaKitModules`, and give it its own section in `appsettings.json` when it has settings.

</Step>
<Step>

### Give it a migration and migrate

Each Module keeps its own schema and its migrations in its own folder; [Migrations](/docs/capabilities/persistence#migrations) has the `dotnet ef migrations add` command. Then migrate it as [Your first Host](/docs/get-started/first-host) migrates Catalog, naming its project and its DbContext.

</Step>
</Steps>

## What holds for every Module

| Rule | Stated in | Proven by |
| --- | --- | --- |
| A Module references no other Module's implementation, and its only public types are its Composition Root and what its Host implements | [Structure tests](/docs/capabilities/testing#structure-tests) | `ModuleBoundaryTests` |
| A declaration belongs to the Module whose builder it was made on | [The Composition Root](/docs/capabilities/modules#the-composition-root) | `CompositionCheckTests` |

## Failure messages

<Accordions>
  <Accordion title="A declaration left on the Host's services">
    A declaration made on `builder.Services` in a Host of Modules belongs to no Module, and the Host fails when it is built, naming its form on the Module's builder and the form that names the Module.
  </Accordion>
  <Accordion title="A ConfigureContainer after AddPouryaKitModules">
    It replaces the container the checks install, and the Host fails when it starts, naming the call.
  </Accordion>
</Accordions>
