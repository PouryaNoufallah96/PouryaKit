---
title: Make a Module tenant-scoped
description: Require a tenant for every command and query of a Module, and read and save its aggregates only within the tenant of the Operation.
---

## What you build

A tenant-scoped [Module](/docs/reference/glossary#module) runs no [Operation](/docs/reference/glossary#operation) and applies no delivery without a [tenant](/docs/reference/glossary#tenant), and its tenant-scoped aggregates are read and saved only by Operations of the tenant they belong to. It is a registration across packages the [Host](/docs/reference/glossary#host) already has, not a package of its own. In the [Proving Sample](/docs/reference/glossary#proving-sample), Catalog and Ledger are tenant-scoped.

<Callout type="warn" title="A tenant comes only from a verified claim">
  At the HTTP boundary the tenant is read from the claim the bearer scheme verified, never from a host name or a route. So a tenant-scoped Module maps no public endpoint: an anonymous caller has no tenant, and its Operation would be refused.
</Callout>

## When to use it

When one Host serves several customers or companies and each must see and change only its own data. A Module that is not tenant-scoped can still keep a delivered tenant on its own rows, as Inventory does: see [Deliveries](/docs/capabilities/multi-tenancy#deliveries).

## Steps

<Steps>
<Step>

### Declare the Module tenant-scoped, first

Call `AddPouryaKitTenancy()` first in the Module's [Composition Root](/docs/reference/glossary#composition-root), before `AddPouryaKitCqrs` and `AddPouryaKitPermissions`. It registers the tenant requirement for every command and query the Module can dispatch, and a requirement registered first refuses a tenantless Operation before any authorizer of the Module's own reads data.

</Step>
<Step>

### Mark each aggregate that holds a tenant's data

Implement `ITenantScoped` on the aggregate, with a `Tenant` property it sets itself, from the tenant its handler takes from the [Operation Context](/docs/reference/glossary#operation-context). The [Kit](/docs/reference/glossary#kit) never sets it.

<Snippet file="samples/ModularMonolith/src/Modules/Catalog/Catalog/Products/Entities/Product.cs" region="product-create" />

Make a unique value unique per tenant: Catalog's name index is on the tenant and the name together. Then add a migration for the new column and index.

</Step>
<Step>

### State the tenant in every plain SQL read

EF Core reads of a tenant-scoped entity are filtered to the Operation's tenant for you. Dapper runs exactly the SQL you write, so a read of a tenant-scoped table states `tenant = current_setting('pouryakit.tenant')` itself, against the tenant the Kit's connection lease set. A structure test holds every such read to one grammar: see [Reading](/docs/capabilities/dapper-reads#reading).

## Failure messages

<Accordions>
  <Accordion title="Tenant.Required">
    The Operation, or a delivery into the Module, has no tenant. It fails before its validator and handler, and over HTTP answers 403. A delivery is retried, then set aside as a dead letter.
  </Accordion>
  <Accordion title="Tenant.Mismatch">
    The Operation added an aggregate for another tenant, or changed or removed one loaded under another tenant. The save is refused and nothing commits.
  </Accordion>
  <Accordion title="Tenant.NotLoaded">
    The Operation changed a tenant-scoped aggregate it attached instead of loading it through a query. Load it through the repository.
  </Accordion>
  <Accordion title="The Host does not build">
    A tenant-scoped Module may not declare a [recurring command](/docs/reference/glossary#recurring-command), a [Snapshot](/docs/reference/glossary#snapshot) of an aggregate whose key two tenants could share, or dispatch a command or query its tenancy declaration does not cover. Each check names the Module and what to change.
  </Accordion>
</Accordions>
