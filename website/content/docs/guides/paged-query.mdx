## What you build

A query that answers one [Page](/docs/reference/glossary#page) of a list: one bounded slice of the result, with its position and the total count. The query carries a `PageRequest` and answers `Page<T>`; a `PageDeclaration` beside it says what a caller may sort and filter by. This guide follows the [Proving Sample](/docs/reference/glossary#proving-sample)'s `ListProducts` [Feature](/docs/reference/glossary#feature).

<Callout type="warn" title="Nothing a caller sends becomes SQL">
  Sort keys and filter fields are declared by name, and the read maps each name to your own column or expression. A sort key or filter the declaration does not name is a validation [Error](/docs/reference/glossary#error), and a filter's value only ever reaches the database as a parameter.
</Callout>

## When to use it

For any read that returns a list. A read of one item is an ordinary query that answers it or a `NotFound` Error.

### Read the Page

Write the read's SQL once, in a static `PageSql`: the select of the items and the count of the same selection, sharing one `FROM` and `WHERE`. Map each sort key to a column, name a unique tie-breaker with `ThenBy`, and test each declared filter, which arrives as `@{field}_{operator}`, for null.

Catalog is tenant-scoped and its products soft-deletable, so the read states both the [tenant](/docs/reference/glossary#tenant) and `not p.is_deleted` itself: plain SQL reads no query filter. To read the Page through EF Core instead, see [Reading a Page](/docs/capabilities/persistence#reading-a-page) and [Dapper or an EF Core Page](/docs/decision-guides/dapper-or-ef-core-page).

</Step>
<Step>

### Bind it from the query string

The endpoint takes an `HttpPageRequest` parameter and passes its `Request` to the query, so a caller sends `?page=2&size=20&sort=name&direction=desc` and filters as `filter[name][contains]=lamp`. Never read paging parameters by hand. [A Page over HTTP](/docs/capabilities/web#a-page-over-http) shows `ListProducts`'s endpoint and the body it answers.

</Step>

## Failure messages

<Accordions>
  <Accordion title="400 with Page.SortUnknown, Page.FilterUnknown or another Page code">
    The request names a sort key, field or operator the declaration does not, or a size above its maximum. Each validation Error carries its code and its target, such as `Sort`. The [Error codes](/docs/reference/error-codes) page lists every `Page.` code.
  </Accordion>
  <Accordion title="400 with a detail and no errors">
    The query string itself could not be read, such as a page that is not a whole number or a direction other than `asc` or `desc`. Its `detail` names the rule it broke.
  </Accordion>
  <Accordion title="InvalidOperationException before any SQL runs">
    A request reached the read without its validator, or the read's mapping misses part of the declaration. A forgotten validator fails loudly; it never runs a caller's text as SQL.
  </Accordion>
</Accordions>
