---
title: Make a command idempotent
description: Let a client repeat a request it never got an answer to, and replay the first success instead of running the command again.
---

## What you build

A command a client may send again, after a response it never received, opts in with `[Idempotent]`. The client gives each request a [request id](/docs/reference/glossary#request-id), over HTTP its `Idempotency-Key` header. Inside the command's [Unit of Work](/docs/reference/glossary#unit-of-work) the [Kit](/docs/reference/glossary#kit) reserves a key made of the [tenant](/docs/reference/glossary#tenant), the [Actor](/docs/reference/glossary#actor), the command and that request id, so a repeat replays the first success without running the handler: nothing is written, saved or published again.

<Callout type="warn" title="The key alone decides">
  The Kit compares no body. A repeat with the same key and another body also replays the first success, so a client gives each distinct request its own key and reuses a key only to repeat one. Only a success is kept: a request that failed recorded nothing, and its repeat runs again.
</Callout>

## When to use it

For a write a client may retry after a lost response, such as creating a product. A command that runs only inside another, or a query, never needs it: a nested command joins the outer [Operation](/docs/reference/glossary#operation), and a query ignores the request id.

<Step>

### Require the key on its endpoint

Call `RequireIdempotencyKey()` on the [Module](/docs/reference/glossary#module)'s POST, PUT, PATCH or DELETE endpoint that sends the command. Every request to it must then carry an `Idempotency-Key` header, whose value becomes the request's id. [A repeatable write](/docs/capabilities/web#a-repeatable-write) shows `CreateProduct`'s endpoint. Another [Gateway](/docs/reference/glossary#gateway) caller sets the request id on the context it builds.

</Step>
<Step>

### Add the key table to the Module's schema

The keys live in a table of the Module's own schema, outside its model. Add an empty migration with `dotnet ef migrations add IdempotencyKeys` and the Module's options, as in [Add a migration](/docs/guides/add-a-migration), then fill it:

### Decide how long a key replays

The [Host](/docs/reference/glossary#host) keeps each key for its retention, then removes it, and a later repeat runs as a new request. Choose a retention longer than any client keeps retrying: see [Idempotency key retention](/docs/capabilities/persistence#idempotency-key-retention) for the setting and its default.

## Failure messages

<Accordions>
  <Accordion title="400 without errors">
    The request carried no `Idempotency-Key`, two of them, or a value the header's rule refuses. Its `detail` states the rule, and the body is never read.
  </Accordion>
  <Accordion title="InvalidOperationException naming the key table's call">
    The Module has no key table yet. The first opted-in command with a request id throws, and nothing commits. Add the migration above.
  </Accordion>
  <Accordion title="InvalidOperationException at dispatch">
    A request id reached an outermost command that does not opt in with `[Idempotent]`. Opt the command in, or stop requiring the key.
  </Accordion>
  <Accordion title="RequireIdempotencyKey on a read">
    On an endpoint mapped for GET, HEAD, OPTIONS or TRACE, or for no method at all, it throws when the endpoint is built, which stops the Host's start. Map the command with POST, PUT, PATCH or DELETE.
  </Accordion>
</Accordions>
