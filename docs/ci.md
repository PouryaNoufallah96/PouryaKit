# CI package validation

The `CI` workflow runs on pushes to `main` and to integration branches (`feat/**`, `wave-**`), all tag pushes, `pull_request` and input-free `workflow_dispatch`. Other topic branch pushes do not run CI; same-repository PR validation provides their automatic hosted checks. Private publication still follows only a `main` CI run. Private-fork workflow execution is disabled; the owner-accepted verification exception is documented under [Hosted proof boundary](#hosted-proof-boundary). `ai-setup` runs the AI configuration check, the docs check (`.agents/scripts/check-docs.py`) and the unit tests beside those scripts. It checks out the full history, because the docs check resolves the revision each architecture diagram pins, which a one-commit checkout lacks. `build-and-test` calls [the reusable package workflow](../.github/workflows/package-validation.yml) from the caller's own revision. It runs the [shared Release validation path](packages.md), including the existing Domain, Core helper, dispatcher, validation, Structure and PostgreSQL Proving Sample tests, every package in `scripts/packaging/inventory.json`, one clean consumer per inventory package and every composition consumer in the inventory. Debug build/test commands are replaced by these same checks against Release output. Before that path, `build-and-test` runs the unit tests in `scripts/ci/` and `scripts/packaging/`. Those in `scripts/ci/` execute the publication trust guard and original-artifact checks with read-only permissions and no feed credentials. `website` installs the docs site under `website/` with pnpm from its committed lockfile (`--frozen-lockfile`), then lints and builds it; until the site's `website/package.json` exists it prints one skip line naming that file and passes. The owner narrowed publication scope on 2026-10-06 to the standard Actions/NuGet path; [plan Phase 5](foundation-review.md#phase-5-packaging-and-releases) records what that scope leaves out.

An integration branch push runs CI by itself. For hosted proof on another topic branch before a PR, run `gh workflow run ci.yml --ref <branch>`. The manual run tests the selected branch SHA through the same validation path; a non-main run cannot authorize private publication. The orchestrator's local checks on the merged tree remain part of [spec execution](agents/running-a-spec.md). To read a failed run, `python3 .agents/scripts/ci-failures.py <run-id>` prints only its failed tests, each with the lines around its assertion.

While hosted runs are unavailable, reproduce the three jobs locally on the commit: every `run:` step of `ci.yml`'s `ai-setup` and `website` jobs, and of `package-validation.yml`'s job with an `--output` directory outside the checkout, except its two `scripts/ci/evidence.py` steps, which read the Actions run (`GITHUB_SHA`, the event payload) and have no local substitute. `.agents/scripts/ci-local.sh <evidence directory outside the checkout>` runs exactly those steps, keeps each step's full output and leaves the validation's log and evidence for reading. Report it as a local reproduction, never as a CI result. The [composition proof](packages.md#the-composition-proof) runs on that evidence directory afterwards, as a recorded step: neither CI nor the script runs it.

## Checkout and credentials

Checkout explicitly selects `github.sha` with `fetch-depth: 0`, `fetch-tags: true` and `persist-credentials: false`. The checkout action uses the read-only repository token to fetch the private repository, then removes its credentials. The shared command receives no token:

```bash
python3 scripts/packaging/validate.py --no-fetch --keep --output "$EVIDENCE_DIR"
```

`EVIDENCE_DIR` is a fresh directory under the runner's temporary directory, outside the checkout. It already holds `revision.json` and keeps the evidence for the artifact, so the command passes `--keep`: without it a directory that holds files is refused, since a PASS removes it. `--no-fetch` uses history already fetched by authenticated checkout and rejects shallow repositories. `history.json` records that mode, the checkout SHA and available tags. The ordinary local command still fetches origin. CI passes no `--since`, the flag with which a local run skips itself when only documentation, AI setup or the docs site changed, so every CI run is the full validation. No version is supplied by CI; MinVer derives the shared build/package version from this history.

For a PR, `github.sha` is the merge revision, not its head commit. `revision.json` checks the actual `HEAD` against that intended SHA and records the event, ref, repository, run ID/attempt, PR head/base SHAs and head repository. The job summary labels the tested SHA and PR head separately. Push validation tests the exact pushed SHA. Manual CI on main tests its selected main SHA; when the owner has tagged that current SHA, the full tag checkout supplies the named MinVer version. GitHub documents [PR merge revision semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) and [same-revision reusable calls](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#calling-a-reusable-workflow).

`CI`, `package-validation.yml` and their jobs grant only `contents: read`; unspecified token permissions are disabled. The reusable workflow has no secret inputs, inherited secrets or environment. Validation has no package publication, tag creation or GitHub Release path. It uses `pull_request`, never `pull_request_target`. GitHub's artifact service credentials let the upload action retain diagnostic artifacts; they are separate from package and repository write permissions. See [workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).

## Artifacts and downstream contract

On success or failure, the collector retains available packages, root validation logs, selected evidence JSON and consumer `obj/project.assets.json` files. It excludes NuGet caches, CLI homes, consumer configuration, raw webhook events and the mutated negative-control package sets. Symlinks that escape the evidence directory fail collection. Artifact names include the run ID and attempt, `package-validation-<run_id>-<run_attempt>`, with 90-day retention. Expired or unavailable artifacts cannot establish provenance for recovery.

The artifact contains:

| File | Meaning |
|---|---|
| `validation.json` | Repository, event/ref, run ID/attempt, tested SHA, PR identity, shared-path outcome, successful version and manifest location |
| `revision.json`, `history.json` | Intended/actual checkout agreement, non-shallow history, available tags and fetch mode |
| `manifest.json`, `packages/*.nupkg` | The successful shared path's source SHA/version/package IDs/filenames/SHA-256 record and original bytes |
| `*.log`, `evaluated-projects.json`, `minver.json` | Release/runtime/pack/consumer/control diagnostics and version proof |
| `package-evidence.json`, `consumers/**/obj/project.assets.json` | Package validation inputs and observed consumer closures; absolute paths identify the original runner, not a portable cache |

On success the collector checks that the manifest SHA equals the tested SHA and that every recorded package matches its checksum. A failed shared command remains a failed step/job, even if diagnostic collection and upload succeed. A failure receipt has no successful version or manifest pointer; partial packages remain diagnostics.

The reusable workflow exposes `tested_sha`, `version`, `validation_result`, `artifact_name` and immutable `artifact_id`. A publisher requires actual successful CI and AI/package jobs, and a trusted same-repository main `push` or `workflow_dispatch` run at the original SHA and attempt. It binds the downloaded receipt and manifest to that identity, checks the inventory and verifies the original local package hashes. A successful PR receipt identifies its tested merge SHA and cannot authorize publication.

The separate [private publication workflow](private-packages.md) uses the official artifact action to download the original run/attempt artifact. It keeps publication privileges outside PR validation and cancelable CI, uses standard NuGet push and checks a clean private-feed restore. `--skip-duplicate` skips HTTP 409 without verifying remote byte identity. Actual hosted publication evidence is recorded in [ticket #27](https://github.com/PouryaNoufallah96/PouryaKit/issues/27).

## Hosted proof boundary

The hosted CI and publication runs on main that completed Phase 5, and those that completed Wave 2, are recorded with their commits, versions and counts in [private package guidance](private-packages.md#hosted-completion).

On 2026-10-06, [temporary same-repository PR #30](https://github.com/PouryaNoufallah96/PouryaKit/pull/30) exercised the reviewed integration commit `be507881ac1aa6727b2fb830f91a72a5c1c14a3e`. It closed without merging. The proof branch alone introduced an undefined `IntentionalHostedConsumerFailure()` in the single-Module consumer fixture, then reverted it.

All three receipts distinguish their tested merge SHA from PR heads `1adba0fc2f49ef5b8a1b164133ab84506e6a0cd7`, `e67fff74b368067eaf5c869a65ff1080b6d099b6` and `112e47a6510bab3d03a6b359f6a379195b52251e`, respectively. Their base stays at the reviewed integration SHA. Actual checkout and shared-path logs confirm full history, all three existing Spike tags, `persist-credentials: false` and `--no-fetch`. MinVer produced `0.1.0-preview.0.8` in all three runs; PR merge height, not a run number, determines this version.

Both successful artifacts contain thirteen nupkgs whose downloaded SHA-256 values match their source-SHA/version manifests, fifteen clean consumer results and a PostgreSQL runtime suite with 386 succeeded, zero failed and zero skipped tests. The failed run also passed the runtime suite, then failed specifically in the single-Module consumer. Its package step, job and overall CI result failed; diagnostic collection/upload passed. Its receipt has no successful version or manifest pointer, and no manifest exists. Artifact names are `package-validation-<run_id>-1`; their uploaded sizes were 608,373, 499,201 and 608,302 bytes, with caches and consumer configuration absent.

Every run's setup logs show only `Contents: read` and `Metadata: read` for both actual jobs, `ai-setup` and `build-and-test / validate`; no publication job ran. The [integration push run](https://github.com/PouryaNoufallah96/PouryaKit/actions/runs/37448605551) also passed at exact SHA `be507881ac1aa6727b2fb830f91a72a5c1c14a3e` with those same two read-only jobs. Repository secrets/environment metadata contained zero entries. The source workflow forwards no release credentials; this inspection complements the observed token permissions rather than proving arbitrary secret absence by logging environment values. Before/after API records confirm main, tags, GitHub Releases and private-fork settings unchanged. This experiment performs no package-feed publication or verification.

Real private fork PR validation was not executed. The [owner accepted this exception](https://github.com/PouryaNoufallah96/PouryaKit/issues/26#issuecomment-6013184398) because no second account was available and prohibited access changes. Same-repository hosted PR validation and permission/credential isolation were observed; they do not prove fork execution. Repository access remains unchanged. All four private-fork settings remained false, including fork workflow execution, write-token forwarding and secret/variable forwarding; that settings receipt is static metadata, not a hosted fork result.
