# CI package validation

The `CI` workflow runs on pushes to `main` and to integration branches (`feat/**`, `wave-**`), all tag pushes, `pull_request` and input-free `workflow_dispatch`. Other topic branch pushes do not run CI; same-repository PR validation provides their automatic hosted checks. Private publication still follows only a `main` CI run. Private-fork workflow execution is disabled, as are write tokens and secrets for forks. `ai-setup` runs the AI configuration check, the docs check (`.agents/scripts/check-docs.py`) and the unit tests beside those scripts. It checks out the full history, because the docs check resolves the revision each architecture diagram pins, which a one-commit checkout lacks. `build-and-test` calls [the reusable package workflow](../.github/workflows/package-validation.yml) from the caller's own revision. It runs the [shared Release validation path](packages.md), including the existing Domain, Core helper, dispatcher, validation, Structure and PostgreSQL Proving Sample tests, every package in `scripts/packaging/inventory.json`, one clean consumer per inventory package and every composition consumer in the inventory. Before that path, `build-and-test` runs the unit tests in `scripts/ci/` and `scripts/packaging/`. Those in `scripts/ci/` execute the publication trust guard and original-artifact checks with read-only permissions and no feed credentials. `website` installs the docs site under `website/` with pnpm from its committed lockfile (`--frozen-lockfile`; a dependency's install script runs only when `website/pnpm-workspace.yaml`'s `allowBuilds` allows it), checks every npm package's licence against the site's allow-list (`pnpm --dir website check-licences`) and runs the site's tests (`pnpm --dir website test`: that check's, the covers', the content pipeline's and the public repository's), then lints the site and builds its static export: the build generates the pages it renders from the Kit's sources, fails when a package's README drifts from its template or quotes C# no sample, test or template holds, and fails when its export carries a private repository link, a local path, a private project's name, delivery vocabulary, a tracker code or a citation of the private plan, or lacks a page or an anchor a README links (`website/lib/kit-sources/`). Last, it typesets the covers (`pnpm --dir website covers`), fails when that render of `src/icon.png` differs from the committed file (`git diff --exit-code -- src/icon.png`), since each nupkg packs the committed icon and the public repository publishes the render, and regenerates the public repository's tree, which fails when its files differ from the committed manifest `website/distribution/manifest.sha256` in any way: a file missing, extra or changed (`pnpm --dir website sync-public --check`).

An integration branch push runs CI by itself. For hosted proof on another topic branch before a PR, run `gh workflow run ci.yml --ref <branch>`. The manual run tests the selected branch SHA through the same validation path; a non-main run cannot authorize private publication. The orchestrator's local checks on the merged tree remain part of [spec execution](agents/running-a-spec.md). To read a failed run, `python3 .agents/scripts/ci-failures.py <run-id>` prints only its failed tests, each with the lines around its assertion.

While hosted runs are unavailable, reproduce the three jobs locally on the commit: every `run:` step of `ci.yml`'s `ai-setup` and `website` jobs, and of `package-validation.yml`'s job with an `--output` directory outside the checkout, except its two `scripts/ci/evidence.py` steps, which read the Actions run (`GITHUB_SHA`, the event payload) and have no local substitute. `.agents/scripts/ci-local.sh <evidence directory outside the checkout>` runs exactly those steps, keeps each step's full output and leaves the validation's log and evidence for reading. Report it as a local reproduction, never as a CI result. The [composition proof](packages.md#the-composition-proof) runs on that evidence directory afterwards, as a recorded step: neither CI nor the script runs it.

## Checkout and credentials

Checkout explicitly selects `github.sha` with `fetch-depth: 0`, `fetch-tags: true` and `persist-credentials: false`. The checkout action uses the read-only repository token to fetch the private repository, then removes its credentials. The shared command receives no token:

```bash
python3 scripts/packaging/validate.py --no-fetch --keep --output "$EVIDENCE_DIR"
```

`EVIDENCE_DIR` is a fresh directory under the runner's temporary directory, outside the checkout. It already holds `revision.json` and keeps the evidence for the artifact, so the command passes `--keep` (see [package validation](packages.md)). `--no-fetch` uses history already fetched by authenticated checkout and rejects shallow repositories. `history.json` records that mode, the checkout SHA and available tags. The ordinary local command still fetches origin. CI passes no `--since`, the flag with which a local run skips itself when only documentation, AI setup or the docs site changed, so every CI run is the full validation. No version is supplied by CI; MinVer derives the shared build/package version from this history.

For a PR, `github.sha` is the merge revision, not its head commit. `revision.json` checks the actual `HEAD` against that intended SHA and records the event, ref, repository, run ID/attempt, PR head/base SHAs and head repository. The job summary labels the tested SHA and PR head separately. Push validation tests the exact pushed SHA. Manual CI on main tests its selected main SHA; when that SHA is tagged, the full tag checkout supplies the named MinVer version. GitHub documents [PR merge revision semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) and [same-revision reusable calls](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#calling-a-reusable-workflow).

`CI`, `package-validation.yml` and their jobs grant only `contents: read`; unspecified token permissions are disabled. The reusable workflow has no secret inputs, inherited secrets or environment. Validation has no package publication, tag creation or GitHub Release path. It uses `pull_request`, never `pull_request_target`. GitHub's artifact service credentials let the upload action retain diagnostic artifacts; they are separate from package and repository write permissions. See [workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).

## Artifacts and downstream contract

On success or failure, the collector retains available packages, root validation logs, selected evidence JSON and consumer `obj/project.assets.json` files. It excludes NuGet caches, CLI homes, consumer configuration, raw webhook events and the mutated negative-control package sets. Symlinks that escape the evidence directory fail collection. Artifact names include the run ID and attempt, `package-validation-<run_id>-<run_attempt>`, with 90-day retention. Expired or unavailable artifacts cannot establish provenance for recovery.

The artifact contains:

| File | Meaning |
|---|---|
| `validation.json` | Repository, event/ref, run ID/attempt, tested SHA, PR identity, shared-path outcome, successful version and manifest location |
| `revision.json`, `history.json` | Intended/actual checkout agreement, non-shallow history, available tags and fetch mode |
| `manifest.json`, `packages/*.nupkg` | The successful shared path's source SHA/version/package IDs/filenames/SHA-256 record and original bytes |
| `*.log`, `evaluated-projects.json`, `minver.json` | Release/runtime/pack/consumer/control diagnostics and version proof |
| `package-evidence.json`, `consumers/**/obj/project.assets.json` | Package validation inputs and observed consumer closures; absolute paths identify the original runner, not a portable cache |

On success the collector checks that the manifest SHA equals the tested SHA and that every recorded package matches its checksum. A failed shared command remains a failed step/job, even if diagnostic collection and upload succeed. A failure receipt has no successful version or manifest pointer; partial packages remain diagnostics.

The reusable workflow exposes `tested_sha`, `version`, `validation_result`, `artifact_name` and immutable `artifact_id`. The [private publication workflow](private-packages.md#publication-and-trust) consumes them. Only a successful `main` CI run can authorize it; a successful PR receipt identifies its tested merge SHA and cannot.
