# Running a spec

How `/implement-spec` runs in this repository, and what a session that drives more than one ticket must know. The steps and gates of each ticket are in `AGENTS.md`, "Workflow for every ticket".

## What changes from the skill

The vendored skill holds in shape: an integration branch, a frontier computed from the tracker's blocking edges, one worktree per ticket, implementers in parallel where their files are disjoint. Five of its steps are replaced:

| The skill says | Here |
|---|---|
| An implementer subagent calls `tdd` | A `kit-implementer` with a brief: `objective`, `allowed_files`, `verify`, optional `stop_if`, and why the work matters. |
| One `code-review` over the integration branch at the end | Review per ticket, sized as workflow step 3 says. The wave's last ticket is the close-out, where `/archify-review` runs once (step 6). |
| A draft pull request | One for the Wave, not one per ticket. Open the integration branch's pull request to `main` as a draft once the first ticket is merged, so the outside reviewers read the work as it lands instead of as one diff at the end; at each ticket close comment `@codex review` on it and judge what comes back as step 4 of `docs/agents/ai-setup.md` says; mark it ready at close-out, once `python3 .agents/scripts/merge-package.py --ready --branch <integration branch>` ends with `ready=yes`. That mode fetches `main` and, when it holds commits the branch lacks, lists them, the paths a merge would conflict in and what the tree check refuses in the merged tree, and changes nothing. A ticket still closes with `gh issue close <n> --comment` as soon as it is merged into the integration branch and its gates pass, so the blocking edges give the next frontier. |
| A merger subagent | The orchestrator merges a clean branch itself (`.agents/scripts/merge-package.py`, "State and handoff"); a merger subagent only on conflicts. |
| The implementer merges the integration tip before reporting | Not required. The orchestrator's merge, and its test run on the merged tree, cover it. |

## Worktrees

- Implementer worktrees start from the orchestrator's commit (`docs/agents/ai-setup.md`, "Subagent worktrees"); the role file's pre-flight is the backstop.
- The orchestrator stays in its checkout and reaches a worktree with `git -C <path>`; a `cd` would move the session's working directory.
- A worktree nested in the checkout inherits `global.json` and `Directory.*.props` from above when its own branch lacks them. A self-contained folder needs stoppers: see `docs/agents/spikes.md`.
- The review `base` is the `base` the implementer's report names, not the orchestrator's tip: implementers fast-forward or rebase onto a moving integration branch, and a Spike's branch starts from an older tip. A Spike record lands by `git cherry-pick` of its record commit after the `spike/<name>` tag is pushed; the code commit is never merged.
- A review reads a detached worktree, so the checkout stays free for merges. `/kit-review` (`.claude/workflows/kit-review.js`) creates and removes its own (step 3). For a single `kit-reviewer`, create one with `git worktree add --detach .claude/worktrees/review-<name> <commit>`, name it in the brief, and `git worktree remove` it afterwards. The reviewer may build and run tests there.

## State and handoff

- **One session owns the integration branch's checkout.** A second session works only in worktrees and signals through the tracker or a pushed tag. Hand off at a ticket boundary with nothing running, after about five closed tickets, earlier when a ticket needs a second review round: a session that ran eleven tickets without a handoff died with "Prompt is too long" before closing the last one. The next session starts in the foreground, in this checkout: Claude Code moves a session started with `claude --bg` into a worktree of its own before its first edit, away from the integration branch and from the gitignored `.claude/handoff/` (probed on 2026-10-09 with Claude Code 2.1.295).
- **The tracker is the state.** The orchestrator's run-state memory note holds only the pointer to the session's `HANDOFF.md` and the owner's decisions the tracker does not hold yet; the integration branch and what is running now are `HANDOFF.md`'s (next bullet). Keep the note under about 40 lines; narrative goes in closing comments, stable knowledge in this document.
- **Reports, briefs, evidence and the handoff go to `.claude/handoff/<session>/`**, gitignored like `.claude/reviews/`: the system temp directory's scratchpad is cleaned by macOS after three days without access, and a dead session's state must outlive it. As soon as a role's final report arrives, the orchestrator saves it verbatim as `.claude/handoff/<session>/report-<ticket>.md`, beside the ticket's evidence file, because subagents cannot write report files here: `python3 .agents/scripts/save-report.py <task-output.jsonl> .claude/handoff/<session>/report-<ticket>.md --title "<ticket> <role> report"` writes the agent's final message from the transcript the task notification names. `HANDOFF.md` in that directory carries the state, the running agents and the next steps; the run-state memory note names the directory, and the next session reads `HANDOFF.md` and those reports first. Validation output and other bulk stay in the scratchpad.
- **Running means spawned.** Before a status message or a handoff, `ListAgents` and `git worktree list` are the source of truth for what is running; a plan to spawn is not a running agent, and a message to an agent goes to the id its spawn result returned.
- **A report is a claim about a moment.** An implementer may commit after it reports, when an answer to a blocker or a scope grant reaches it late: before fixing a reported blocker yourself, read its worktree's tip (`git -C <worktree> log -1`), and merge the tip, not the stale `head` (`merge-package.py` refuses a branch whose tip is past the report's `head`; session 6 duplicated a two-line edit this way).
- **A brief names the frontier it was written for.** When the frontier changes (a ticket added or reordered), update the parallel-tickets line of every brief not yet spawned, so an implementer's `merge_notes` cover the tickets that actually run beside it (session 5's brief for #87 still said "runs alone" when four tickets ran beside it).
- **A failure seen twice is not a transient.** The second time a test fails the same way, send a `kit-scout` for the cause before a third run; sessions 4 and 5 called PostgreSQL's `53300` a transient four times before a scout found a deterministic near-limit (`docs/acceptance.md`, ticket #94).
- **The merged tree.** The implementer's verify counts as the merged-tree proof only when all three hold: the merge commit's tree equals the implementer's `head` tree, the report's verify ran on that `head` (its `commands` name no earlier commit), and the environment is the one the report names (same machine, SDK pin and containers). The orchestrator reads the report for the last two, and the merge script proves the first: `python3 .agents/scripts/merge-package.py .claude/handoff/<session>/report-<ticket>.md -m "<merge message>" --branch <integration branch> --push`, without `--push` when the report fails either condition. `--branch` is required and must be the checked-out branch; `main` is refused, since only the pull request merges there. The script takes `head`, `branch` and the validated commit (`validated`, or `commit <sha>` in `validate`) from the last JSON object in the saved report, so after an orchestrator fix round append one with the new `head` and `validated` (session 1 of Wave 3 did this four times) and refuses a dirty checkout, a `branch` that is not a branch name (`pkg~1`), a branch whose tip is past `head` (an agent that a queued message reached may commit after its report, and then its tip is merged or the agent asked, never the stale `head`), and a `head` that differs from the validated commit in any path but Markdown: a code change after `validate.py` ran is unproven, so the implementer reruns the validation on its head (session 3, 2026-10-09: a fix round added a test file after the validation and the merge went through unproven). It merges with `--no-ff`, compares the trees (`git diff --quiet <head> HEAD`), runs the AI-setup and docs checks, and pushes only when the tree is equal and every check passed. Its last line is the summary: `merge=<sha> tree=EQUAL|DIFFERS(<n>) checks=ok|FAIL(<names>) push=yes|no`. After `tree=DIFFERS`, or a merge without `--push`, run the ticket's `verify` on the merged tree, then push. A conflict leaves the merge in progress for the orchestrator to resolve and commit, and a failed check blocks the push until a fix is committed; then `merge-package.py --post-merge <head> --branch <integration branch>` runs the same checks, and the tree, which now differs from `head`, needs that `verify` before the push. Two packages that both append to `docs/acceptance.md` conflict there by design; keep both sections, in ticket order.
- **The closing comment is the ticket's record:** what landed and at which commits, the review and the disposition of each finding, a value, cost and impact paragraph (the `archify-review` lens), and the decisions and seams later tickets depend on. Copy commit hashes from command output.
- **A failed CI run:** `python3 .agents/scripts/ci-failures.py <run-id>` prints each failed test with the lines around its assertion, from the failed jobs' logs only. It takes about a minute, most of it the log download.
- **A fix after the normal rounds.** `AGENTS.md` caps a ticket at two full reviews. When the second raises a new high, a fresh `kit-implementer` takes it from a short handoff brief (the ticket, the branch and commit, the findings with their evidence, the files, the ticket's `verify`), because an implementer is resumed for one fix round at most. A single `kit-reviewer` then re-scores those findings only, from a detached worktree of the fix commit (`git worktree add --detach .claude/worktrees/review-<ticket> <commit>`, removed afterwards), and the closing comment records each finding's state. No third full review. A low the re-score raises follows step 4 of `AGENTS.md`: the orchestrator fixes a trivial, local one itself and re-scores it from the diff, and records a disposition otherwise.
- **Every brief allows the docs-sync set by default**, as `docs/agents/brief-template.md` lists it, and a package brief's `stop_if` never narrows it, so step 6 and 7 edits cost neither a fix round nor a scope request. Package validation is the last, post-commit step: the brief asks for the commit, then `python3 scripts/packaging/validate.py --no-fetch --since <the brief's integration tip> --output <fresh directory outside the checkout>` runs on the committed tree (it refuses uncommitted changes and needs full history and tags) and its PASS line goes in `docs/acceptance.md`. With `--since` the script decides from the paths that differ from that commit whether a package, a template or the validation itself could have changed, and prints one `SKIP` line when none could; the set of paths is in the script alone. CI passes no `--since`, so every push and pull request gets the full validation.
- **A brief starts from `docs/agents/brief-template.md`** and carries the ticket's own content and scope statement, as `AGENTS.md`, "Operating model", requires. For CI and packaging, apply its standard-tool and early external-probe rules before extending the implementation. The worktree base, the status (`README.md`) and the C# idioms (the build and `.claude/rules/kit-code.md`) are covered elsewhere. The harness supplies each agent's commit attribution, so a brief carries no trailer text.

## Merging with diagram conflicts

A merge that conflicts in a diagram source and its page (three of five package merges in Wave 3 session 2) goes to a merger subagent with the implementers' `merge_notes`: take both sides' nodes, edges and citations in the source, remap each cited range to the merged file (a range that only moved keeps its label; verify every citation against the side whose file the merge kept), take either page, build and run the architecture tests, commit the merge with `--no-verify` (no revision is current for both sides), then pin every re-ranged source to the merge commit, refinalize the pages with Archify, and commit the pins through the hooks. The merger commits with the session's attribution trailers passed explicitly (`git commit --trailer`), since a subagent's default trailer names its own model; the orchestrator amended five pin commits in Wave 3 session 3 for that. `merge-package.py` names the pairs when it stops on the conflict; its `--post-merge` run follows the pin commit. The union-merged implementer memory index keeps both sides' lines: `--post-merge` fails on a duplicated file until one line per file carries both sides' ticket numbers.

## Spikes

A Phase that opens with Spikes follows `docs/agents/spikes.md`. Name that document in each Spike's brief and in the brief of the review of its record: no rule loads for `spikes/` or `docs/adr/`, so the brief is how it reaches them.
