## The service defaults recipes

- **Kit files:** `samples/ModularMonolith/src/ModularMonolith.ServiceDefaults/Extensions.cs`, which `PouryaKit.Templates` packs into both templates
- **Upstream:** https://github.com/microsoft/aspire
- **Commit:** 3751e615ad660621f2a7aa4c390ef48e08a0eed8
- **Upstream paths:** `src/Aspire.ProjectTemplates/templates/aspire-servicedefaults/Extensions.cs`
- **Licence:** MIT
- **Adoption:** adapted
- **Ticket:** #52, recorded in the final audit of Wave 2 (2026-10-08)
- **Intentional differences:**
  - The class, its namespace `Microsoft.Extensions.Hosting`, the two endpoint path constants and the names `AddServiceDefaults`, `ConfigureOpenTelemetry`, `AddDefaultHealthChecks` and `MapDefaultEndpoints` are upstream's, so a Host composes the recipes as an Aspire project does; the members are C# 14 extension members.
  - OpenTelemetry adds the Kit's source and meter (`OperationTelemetry.SourceName`) beside the application's, Npgsql's own source `Npgsql` (ticket #80) and Microsoft.Extensions.AI's source and meter for the chat client of `PouryaKit.AI` (ticket #135), which upstream does not add, and exports over OTLP only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, as upstream does.
  - Readiness adds the `databases` check, which asks each registered DbContext whether its database answers; upstream has the `self` liveness check only.
  - Every `HttpClient` takes `AddPouryaKitResilience()`, which retries safe methods only, in place of upstream's `AddStandardResilienceHandler()`.
  - `/alive` is mapped in every environment, anonymous and exempt from rate limiting, and `/health` in Development only (ticket #64); upstream maps both in Development only.
  - `AddSerilogDefaults()` is the Kit's own recipe; upstream has none.

## Dead-letter and replay acceptance scenario

- **Kit files:** `tests/ModularMonolith.Tests/FailingDeliveryTests.cs`, `tests/ModularMonolith.Tests/Stub/StubCirculation.cs`
- **Upstream:** Ultrabusiness (`ultrabusiness_server_microservices`, a private repository with no public URL)
- **Commit:** a85eacd4db5e1af9b8349d49350be12397f24402
- **Upstream paths:** `src/Services/Treasury/Tests/Treasury.IntegrationTests/Features/IncomingChequeReceipt/Events/IncomingChequeReceiptCreatedForChequeDomainEventHandlerTests.cs` (`Deliver_WhenCreationFails_ShouldKeepSourceAndRecoverItsOriginalOccurrence`)
- **Licence:** unconfirmed
- **Adoption:** pattern
- **Ticket:** #17
- **Intentional differences:**
  - Kept: a delivery that keeps failing uses up its retries and is kept with its error, never recorded as processed, while the change that published it stays; once the cause is fixed and the delivery is put back, the original message is applied once.
  - Re-expressed for PostgreSQL and Wolverine: the delivery is set aside in Wolverine's dead-letter storage and replayed from there, through `PouryaKit.Testing`, instead of a retry counter and an error column on an outbox row.
  - Two subscriptions to one Integration Event, so the test also shows that the replay runs only the failed subscription's handler, and a second replay of the same delivery applies nothing because of its Receipt.
