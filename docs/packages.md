# Package validation and consumption

Run from a clean committed checkout with the SDK in `global.json`, Python 3.11 or later, Git access to origin and Docker running:

```bash
python3 scripts/packaging/validate.py
```

To preserve evidence at a chosen location, pass `--output /absolute/path/to/new-evidence-directory`. Use a fresh directory outside the checkout: one that already holds files is refused before any work unless `--keep` is passed, since a PASS removes the directory with everything in it. The default is a new system temporary directory. The command fetches origin's tags, completes shallow history, evaluates packability, builds Release once with `ContinuousIntegrationBuild=true`, runs the existing tests with `--no-build` and a run-level `--timeout 45m`, so a hung suite ends with the test platform's own exit code inside the hosted job's 60 minutes, and packs that output with `--no-build`. A failure stops the path before a manifest is written. The command never publishes packages or creates a tag in the Kit repository.

`--no-fetch` skips the fetch and rejects shallow repositories, so use it only when the complete history and tags are already fetched, as CI does ([CI guidance](ci.md)).

## The package set

[`scripts/packaging/inventory.json`](../scripts/packaging/inventory.json) is the explicit inventory of every Kit package ID; `PouryaKit.Templates` is marked `"kind": "template"`. The validator evaluates every source, test and sample project against it, but the projects under `src/PouryaKit.Templates/content`, which are template content. Missing projects, extra packable projects, mismatched IDs, duplicate or empty inventory entries and disabled package validation fail. Tests and samples are non-packable by default; the Kit's source projects, one per inventory package, are packable.

MinVer 8.0.0 is the only version engine, pinned centrally and private to the build. Its minimum major/minor is `0.1`, tag prefix is `v`, and default prerelease identifiers are `preview.0`. A temporary Git repository proves untagged, exact-tag and post-tag behaviour on each validation. The real package set must agree with MinVer's calculated package/build version. MinVer normalizes `AssemblyVersion` to `major.0.0.0` and `FileVersion` to `major.minor.patch.0`; prerelease identity lives in package and informational versions. See [MinVer's version rules](https://github.com/adamralph/minver/blob/9f485aabb9936efd8fb8b633ae09ae4d0659c94f/README.md#version-numbers).

Each nupkg contains `LICENSE` with the Kit's MIT text, source commit metadata with no repository URL in its nuspec, since the source repository is private (the embedded SourceLink map still names it), its project's `README.md`, the shared `icon.png` (`src/icon.png`), its project's own `PackageDescription`, held by equality, its tags, exactly the three every package shares and its project's own `PackageTags`, compared as a set, each once, and, but for the template package, which holds content only, a `net11.0` assembly with an embedded portable PDB and its XML documentation file, so a consumer reads the Kit's summaries in the editor. SDK 11 supplies GitHub SourceLink support. Validation reads the PDB's SourceLink map, checks its repository and commit, expands exact and wildcard mappings in order of specificity, and compares every package source document's mapped URL with its repository-relative path. A real embedded-PDB control with the correct repository/commit and a bogus file path must fail. This proves the map in the artifact; it does not prove authenticated downloads from the private GitHub source URL. `EnablePackageValidation` is on for every Kit package. This path sets no compatibility baseline.

| Package | Held at | Newest stable | Why | Released by |
|---|---|---|---|---|

| `Npgsql` | 10.0.3 | 11.0.0 | Npgsql 11 removed `NpgsqlConnectionStringBuilder.Multiplexing`, which `WolverineFx.Postgresql` 6.64.2, its newest stable, still reads as it builds its message store, so a Host with Wolverine's PostgreSQL message store fails when it starts (JasperFx/wolverine [issue 5725](https://github.com/JasperFx/wolverine/issues/5725), fixed by [pull request 5726](https://github.com/JasperFx/wolverine/pull/5726), unreleased on 2026-11-21). Marten's projection daemon, which the Kit does not run, fails the same way through `Weasel.Postgresql` 9.51.0's advisory lock (JasperFx/weasel [issue 910](https://github.com/JasperFx/weasel/issues/910)). The Kit's own two uses of the setting, the realtime listener's connection and the Dapper read connection's refusal of a multiplexed connection string, change with the move | A stable `WolverineFx` 6.x that runs on Npgsql 11, and a `Weasel.Postgresql` 9.x for Marten's projection daemon |
| `EFCore.NamingConventions` | 10.0.1 | 11.0.0 | 11.0.0 requires EF Core 11.0.0 or later, which the provider's release candidate refuses ([Temporary prerelease dependencies](#temporary-prerelease-dependencies)) | The stable EF Core line, with `Npgsql` 11 |

## Temporary prerelease dependencies

The Kit's EF Core line runs on the PostgreSQL provider's release candidate and the EF Core release candidate it pins, by the owner's decision of 2026-11-15: a prerelease package is allowed where no stable version serves, if it works and brings no significant compatibility or reliability issue. The stable line exists: EF Core 11.0.0 and `dotnet-ef` 11.0.0 since 2026-11-10, the stable `Npgsql.EntityFrameworkCore.PostgreSQL` 11.0.0 and `EFCore.NamingConventions` 11.0.0 since 2026-11-20. On 2026-11-21 it still does not serve: the stable provider requires the driver `Npgsql` 11.0.0, on which no Host with Wolverine's PostgreSQL message store starts, so `Npgsql` stays at 10.0.3 and the release candidates stay ([Held packages](#held-packages)). Each moves to its stable version, with the driver and `EFCore.NamingConventions` 11.0.0, when a stable `WolverineFx` 6.x runs on Npgsql 11.

| Package | Version | Why no stable version serves |
|---|---|---|
| `Npgsql.EntityFrameworkCore.PostgreSQL` | 11.0.0-rc.3 | 11.0.0 is stable since 2026-11-20, but requires `Npgsql` 11.0.0, which the Kit holds at 10.0.3. The stable 10.0.3 requires EF Core below 11 and fails on EF Core 11 at run time: its JSON type mapping calls an EF Core constructor that 11 no longer has |
| `Microsoft.EntityFrameworkCore.Relational` and `.Design` | 11.0.0-rc.3.26522.148 | 11.0.0 is stable, but the provider's release candidate requires EF Core and EF Core Relational at exactly this version, so 11.0.0 fails the restore (NU1608) |
| The `dotnet-ef` tool | 11.0.0-rc.3.26522.148 | It runs with the Hosts' EF Core Design, this version |

They bring EF Core itself, `Microsoft.EntityFrameworkCore`, with its abstractions and analyzers packages at the same version. These six packages are the only prereleases in any closure: `PackageGraph` refuses any other in a Kit package's restored closure and in every clean consumer's. EF Core's release candidate also asks for `Microsoft.Extensions.Logging`, `Microsoft.Extensions.Caching.Memory` and `Microsoft.Extensions.DependencyModel` at its own version, and the stable Roslyn 5.9.0 EF Core Design brings asks for the prerelease analyzer `Microsoft.CodeAnalysis.Analyzers` 5.9.0-1.26328.17, each as a minimum a stable version satisfies. So `PouryaKit.Persistence.EFCore` references `Microsoft.Extensions.Logging` and `Microsoft.Extensions.Caching.Memory` 11.0.0, where EF Core enters the Kit, and `PouryaKit.Messaging.Wolverine.EFCore` references `Microsoft.Extensions.DependencyModel` 11.0.0 and `Microsoft.CodeAnalysis.Analyzers` 5.12.0, where Design does; their nuspecs carry these stable floors to every consumer. The three `Microsoft.Extensions` floors leave when EF Core is stable; the analyzer floor stays for as long as EF Core Design brings Roslyn 5.9.0, which its stable 11.0.0 does too. `EFCore.NamingConventions` 10.0.1 admits the release candidate below its cap of 11.0.0, so it needs no override; its 11.0.0 waits with the stable line.

Tested on 2026-11-15, all on these versions: every test project, the Gateway suite three times, `dotnet ef migrations has-pending-model-changes` answering "No changes" for the five migrated models (so no table, column, key or index name moved), and the package validation, whose clean consumers and generated templates restore the packed packages with no override of their own. The risk a release candidate leaves: its code may differ from the stable release's, as earlier release candidates differed from EF Core 11.0.0, so the stable line is tested again before it replaces this one. A project that references EF Core 11.0.0 beside the Kit meets the provider's exact pin and fails its restore until then. No stable Kit version packs until then either: NuGet refuses a stable package with a prerelease dependency (NU5104, an error under the build's `TreatWarningsAsErrors`), which every Kit package that references EF Core or its provider directly has, so the Kit's versions stay previews.

## Clean consumers

The inventory also enumerates the compositions. A template consumer names its template and, as `generated`, the name its solution is generated under; the validation generates, builds, smoke-tests and publishes exactly the templates the inventory's consumers name, and finds each generated solution's Host and test project by that name (`<name>.Host` and `<name>.Tests`), so a template added to the inventory needs no change to the script.

| Consumer | What is built |
|---|---|
| Each library package ID in the inventory | A separate application compiling a public type from that package, with one direct Kit package reference |
| Single Module | The registrations and explicit Operation scope of [the Modules guidance](../.agents/skills/pourya-kit/references/modules.md#an-application-of-one-module), with Cqrs's Host entry `AddPouryaKitCompositionChecks`, using Cqrs, Validation, Postgres persistence, Dapper reads and Web without Modularity or Messaging |
| Modular monolith | A copy of the Proving Sample's two Hosts (`ModularMonolith.Host` and `Inventory.Host`), its `ModularMonolith.ServiceDefaults` recipe project, Modules and Contracts, with every Kit ProjectReference replaced by a package reference; each Host then takes the template Hosts' production step on the copy: `codegen write`, a Release restore and publish, and the same publish check (ADR 0004) |
| Template monolith | `dotnet new pouryakit-monolith -n Acme.Shop` from the produced `PouryaKit.Templates`, installed into a template hive of its own (`--debug:custom-hive`), restored with only the consumer's `NuGet.Config` and built as generated, its own `global.json`, build settings and central versions included; `PouryaKit.Modularity` and `PouryaKit.Testing` are refused in the closure of every project but the generated test project, which restores `PouryaKit.Testing` and, through it, Modularity, and its HTTP smoke test runs; then `codegen write` runs on its Host from the Release build, the Host is restored for Release and published, and the publish must hold the Host built with the generated code and neither `Wolverine.RuntimeCompilation.dll` nor `JasperFx.RuntimeCompiler.dll` (ADR 0004), nor an assembly of a refused package |
| Template modular monolith | `dotnet new pouryakit-modular-monolith -n acme-shop`, the same way, with a name a namespace cannot hold, so the generated solution's paths carry it as typed and its code `acme_shop`; `PouryaKit.Testing` is refused outside its test project, its smoke test runs, and its Host's Release publish is checked the same way |
| Template service | `dotnet new pouryakit-service`, the same way, as `-n Acme.Stock` and as `-n acme-stock`, two consumers: one Module, Inventory, with `Catalog.Contracts` and no Reverse proxy; `PouryaKit.Testing` and `PouryaKit.ReverseProxy` are refused outside its test project, its smoke tests run against PostgreSQL and RabbitMQ in containers, and its Host's Release publish is checked the same way |

The Service composition, one Module in its own process over RabbitMQ, is the template consumer above, `pouryakit-service`, generated from the business code that `Inventory.Host` runs; this validation also builds that Host from packages beside `ModularMonolith.Host` ([the project templates](../.agents/skills/pourya-kit/references/templates.md)).

Every consumer lives outside the checkout, has its own empty NuGet package and HTTP caches in a sibling directory outside its source globs, and uses source mapping to resolve `PouryaKit.*` only from the produced local feed. It inherits neither the checkout's build settings nor user feed configuration. Restored assets must name the expected Kit IDs at the exact release version as packages, with no source fallback. Each cached Kit nupkg must have the same SHA-256 as the produced artifact. The modular monolith's ProjectReferences are only between its copied application projects.

`PackageGraph` checks produced nuspecs and each Kit package's reachable restored consumer closure using the same reference table as the source tests. `LicenceTests` checks third-party licenses in those closures under ADR 0002. Private MinVer is excluded from the source dependency graph but remains in the source license check; a shipped MinVer reference fails the nuspec graph. Negative controls reject missing/extra artifacts, wrong versions and commit metadata, forbidden direct and restored transitive dependencies, and invalid symbols. The transitive control adds Npgsql under WolverineFx in real consumer assets and must fail specifically on the transport-neutral package's Npgsql exclusion. Inventory controls and the focused metadata tests cover the remaining inventory and license cases.

## Consume a verified local set

Run the validator with `--keep`, since after a PASS it removes its output directory otherwise, and use the `packages/` directory it prints as a local NuGet source. Select the version in its `manifest.json`, and use that same version for every Kit PackageReference or central PackageVersion. Keep `nuget.org` available for third-party dependencies. Under package source mapping, map `PouryaKit.*` to the local feed and `*` to nuget.org. The more specific Kit pattern keeps its dependencies in the verified set.

```xml
<PackageReference Include="PouryaKit.Web" Version="0.1.0-preview.0.HEIGHT" />
```

Replace the example version with the manifest's actual MinVer version. The shared validator never publishes; the [private publisher](private-packages.md) handles GitHub Packages publication and consumption. After its push it restores every library package from the feed and installs `PouryaKit.Templates` from it rather than referencing it, then generates and restores the solution of each template; only `main` publishes. `0.1.0-preview.2` is also on nuget.org ([nuget.org publication](private-packages.md#nugetorg-publication)), where no workflow publishes.

## Evidence

With `--keep`, the output directory retains `build.log`, `runtime-tests.log`, `pack.log`, `evaluated-projects.json`, `package-evidence.json`, `template-install.log`, individual consumer restore/build logs and each template consumer's smoke test, `codegen write` and publish logs, `consumer-closures.log`, negative-control logs and `minver.json`. `manifest.json` records the source commit, shared version and each package's filename and SHA-256. [CI](ci.md) preserves this directory as the original tested artifact set for the [private publisher](private-packages.md).

Package restore/build evidence is separate from the Proving Sample's PostgreSQL runtime suite. The latter still executes against the source projects' shared Release output. Consumer builds do not start PostgreSQL, the Host or its deliveries, but for the template consumers: each generated solution's smoke test hosts its generated Host in memory against PostgreSQL and, for the service, RabbitMQ in containers, so the validation needs Docker. Each smoke test run carries the same run-level `--timeout 45m`, so a hung fixture ends with the test platform's own exit code, also locally, where no job limit stops it. This command proves local packaging and consumption; hosted PR isolation, private-feed publication, compatibility with a named baseline and recovery require their own evidence.

## The composition proof

The smoke tests host each generated Host alone, in memory. `scripts/packaging/composition_proof.py` runs two of them together as processes, on the output directory of a validation kept with `--keep`, the way [`.agents/scripts/ci-local.sh`](../.agents/scripts/ci-local.sh) keeps it too:

```bash
python3 scripts/packaging/validate.py --keep --output /absolute/path/to/new-evidence-directory
python3 scripts/packaging/composition_proof.py /absolute/path/to/new-evidence-directory
```

It takes the inventory's `pouryakit-modular-monolith` and `pouryakit-service` consumers, starts `postgres:18.7` and `rabbitmq:4.4.0` in containers on free loopback ports, and migrates a database of its own for each solution with `dotnet tool restore` and `dotnet ef database update --configuration Release --no-build` per EF Core Module, with the consumer's isolated caches. It runs each Host's Release publish in Production with the same bearer issuer, audience and signing key, the service first, and waits until each Host's queue, the template's derived service name, has its consumer on the broker. It then creates a category and a product in the tenant `north` through the modular monolith's Catalog with a token it signs, and asks the service's `GetStockItem` until it answers 200 with that product's id, within 60 seconds. It prints one `PASS composition proof` line naming both generated solutions, the queues and the stock item observed, or a `FAIL` line with the last answer, and stops both Hosts and removes both containers with their anonymous volumes either way; each step's output is in `<output>/composition-proof/`. A wrong wire name, queue name or missing subscription in generated content fails it. It is a recorded step, not a step of the validation, which neither runs nor needs it; its own token, inputs and PASS line have unit tests in `scripts/packaging/test_composition_proof.py`.
